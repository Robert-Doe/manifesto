HTTP Versions & Keep-Alive

From a One-Line Protocol in 1991 to QUIC in 2022

Every time your extension calls fetch(), sends a message to an API, or loads a script from a CDN, HTTP is doing the work underneath. Understanding which version of HTTP is being used — and why that version exists — makes you a dramatically better debugger. You will stop thinking of "the network" as a black box and start seeing it as a series of engineering trade-offs made by real people solving real bottlenecks. This mini-module tells that story from the first one-line protocol in 1991 to QUIC in 2022, with keep-alive as the red thread running through every version.

Why HTTP Keeps Changing

HTTP is the application-layer protocol that web browsers and servers use to exchange documents, data, and media. It was designed to be simple, stateless, and text-based. Those three properties were exactly right for 1991 — when a "web page" was a single HTML file with no images, no scripts, and no stylesheets. A user requested one file. The server returned it. Done.

The problem is that the web did not stay simple. A modern web page makes 50–200 HTTP requests per load: HTML, CSS files, JavaScript bundles, fonts, images, API calls, tracking pixels. Each of those requests costs time. The history of HTTP versions is the history of engineers figuring out how to pay that cost as cheaply as possible.

Every major version of HTTP was born out of a specific bottleneck that had become intolerable. The bottlenecks changed as hardware, bandwidth, and usage patterns evolved. Understanding the bottleneck each version solved is the fastest way to understand what each version actually does.

TCP Primer — The Layer Below HTTP

To understand keep-alive, you first need to understand TCP, because keep-alive is fundamentally about TCP connection reuse.

HTTP/1.x and HTTP/2 run on top of TCP (Transmission Control Protocol). TCP provides a reliable, ordered byte stream between two endpoints. Before any data can be exchanged, TCP must complete a three-way handshake:

Client                          Server
  ──── SYN ───────────────────────►   client: "I want to connect"
  ◄─── SYN-ACK ────────────────────   server: "ok, I acknowledge"
  ──── ACK ───────────────────────►   client: "confirmed"
  ... data can now flow ...
  ──── FIN ───────────────────────►   client: "I'm done"
  ◄─── FIN-ACK ────────────────────   server: "closing"

The three-way handshake costs 1 round-trip time (RTT) before a single byte of HTTP data can be sent. If you add TLS (HTTPS), that's another 1–2 RTTs for the TLS handshake. On a connection with 100ms latency, just opening a new HTTPS connection costs 200–300ms before the server even sees your GET request.

Now imagine doing that for every single resource on a page. That was the reality of HTTP/1.0, and it was slow.

HTTP/0.9 — The One-Line Protocol (1991)

HTTP / 0.9 · 1991 · Tim Berners-Lee at CERN

The One-Line Protocol

RFC: None (pre-standard) Transport: TCP TLS: No Keep-Alive: No
No headers No status codes No methods except GET Connection closes immediately Extremely simple

HTTP/0.9 barely deserves to be called a protocol. A complete request was a single line:

Complete HTTP/0.9 transaction:

GET /index.html

↓ Server responds with the raw HTML, no headers, then closes the connection

<html>Hello, World</html>
[connection closes]

There were no HTTP headers of any kind. No Content-Type, no Content-Length, no status codes. If the file didn't exist, the server sent back an HTML error page with no way to distinguish it from a successful response. The only way to know the response was complete was that the server closed the TCP connection.

This design makes one assumption that would haunt HTTP for decades: one TCP connection carries exactly one resource, then closes. For a world with one HTML file per page, that was fine. It would not stay fine.

HTTP/1.0 — Headers Arrive (1996)

HTTP / 1.0 · May 1996 · RFC 1945

Headers, Methods, Status Codes

RFC 1945 Transport: TCP TLS: Optional (HTTPS) Keep-Alive: Optional (non-standard)
HTTP headers Status codes (200, 404, 500…) GET, POST, HEAD methods Content-Type, Content-Length Connection closes after every response Keep-Alive as opt-in extension

By 1996, web pages had images. A page with 10 images meant 11 HTTP transactions: one for the HTML, ten for the images. Each transaction required its own TCP connection. HTTP/1.0 brought the richness of headers and status codes, but kept the same connection model: one request, one response, connection closes.

HTTP/1.0 — one full transaction per resource:

TCP handshake (1 RTT)
GET /index.html HTTP/1.0
Host: example.com
User-Agent: Mosaic/2.4

↓
HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 1453

<html>...</html>
[connection closes immediately]
[new TCP handshake needed for next resource]

Keep-Alive in HTTP/1.0 — The Unofficial Extension

Browser vendors noticed the performance disaster of per-resource TCP connections almost immediately. Netscape and Internet Explorer began supporting a non-standard extension header in their implementations:

Connection: keep-alive
Keep-Alive: timeout=5, max=100

If both client and server sent this header, they agreed to keep the TCP connection open after the response, ready for the next request. The TCP handshake overhead was paid once instead of once per resource.

The Problem With 1.0 Keep-Alive
HTTP/1.0 keep-alive was a vendor extension — it was not in the RFC. There was no standard for what timeout and max meant across different server implementations. Proxy servers often didn't understand the header and would pass it through to backend servers, causing desynchronization. It worked well enough in practice but was messy in theory. HTTP/1.1 would fix this by making persistent connections the default.

The performance gain was dramatic. Browsers began opening 2–4 parallel TCP connections per domain (to get around the serial nature of HTTP/1.0) and reusing them with keep-alive headers. This is the architectural root of a behavior you can still observe today in browser DevTools — connections being established, reused, and eventually closed on a timeout.

HTTP/1.1 — The Protocol That Ran the Web for 18 Years (1997)

HTTP / 1.1 · January 1997 · RFC 2068, updated RFC 2616, revised RFC 7230–7235

Persistent Connections, Chunked Transfer, Host Header

RFC 2616 / 7230–7235 Transport: TCP TLS: Standard via HTTPS Keep-Alive: Default ON
Persistent connections by default Chunked transfer encoding Host header (virtual hosting) Pipelining (spec) Cache-Control, ETag, If-Modified-Since Head-of-line blocking (response ordering) Pipelining broken in practice Header repetition — no compression

Persistent Connections — Keep-Alive Becomes the Default

HTTP/1.1's most important change was inverting the default: connections are now persistent (keep-alive) by default. You have to explicitly opt out:

HTTP/1.1 — connection stays open unless told otherwise

GET /style.css HTTP/1.1
Host: example.com
[no Connection header needed — persistent is assumed]

HTTP/1.1 200 OK
Content-Type: text/css
Content-Length: 4832
[connection stays open — browser sends next request immediately]

GET /app.js HTTP/1.1
Host: example.com
... and so on, all over the same TCP connection

To close explicitly:
Connection: close

This single change dramatically reduced page load times. Instead of paying 1 RTT per resource for TCP handshakes, you pay it once per domain for the duration of the connection. The Host header (new in 1.1) enabled virtual hosting — multiple websites on a single IP address — which is why the modern internet is economically feasible.

The keep-alive parameters became standardized server configuration rather than per-request headers:

  • timeout — how many seconds the server will hold an idle connection open waiting for the next request. Typical values: 5–120 seconds. Apache default: 5s. Nginx default: 75s.
  • max requests — how many requests the server will serve on one connection before closing it. Protects against memory leaks and ensures load is distributed across server processes. Typical: 100–1000.

Pipelining — The Feature That Failed

HTTP/1.1 also introduced pipelining: the ability to send multiple requests without waiting for a response to each one first. Instead of request → wait → response → request → wait → response, you could send request₁ → request₂ → request₃ and then receive response₁ → response₂ → response₃.

On paper, this eliminates the serial wait time. In practice, pipelining had a fatal problem: Head-of-Line (HOL) blocking.

The server must respond to requests in the same order they were received. If request₁ is a 5 MB video file and request₂ is a tiny 200-byte CSS file, the CSS response cannot be delivered until the video response is complete — even though the server could have served the CSS in microseconds.

Head-of-Line Blocking in HTTP/1.1 Pipelining
REQ 1: video.mp4
▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 5 MB — BLOCKING THE QUEUE
REQ 2: style.css
waiting... waiting... waiting... (200 bytes, ready instantly)
REQ 3: logo.png
waiting... waiting... waiting... (4 KB, ready instantly)
Requests 2 and 3 are stuck behind the slow video response despite being tiny. This is HOL blocking.

Because of HOL blocking, browser vendors never enabled pipelining by default. Instead they opened 6 parallel TCP connections per domain (the HTTP/1.1 RFC limit), allowing different resources to be fetched concurrently on different connections. Each connection still had serial HOL blocking, but 6 connections in parallel reduced the wall-clock time substantially.

The 6-connection limit itself became a problem. Web developers responded with domain sharding — splitting resources across static1.example.com, static2.example.com, etc., to get more than 6 connections per page. This technique is an anti-pattern in HTTP/2 but was standard practice for a decade of HTTP/1.1.

HTTP/2 — Multiplexing Solves HOL Blocking (2015)

HTTP / 2 · May 2015 · RFC 7540 (now RFC 9113)

Binary Framing, Multiplexing, Header Compression, Server Push

RFC 7540 / 9113 Transport: TCP TLS: Required in practice (browsers enforce) Keep-Alive: One persistent connection, always
Multiplexed streams — no HOL blocking at HTTP layer Binary framing (not text) HPACK header compression Server push Stream prioritization TCP-level HOL blocking remains Head-of-queue at TCP layer on packet loss

HTTP/2 was developed by Google (originally as the SPDY protocol) specifically to fix the architectural limitations of HTTP/1.1. The fundamental insight was: the serial request/response model of HTTP/1.1 is not a law of physics. It is a protocol choice. We can choose differently.

Multiplexing — Many Streams, One Connection

HTTP/2 introduces the concept of streams: logical request/response channels multiplexed over a single TCP connection. Instead of text, HTTP/2 sends binary frames. Each frame has a stream ID. The receiver reassembles frames with the same stream ID into a complete request or response.

HTTP/2 binary frame format (simplified):

+──────────────────────────────────────────────────────+
│  Length (24 bits)  │  Type (8 bits)  │  Flags (8 bits) │
+──────────────────────────────────────────────────────+
│  Stream Identifier (31 bits)                          │
+──────────────────────────────────────────────────────+
│  Frame Payload (variable)                             │
+──────────────────────────────────────────────────────+

Types: DATA, HEADERS, PRIORITY, RST_STREAM, SETTINGS,
       PUSH_PROMISE, PING, GOAWAY, WINDOW_UPDATE, CONTINUATION

On a single TCP connection, the server can interleave frames from multiple streams freely. Stream 1 might be sending video frames while stream 3 is receiving a CSS file and stream 7 is sending a POST body. No stream blocks another at the HTTP layer.

HPACK Header Compression

HTTP/1.1 headers are text, and they repeat constantly. Every request from a browser to a server sends the same Accept, Accept-Encoding, Accept-Language, User-Agent, and Cookie headers — verbatim, every single time. On a page with 100 requests, that's 100 copies of the same 800-byte header block.

HTTP/2 solves this with HPACK: a stateful compression scheme that maintains a header table on both client and server. Common headers are assigned short integer codes. On the first request, you send the full header. On subsequent requests, you send the integer code. A header that was 800 bytes becomes 4 bytes.

First request — full headers sent:
:method: GET          → stored in table at index 62
:path:   /index.html  → stored at index 63
:scheme: https        → already in static table at index 7
user-agent: Chrome/124 → stored at index 64

Second request — only changed headers need resending:
:method:  [62]        → 1 byte instead of 14
:path:    /style.css  → new path, must send in full
:scheme:  [7]         → 1 byte
user-agent: [64]      → 1 byte instead of 18

Server Push — Proactive Resource Delivery

HTTP/2 allows the server to push resources to the client before they are requested. When the server returns the HTML for /index.html, it can simultaneously push style.css and app.js — resources it knows the browser will need — without waiting for the browser to parse the HTML and request them.

In practice, server push was largely a failure. It's hard for servers to predict exactly what the browser already has in cache. Pushing resources the browser already has wastes bandwidth. Chrome removed support for HTTP/2 server push in 2022. The concept survives as the 103 Early Hints response code (the server sends a hint about what to preload before sending the full 200 response).

HTTP/2's Remaining Problem: TCP-level HOL Blocking
HTTP/2 solved HOL blocking at the HTTP layer. But it still runs over TCP, which has its own HOL blocking: if a single TCP packet is lost, all streams pause while TCP retransmits that packet — even streams that don't need the lost data. On a lossy mobile network, a 1% packet loss rate causes TCP retransmit delays that affect every active HTTP/2 stream simultaneously. This is the exact problem HTTP/3 was designed to solve.

HTTP/3 — Replacing TCP With QUIC (2022)

HTTP / 3 · June 2022 · RFC 9114

QUIC Transport, 0-RTT Connections, True Stream Independence

RFC 9114 Transport: QUIC (UDP-based) TLS 1.3: Always, built into QUIC Keep-Alive: Connection ID survives network changes
No TCP HOL blocking — stream independence at transport layer 0-RTT reconnection TLS 1.3 built in (not bolted on) Connection migration (IP change survival) QPACK header compression UDP — less firewall/NAT support than TCP Higher CPU usage (user-space protocol stack)

QUIC — A New Transport Protocol Built on UDP

The engineers at Google recognized that the only way to eliminate TCP's HOL blocking was to stop using TCP. But TCP is deeply embedded in operating systems, routers, and firewalls — you can't just replace it with a new kernel-level protocol and expect it to work everywhere.

The solution: build a new transport protocol on top of UDP in user space. UDP is fire-and-forget — it has no ordering guarantees and no retransmit logic. QUIC implements its own reliable, ordered delivery, but crucially, it implements it per stream rather than per connection.

In TCP, the entire connection shares a single ordered byte stream. A lost packet at byte position 1000 stalls everything until position 1000 is retransmitted, even if you only need bytes at position 5000. In QUIC, each stream has its own sequence numbers. A lost packet in stream 1 stalls only stream 1. Streams 2, 3, and 4 keep flowing.

TCP packet loss — affects all HTTP/2 streams:

Stream 1: ▓▓▓▓▓ X ▓▓▓▓   ← packet X lost
Stream 3: ▓▓▓▓▓ WAIT       ← BLOCKED waiting for X retransmit
Stream 5: ▓▓▓▓▓ WAIT       ← BLOCKED waiting for X retransmit

QUIC packet loss — only the affected stream stalls:

Stream 1: ▓▓▓▓▓ X ▓▓▓▓   ← packet X lost, stream 1 stalls, retransmitting
Stream 3: ▓▓▓▓▓▓▓▓▓▓    ← CONTINUES — unaffected
Stream 5: ▓▓▓▓▓▓▓▓▓▓    ← CONTINUES — unaffected

0-RTT Handshake — Reconnecting With Zero Latency

QUIC integrates TLS 1.3 at the protocol level rather than layering it on top of TCP. This allows a dramatic optimization for reconnections:

ScenarioTCP + TLS 1.2TCP + TLS 1.3QUIC (HTTP/3)
First connection3-way TCP + 2 TLS = 3 RTT3-way TCP + 1 TLS = 2 RTT1 RTT (QUIC + TLS together)
Reconnection (seen server before)3-way TCP + 1 TLS = 2 RTT3-way TCP + 0 TLS (session resumption) = 1 RTT0 RTT — first packet carries data

In 0-RTT mode, the client uses a session ticket from a previous connection to encrypt the very first packet. That first packet contains the HTTP request. The server can process the request before the handshake is complete. The response can arrive before a second round-trip. On a 100ms latency connection, this saves 100–300ms on every reconnection.

HTTP/3 also introduces connection migration: QUIC connections are identified by a 64-bit Connection ID rather than by the client's IP address and port. When you walk from a WiFi network to a cellular network, your IP address changes. A TCP connection is destroyed and must be re-established. A QUIC connection simply migrates — the client sends a packet with the same Connection ID from the new IP, and the server continues the connection seamlessly.

HTTP/3 Adoption in 2024
As of mid-2024, approximately 30% of web traffic uses HTTP/3, up from nearly 0% in 2020. Chrome, Firefox, and Safari all support it. Major CDNs (Cloudflare, Fastly, Google) serve HTTP/3 by default. The challenge is network middleboxes (firewalls, load balancers, corporate proxies) that block UDP traffic on port 443. HTTP/3 falls back to HTTP/2 when QUIC is blocked.

Keep-Alive: The Full Story

Keep-alive is the single concept that threads through every HTTP version. Let's now explain it completely, from first principles to modern implications.

Why Keep-Alive Was Invented

Establishing a TCP connection is expensive in three ways:

  • Time: The three-way handshake costs 1 RTT. On a 50ms connection, that's 50ms before a single byte of HTTP data can flow. On a 200ms intercontinental connection, it's 200ms.
  • CPU: Both client and server allocate buffers, initialize sequence numbers, and negotiate window sizes. At scale, millions of short-lived connections per second stress server CPU and kernel memory.
  • TCP slow start: Every new TCP connection begins in "slow start" mode — it starts with a small congestion window and ramps up bandwidth gradually over the first few round-trips. A connection that's closed immediately after one response never escapes slow start. A reused connection has already ramped up to full speed.

Keep-alive solves all three. The TCP connection is established once. The handshake cost is paid once. Slow start is paid once. Subsequent requests on the same connection flow immediately at full bandwidth.

The Keep-Alive Parameters Explained

HTTP/1.0 — client signals desire for keep-alive:
Connection: keep-alive
Keep-Alive: timeout=30, max=100

HTTP/1.1 — server confirms with same headers (or just Connection: keep-alive):
Connection: keep-alive
Keep-Alive: timeout=75

HTTP/1.1 — closing a persistent connection explicitly:
Connection: close

timeout=N — The server will keep the connection open for N seconds after the last response, waiting for another request. If no request arrives within N seconds, the server closes the connection. The client should also close its end before the timeout (to avoid sending a request on a connection that the server has already closed, causing a connection reset error).

max=N — The server will close the connection after N requests have been served on it. This prevents a single client from monopolizing a server process indefinitely. Apache's default is 100; Nginx doesn't implement this parameter but uses keepalive_requests (default 1000 since Nginx 1.19).

TCP Keep-Alive vs HTTP Keep-Alive — A Critical Distinction

These are two completely different mechanisms that happen to share a name:

TCP Keep-AliveHTTP Keep-Alive
LayerTransport (Layer 4)Application (Layer 7)
PurposeDetect dead connections (send probes to confirm peer is still alive)Reuse connections for multiple HTTP requests
How it worksSends empty ACK packets at a configurable interval to the peerKeeps the TCP connection open instead of closing after each response
Who controls itOperating system kernel settings (tcp_keepalive_time, tcp_keepalive_interval, tcp_keepalive_probes)HTTP headers / server config
Relevant toLong-lived connections through NAT (routers that time out idle flows)Web performance, connection reuse

When an extension developer says "keep-alive" in the context of a Chrome extension's chrome.runtime.connect() port, they mean a third kind of keep-alive — an application-level technique for keeping the service worker alive (see Module 05). These three meanings must never be conflated.

The Extension Development Angle

Everything you just learned directly affects how you write extension networking code:

fetch() reuses connections. Chrome's fetch() API uses the browser's HTTP stack, which maintains a connection pool per origin. If your extension's service worker calls fetch('https://api.example.com/a') followed by fetch('https://api.example.com/b'), the second request reuses the same TCP connection (and the same QUIC stream or HTTP/2 stream, depending on the server's version). You don't pay a new handshake for every API call — as long as you don't wait too long between calls (exceeding the server's keep-alive timeout).

The 6-connection limit. Even in HTTP/1.1, Chrome maintains at most 6 connections per origin in the pool. If your extension hammers an API with 20 parallel fetch() calls, 14 of them queue until one of the 6 slots frees up. HTTP/2 eliminates this problem — one multiplexed connection handles all 20 requests simultaneously.

Service worker death kills in-flight requests. HTTP connections are owned by the browser's network process, not the service worker. A fetch() initiated from a service worker that then gets killed will... continue! The network process is separate from the JS process. The response will arrive, but the service worker callback won't be there to receive it unless the worker wakes up again. This is why you should use event.waitUntil(fetch(...)) in service worker fetch handlers — it tells Chrome to keep the worker alive until the fetch completes.

CORS and network requests from extensions. Content scripts make requests from the context of the page's origin. Background service workers make requests from the extension's origin (chrome-extension://id/). The CORS rules that apply to the page don't apply to background requests — background fetch calls get full CORS bypass for origins listed in the manifest's host_permissions. Understanding which HTTP context your code runs in is essential for debugging network errors in extensions.

Exercises

Exercise 01

Observe HTTP Versions in DevTools

  1. Open Chrome DevTools → Network tab. Visit https://www.google.com.
  2. Right-click the column headers in the Network tab → enable "Protocol".
  3. Sort by Protocol. Find resources labeled h2 (HTTP/2) and h3 (HTTP/3). Identify at least one of each.
  4. Click a request. In the Headers tab, find the :method, :path, and :status pseudo-headers — these are HTTP/2's binary headers rendered as text by DevTools.
  5. Visit a site that uses HTTP/1.1 only (try a small personal site or internal tool). Compare how many connections are opened vs Google.
What to look for: On a modern site, nearly all requests should show h2 or h3. If you see http/1.1, it's likely a third-party domain (ad networks often lag behind on HTTP version upgrades).
Exercise 02

Measure TCP Connection Cost

  1. In DevTools Network tab, enable the "Timing" column. Click any request and look at the "Timing" tab.
  2. Find a request where "Initial connection" is greater than 0ms. This is the TCP + TLS handshake cost.
  3. Find a second request to the same domain. Verify "Initial connection" is 0ms — it reused the connection.
  4. Calculate: how much total time was saved on the page load by reusing connections instead of opening a new one per request?
Tip: Sort by "Time" (total duration) to find the slowest requests. Then check whether they were the first to a domain (paying handshake cost) or reusing a connection.
Exercise 03

Write a fetch() That Reuses Connections

  1. In your NeuralTab extension's background service worker (or in the browser console), write code that makes 5 sequential fetch() calls to the same origin (e.g., https://httpbin.org/get?n=1 through ?n=5).
  2. Observe in DevTools → Network tab whether Chrome reuses the same connection (look at the "Connection ID" column if available, or check Timing for "Initial connection" = 0ms on requests 2–5).
  3. Now modify the code to add a 10-second delay between calls with await new Promise(r => setTimeout(r, 10000)). Does the connection get reused after the long gap? (Depends on the server's keep-alive timeout.)
Expected result: Sequential calls to the same origin should reuse the connection. After a long gap, the server may have closed its end and Chrome must open a new connection.
Exercise 04

Understand the Three Kinds of Keep-Alive

  1. Write a one-paragraph explanation of each of the three meanings of "keep-alive" in your own words: (a) TCP keep-alive probes, (b) HTTP persistent connections, (c) Chrome extension port keepalive from Module 05.
  2. For each one, write one sentence describing when you would use it in an extension and when you would not.
Key distinction: TCP keep-alive prevents router NAT tables from timing out idle connections. HTTP keep-alive prevents the overhead of re-establishing TCP for sequential requests. Extension port keep-alive prevents Chrome from killing the service worker. They solve three completely different problems at three different layers.
Exercise 05

Head-of-Line Blocking in Slow Network Simulation

  1. In Chrome DevTools → Network tab → throttling dropdown → "Slow 3G".
  2. Visit a page with many resources (try any news site). Observe the waterfall chart.
  3. Look for resources that start fetching much later despite being requested early. These are experiencing HOL blocking or connection queue exhaustion.
  4. Disable throttling. Observe the same page load without the constraint. Note how many resources load in parallel vs serial.
  5. In your notes: explain whether the page uses HTTP/2 and whether that helps the HOL blocking situation under slow conditions.
HTTP/2 nuance: On slow 3G, HTTP/2 can sometimes perform worse than HTTP/1.1 due to TCP-level HOL blocking amplifying packet loss. HTTP/3 (QUIC) would perform better in these conditions because stream independence extends to the transport layer.

Summary

The Story in Six Sentences

  • HTTP/0.9 (1991) was a one-line protocol with no headers, no status codes, and one TCP connection per resource — fine for a world of single HTML documents.
  • HTTP/1.0 (1996) added headers, methods, and status codes, but kept closing the connection after every response; vendors patched this with the non-standard Connection: keep-alive header.
  • HTTP/1.1 (1997) made persistent connections the default, standardized keep-alive, added chunked transfer and the Host header — and ran the entire web for nearly two decades.
  • HTTP/2 (2015) replaced the text protocol with binary framing, introduced multiplexed streams to eliminate HTTP-layer HOL blocking, and added HPACK header compression — but TCP-layer HOL blocking remained.
  • HTTP/3 (2022) replaced TCP with QUIC (UDP-based), achieving per-stream reliability with no shared HOL blocking, 0-RTT reconnection, TLS built-in, and connection migration when IP addresses change.
  • Keep-alive is the thread running through all versions: the insight that TCP handshake overhead must be amortized across multiple requests, not paid once per resource — and that understanding this is essential for writing performant extension networking code.
