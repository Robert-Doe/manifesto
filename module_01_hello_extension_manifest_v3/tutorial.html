What Is a Browser Extension — Really?

Most people think of a browser extension as a small app that adds a button to the toolbar. That is the visible surface, but it is not the definition. A browser extension is a privileged web application that runs inside the browser process with elevated access to browser internals — access that normal web pages are explicitly forbidden from having.

A normal webpage running at https://example.com cannot see what other tabs are open. It cannot read your bookmarks. It cannot intercept a network request made by a different page. It cannot modify what you see on another website. These restrictions exist because the web's security model assumes pages are untrusted — served by strangers over the internet.

An extension is different. You install an extension deliberately, which is an act of explicit trust. In exchange for that trust, the browser grants the extension capabilities far beyond what any web page can do. An extension can read every tab's URL and title. It can intercept and block network requests. It can inject JavaScript into any page you visit. It can read and write your bookmarks and history. It can listen to every keystroke in every tab. This power is why extension security matters enormously — and why the Chrome Web Store vets every extension before publishing it.

Structurally, an extension is a directory of files — HTML, CSS, JavaScript, images, and one special file called manifest.json. The manifest is the single file that Chrome reads first. It tells Chrome everything about what your extension is, what it wants to do, and what permissions it needs to do it. Without a valid manifest, Chrome will refuse to load your extension entirely. With a valid manifest, your directory becomes a living part of the browser.

Key Insight
Extensions are not installed from a web server at runtime — they are installed once and then live inside Chrome's profile directory on your hard drive. When you open a new tab or visit a page, Chrome reads the extension's files directly from disk. This is why extensions load instantly and work offline.

The Four Contexts of a Chrome Extension

One of the most confusing things about extension development is that your code runs in multiple separate JavaScript environments simultaneously, each with different capabilities and different lifetimes. Before you write a single line of code, you need to have a mental model of these four contexts.

1. Popup Page

The HTML page that appears when you click the toolbar icon. It has full access to Chrome APIs. It exists only while the popup is open — the moment you click away, it is destroyed and all its JavaScript variables are gone.

2. Background Service Worker

A JavaScript file that runs in the background, responding to browser events (a tab being created, an alarm firing, a network request). It is ephemeral — Chrome kills it after 5 minutes of idle time. Introduced in Module 05.

3. Content Script

JavaScript injected into web pages you visit. It can read and modify the page's DOM. It runs in an "isolated world" — it shares the DOM with the page but has its own separate JavaScript heap. Introduced in Module 02.

4. Options / Side Panel Page

Full HTML pages hosted by the extension. The options page is for settings. The Side Panel (Module 16) is a persistent panel that stays open as you navigate. Both have full API access like the popup.

Manifest V3 vs Manifest V2 — Why It Matters

If you search for browser extension tutorials online, you will find two kinds: ones that use "manifest_version": 2 and ones that use "manifest_version": 3. This distinction is critical. MV2 is dead. Google began force-disabling MV2 extensions in Chrome Stable in June 2024. By the time you finish this course, attempting to install an MV2 extension in Chrome will fail silently.

MV3 was introduced in Chrome 88 (January 2021) and is now mandatory. The key differences that affect real-world development are:

Area Manifest V2 (dead) Manifest V3 (current)
Background Persistent background.html page — stays alive forever Ephemeral service worker — killed after 5 min idle
Network interception webRequest blocking — can modify request/response bodies declarativeNetRequest — rules-based, cannot read bodies
Remote code Could load JS from external CDN at runtime Strictly forbidden — all code must be in the extension package
CSP Relaxed — inline scripts allowed with unsafe-inline Strict — no inline scripts, no eval(), no unsafe-eval
Host permissions Mixed into permissions array Separate host_permissions array — clearer model
Warning — Ignore MV2 Tutorials
You will encounter MV2 code on Stack Overflow, YouTube, and older blog posts. The APIs look similar but the behaviour is different. If a tutorial uses background.page, chrome.extension.getBackgroundPage(), or blocking webRequest, it is MV2 and will not work in your extension. Always check the manifest version before following any guide.

Anatomy of manifest.json — Every Key Explained

The manifest is a JSON file. JSON does not allow comments, which makes it unfriendly for learning. Below we walk through NeuralTab's manifest key by key, with a full explanation of what each one does and what Chrome does when it reads it.

Tip — Chrome Validates Your Manifest
If your manifest.json has a typo, a missing required key, or an invalid value, Chrome will refuse to load your extension and show a red error on the chrome://extensions page. This is your first debugging tool — always check that page when your extension fails to load.

Code Walkthrough — Every File Explained

manifest.json — The Extension's Identity Card

This is the only file Chrome reads directly. Everything else — popup.html, popup.js, content scripts, icons — is referenced from here. Chrome will not load a file unless it is reachable from a chain starting at manifest.json.

manifest.json JSON 
{
  // ① The ONLY valid value in 2024+. MV2 is disabled by Chrome.
  "manifest_version": 3,

  // ② Shown in the Chrome Web Store and on chrome://extensions
  "name": "NeuralTab",

  // ③ Semantic version. Chrome Web Store requires you to increment
  //    this every time you publish an update. Format: major.minor.patch
  "version": "0.1.0",

  // ④ Shown below the name in the Web Store and extensions page
  "description": "Your AI-powered browser assistant. Module 01: The Foundation.",

  // ⑤ "action" defines the toolbar button behaviour.
  //    default_popup: the HTML file that opens when user clicks the icon.
  //    If you omit default_popup, clicking the icon fires the
  //    chrome.action.onClicked event in the background worker instead.
  "action": {
    "default_popup": "popup.html",

    // ⑥ Three sizes required: 16px (toolbar), 48px (extensions page),
    //    128px (Chrome Web Store). Chrome picks the best size for context.
    "default_icon": {
      "16":  "icons/icon16.png",
      "48":  "icons/icon48.png",
      "128": "icons/icon128.png"
    },

    // ⑦ Tooltip shown when user hovers over the toolbar icon
    "default_title": "NeuralTab — Click to open"
  },

  // ⑧ "icons" is separate from action.default_icon.
  //    This one is used on the chrome://extensions page and in the
  //    Web Store listing. They can differ from the toolbar icon,
  //    but in practice you use the same files.
  "icons": {
    "16":  "icons/icon16.png",
    "48":  "icons/icon48.png",
    "128": "icons/icon128.png"
  },

  // ⑨ Chrome API permissions your extension needs.
  //    We declare ZERO right now. Chrome.tabs.query with
  //    {active:true, currentWindow:true} works WITHOUT "tabs" permission.
  //    We add permissions only when we need them — not upfront.
  "permissions": [],

  // ⑩ Domains your extension can access via fetch() or XMLHttpRequest.
  //    Also controls which pages your content scripts can inject into.
  //    Empty for now — we add these in Module 09 when we hit real APIs.
  "host_permissions": []
}
KeyRequired?What Chrome does with it
manifest_versionrequired Rejects the extension if not 3
namerequired Shown in toolbar tooltip, extensions page, Web Store
versionrequired Used by CWS to detect new uploads; must increment on every publish
descriptionoptional Shown on chrome://extensions and in the Web Store listing
actionoptional Defines toolbar button. Omit it and no icon appears at all
iconsoptional Extension page + Web Store images. Chrome shows grey puzzle piece if absent
permissionsoptional Gates which chrome.* APIs you can call
host_permissionsoptional Gates which URLs your extension can access or inject into

popup.html — The Extension's UI Shell

The popup is an ordinary HTML page with one critical constraint: no inline JavaScript is allowed. This is enforced by the extension's Content Security Policy, which MV3 applies automatically. Every <script> tag must use a src attribute pointing to a separate file. Inline event handlers like onclick="fn()" are also blocked. This is not a bug — it is a deliberate security feature that prevents injected content from executing code in your privileged extension context.

Danger — This Will Silently Fail
Writing <script>alert('hello')</script> inside popup.html will produce a CSP violation error in the DevTools console and do nothing. Your JavaScript must always live in a .js file referenced via <script src="popup.js"></script>. The same rule applies to options.html, sidepanel.html, and any other extension-owned HTML page.
popup.html HTML 
<!DOCTYPE html>
<html lang="en">
<head>
  <!-- charset must be UTF-8. Chrome enforces this for extension pages. -->
  <meta charset="UTF-8" />
  <title>NeuralTab</title>
  <!-- External stylesheet is allowed. Only inline <style> blocks and
       inline JS are blocked by CSP. -->
  <link rel="stylesheet" href="popup.css" />
</head>
<body>

  <!-- All sections with IDs so popup.js can target them -->
  <div class="header"> ... </div>

  <!-- #current-url and #tab-title filled by popup.js at runtime -->
  <span id="current-url">Loading...</span>

  <!-- Buttons use data-action attributes, not onclick handlers -->
  <button class="btn btn-green" data-action="on">Set ON</button>

  <!-- Script is ALWAYS at the bottom, ALWAYS in a separate file -->
  <script src="popup.js"></script>
</body>
</html>

popup.js — Reading the Active Tab and Controlling the Badge

This is where the interesting logic lives. There are three things happening: reading the current tab, filling in extension metadata, and handling button clicks. Let's walk through each one.

popup.js — Part 1: Reading the active tab JavaScript 
'use strict';  // Catch accidental globals and undeclared variables

// Grab DOM references once at startup.
// We store them in constants so we do not re-query on every event.
const elUrl  = document.getElementById('current-url');
const elTitle= document.getElementById('tab-title');

// chrome.tabs.query() returns a Promise in MV3.
// The filter narrows results to exactly the one active tab.
//
// WHY no "tabs" permission?
// The "tabs" permission gates access to tab.url and tab.title for
// background tabs (tabs the user is not on). The active tab in the
// CURRENT WINDOW is always readable without any permission — Chrome
// considers this low-risk because the user is already looking at it.
chrome.tabs.query({ active: true, currentWindow: true })
  .then(([tab]) => {

    // tab may be undefined on chrome:// or edge:// internal pages
    if (!tab) {
      elUrl.textContent   = 'No active tab found';
      elTitle.textContent = '—';
      return;
    }

    // tab.url is empty for restricted pages (chrome://, file://) when
    // the "tabs" permission is absent. We handle that gracefully.
    elUrl.textContent   = tab.url   || '(restricted — no URL access)';
    elTitle.textContent = tab.title || '(no title)';

    // Update the badge immediately when popup opens
    chrome.action.setBadgeText({ text: '✓', tabId: tab.id });
    chrome.action.setBadgeBackgroundColor({ color: '#4ade80', tabId: tab.id });
  })
  .catch((err) => {
    elUrl.textContent = `Error: ${err.message}`;
  });
popup.js — Part 2: Extension metadata JavaScript 
// chrome.runtime.getManifest() returns YOUR manifest.json as a JS object.
// Chrome parses and caches it — this call is synchronous and instant.
// It is the only way to read your own manifest at runtime without fetch().
const manifest = chrome.runtime.getManifest();

document.getElementById('ext-id').textContent
  = chrome.runtime.id;      // 32-char string like "abcdefghijklmnopqrstuvwxyzabcdef"

document.getElementById('ext-version').textContent
  = manifest.version;       // "0.1.0" — read from manifest.json

document.getElementById('manifest-ver').textContent
  = `v${manifest.manifest_version}`;  // "v3"
popup.js — Part 3: Badge control buttons JavaScript 
let clickCount = 0;  // lives in popup.js memory — reset when popup closes

// Query ALL buttons at once, loop over them.
// Each button has data-action="on|count|clear" — avoids writing
// three separate event listeners for three nearly identical handlers.
document.querySelectorAll('.btn').forEach((btn) => {
  btn.addEventListener('click', () => {
    const action = btn.dataset.action;

    if (action === 'on') {
      // Omitting tabId means the badge applies to ALL tabs globally
      chrome.action.setBadgeText({ text: 'ON' });
      chrome.action.setBadgeBackgroundColor({ color: '#4ade80' });
    }

    if (action === 'count') {
      clickCount++;
      chrome.action.setBadgeText({ text: String(clickCount) });
      chrome.action.setBadgeBackgroundColor({ color: '#fb923c' });
    }

    if (action === 'clear') {
      clickCount = 0;
      // Empty string removes the badge overlay entirely
      chrome.action.setBadgeText({ text: '' });
    }
  });
});
Key Insight — The Badge Persists, The Variable Does Not
Notice that clickCount is a JavaScript variable in popup.js. When you close the popup, that variable is destroyed. If you reopen the popup, clickCount resets to 0. However, the badge itself persists — it is stored by Chrome in the extension's action state, not in your JS memory. This is the fundamental lesson of extension development: anything stored in a JavaScript variable dies when the context closes. Anything stored via a chrome.* API (badge, storage, alarm) persists. We will use chrome.storage from Module 03 onward to solve exactly this problem.

Build & Run — Loading Your Extension Into Chrome

Unlike a website, you do not run a server to develop an extension. Chrome loads extension files directly from your hard drive. The workflow during development is: edit a file → reload the extension → test. No build step is needed until Module 18 when we introduce the Vite/TypeScript toolchain.

Step 1 — Generate Your Icons

Before loading the extension, you need three PNG icon files. We generate them in-browser to avoid any tooling dependency.

  1. Open module_01/icons/create_icons.html in Chrome by dragging it into a new tab, or by going to File → Open File in Chrome.

  2. Click Download icon16.png, then Download icon48.png, then Download icon128.png.

  3. Move all three downloaded files into the module_01/icons/ folder. The filenames must match exactly: icon16.png, icon48.png, icon128.png.

Step 2 — Load the Extension as Unpacked

  1. Open a new Chrome tab and navigate to chrome://extensions

  2. Toggle Developer mode ON — it is the switch in the top-right corner of the page. The page will refresh and show three new buttons.

  3. Click Load unpacked. A file picker opens. Navigate to and select your module_01/ folder — the folder that contains manifest.json directly inside it.

  4. If everything is correct, a NeuralTab card appears on the extensions page. If there is a red error message, read it carefully — it tells you exactly what is wrong in your manifest.

  5. Click the puzzle-piece icon in the Chrome toolbar, find NeuralTab in the list, and click the pin icon to make it permanently visible in the toolbar.

Step 3 — Test It

  1. Open module_01/demo/index.html in Chrome (drag it into a new tab).

  2. Click the NeuralTab ⚡ icon in the toolbar. The popup opens.

  3. Verify the popup shows the demo page's URL and title. Both should match what you see in the browser's address bar and title bar.

  4. Click Set ON — the toolbar icon badge should immediately show "ON" in green. Click Count three times — should show 1, 2, 3. Click Clear — badge disappears.

Step 4 — Reload After Every Edit

Chrome does not automatically detect file changes in unpacked extensions. Every time you edit a file, you must tell Chrome to reload. There are two ways:

How to reload after editing 
Option A (faster):
  Go to chrome://extensions → find NeuralTab → click the ↺ reload button
  Then close and reopen the popup.

Option B (keyboard):
  Navigate to chrome://extensions, then press R while the NeuralTab card is focused.

Note: Changes to popup.html and popup.js take effect immediately after
reload. Changes to manifest.json ALWAYS require a reload — Chrome only
reads the manifest when the extension loads, not on every popup open.
Tip — Open the Popup's DevTools
To debug the popup, right-click anywhere inside the open popup and select Inspect. This opens a dedicated DevTools window for the popup page — you can see console logs, the DOM, network requests, and errors exactly as you would for any web page. This is your primary debugging tool for all popup-context code.

Exercises

Do not skip these. Each exercise is carefully designed to surface an insight that the prose cannot convey — only by breaking something and fixing it do you actually understand it.

Warm-Up Exercise 1 — Break the Manifest and Read the Error

The goal is to see Chrome's manifest validation in action and learn to read its error messages — a skill you will use constantly.

  • Open manifest.json and delete the "name" key entirely. Save the file.
  • Go to chrome://extensions and click the ↺ reload button on NeuralTab.
  • Read the red error message that appears. Notice exactly what Chrome says is missing.
  • Now restore the "name" key and reload again — the error disappears.
  • Repeat this experiment: remove "manifest_version" and observe the error.
  • Try changing "manifest_version": 3 to "manifest_version": 2. What happens?
What to notice: Chrome's error messages name the exact key that is missing or invalid. Reading them carefully saves hours of debugging. Also notice that changing to manifest_version 2 does NOT give an error — Chrome still loads it, but marks the extension as "deprecated" and it will stop working in future Chrome versions.
Warm-Up Exercise 2 — Prove the Inline Script Block

The MV3 Content Security Policy block on inline scripts is not obvious until you see it fail. Let's see it fail deliberately.

  • Open popup.html and add this line just before the closing </body> tag:
    <script>console.log('inline test');</script>
  • Reload the extension and open the popup.
  • Open the popup's DevTools (right-click → Inspect inside the popup).
  • Check the Console tab. You should see a CSP violation error — the inline script was blocked.
  • Now move that console.log into popup.js instead. Reload and verify it works.
What to notice: The CSP error message mentions "unsafe-inline" and names the policy that blocked it. This is the exact same error you will see if you accidentally paste inline JS into an extension page later in the course — now you will recognise it immediately.
Core Exercise 3 — Add a "Tab Count" Feature

Modify popup.js to display how many tabs are currently open in all Chrome windows. Add a new section to popup.html to show this number.

  • Call chrome.tabs.query({}) — empty filter object returns ALL tabs across ALL windows.
  • The promise resolves with an array of tab objects. Use .length to get the count.
  • Add a new <div class="section"> block in popup.html with a label "OPEN TABS" and a span with id "tab-count".
  • In popup.js, fill in tab-count with the result.
  • Open 5 new tabs, then open the popup again. Verify the count updates.
Hint: You do NOT need to add any permission to the manifest for this. chrome.tabs.query({}) returns a count of all tabs but the URL and title fields will be empty for tabs you are not currently on — that is the tabs permission gate in action.
Core Exercise 4 — Persist the Badge Across Popup Opens

The clickCount variable in popup.js resets to 0 every time the popup closes. Your task is to make the count survive popup opens and closes using chrome.storage.local — even though we cover storage formally in Module 03, the API is simple enough to use now. This is the most important exercise in Module 01.

  • At the top of popup.js, load the saved count when the popup opens:
    chrome.storage.local.get('clickCount', (data) => { clickCount = data.clickCount || 0; });
  • After incrementing clickCount in the "count" button handler, save it back:
    chrome.storage.local.set({ clickCount });
  • Also update chrome.action.setBadgeText inside the storage.get callback so the badge reflects the loaded count on popup open.
  • Test: click Count 3 times → close popup → reopen popup → count should resume at 3, not reset to 0.
What you just learned: You used a Chrome API to persist state across context lifecycles. This is the core discipline of extension development. The popup dies. The badge state lives in Chrome. The count now lives in chrome.storage. In Module 07 we build a full storage abstraction layer around this pattern.
Stretch Exercise 5 — Build a "Permissions Explorer" Popup

Create a second HTML page called permissions.html with a link from the main popup. This page should dynamically list every permission that NeuralTab is currently granted, and for each one, show a one-line explanation of what it allows.

  • Add a small link at the bottom of popup.html: <a href="permissions.html" target="_blank">View permissions</a>
  • Create permissions.html with a linked permissions.js
  • In permissions.js, call chrome.runtime.getManifest() and read the permissions array
  • Build a hardcoded lookup object that maps permission name → human explanation, for example:
    "tabs": "Read the URL and title of all open tabs"
    "storage": "Store data in the browser that survives restarts"
    "alarms": "Schedule timers that wake up the service worker"
    (include at least 10 common ones)
  • Render the list dynamically. Currently NeuralTab has zero permissions — the page should say "No permissions declared".
  • Add "storage" to the manifest permissions array, reload, and verify the page now shows it.
Why this matters: In Module 03 you will implement the full Optional Permissions flow. Understanding what each permission means before you request it is the foundation of good permissions UX design.

Content Scripts, DOM Surgery & Web Accessible Resources

Right now NeuralTab lives entirely inside its own popup. It can read tab metadata, but it cannot touch the actual web page — its DOM, its text, its structure. In Module 02 we fix that by introducing content scripts, the mechanism that lets your extension reach into any webpage and modify what the user sees. We will inject a floating "Summarize" button onto every article page the user visits — the first visible, in-page feature of NeuralTab. Along the way you will learn why content scripts run in an "isolated world" (they share the DOM but cannot touch the page's JavaScript variables), and you will master web_accessible_resources — the manifest key that lets you inject your own fonts, images, and scripts into third-party pages without being blocked by their Content Security Policy. The new file added in Module 02 is content.js, which is the script Chrome automatically injects into every page you declare as a match pattern — and understanding how Chrome decides when to inject it, and into which frame, is the core lesson of that module.
