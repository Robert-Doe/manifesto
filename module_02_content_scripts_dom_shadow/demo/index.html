The Isolated Worlds Demo

This page deliberately defines JavaScript variables in the main world (world 0). Open your browser DevTools console. Type window.myPageSecret — you will see the value. Now open the content script's world by selecting "NeuralTab content script" in the console's context dropdown. Type the same variable — you will get undefined. Same page. Different JavaScript heaps. That is isolated worlds in action.

Long-form Article Content — For Word Count Testing

Understanding the architecture of modern web browsers requires grappling with an astonishing complexity of interconnected subsystems. The rendering engine, JavaScript runtime, networking stack, and security sandbox all interact in ways that are simultaneously elegant and terrifying. When a browser extension developer writes a content script, they are participating in a carefully orchestrated system that Chrome has evolved over fifteen years of continuous development.

The concept of isolated worlds was introduced specifically to address a security vulnerability that existed in early browser extension implementations. If content scripts shared the same JavaScript execution environment as the host page, a malicious page could modify JavaScript prototypes — Array.prototype.push, for example — and corrupt the extension's behaviour. By separating the heaps entirely, Chrome guarantees that the extension's JavaScript environment is pristine regardless of what the host page does to its own environment.

Consider what this means practically: if a page runs Array.prototype.map = () => 'hacked', a content script that calls [1,2,3].map(x => x * 2) will still return [2,4,6] because it is operating on its own separate Array prototype chain. The page's modification is invisible. This is not magic — it is a consequence of V8 creating separate JavaScript contexts (called Isolates and Contexts at the engine level) for each world. We explore this in depth in Module 10 when we study V8 internals directly.

Web Accessible Resources solve a complementary problem. An extension's files live inside the browser's extension package — inaccessible to the web by default. If a content script tries to inject an image from the extension package into a page using a relative URL, it will get a 404 because the page's origin cannot resolve extension-internal paths. The web_accessible_resources manifest key is an explicit whitelist: "these specific files may be loaded by pages whose origin matches these patterns." Chrome generates a special URL for each listed resource in the format chrome-extension://[extension-id]/[resource-path], which the page can load as if it were a normal web resource.

This is also why inject.js can be loaded as a script tag from content.js. The content script builds a URL by calling chrome.runtime.getURL('assets/inject.js'), which returns the full chrome-extension:// URL. It then creates a script element with that URL as the src attribute and appends it to the document. Chrome fetches the file from the extension package, executes it in the page's main world, and the cross-world communication channel via postMessage does the rest.

Single-Page Applications present a unique challenge for content script developers. In a traditional multi-page website, every navigation triggers a full page reload and Chrome re-injects the content script fresh. In a React or Next.js application, clicking a navigation link updates the URL and rerenders the component tree without any page reload. Chrome does not re-inject content scripts on these soft navigations because there is no navigation event — only DOM mutations and a history.pushState call. The MutationObserver approach in NeuralTab's content.js is the standard solution: watch for significant DOM changes, compare the URL, and reset state accordingly.
