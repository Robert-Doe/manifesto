What Is a Content Script?

In Module 01, NeuralTab existed entirely inside its own popup. It could read tab metadata — URLs, titles — but it could not touch the actual content of any webpage. If you wanted to highlight text on Wikipedia, count words on a news article, or inject a button onto a shopping page, the popup alone is powerless. That is what content scripts solve.

A content script is a JavaScript file that Chrome automatically injects into web pages you visit, based on URL patterns you declare in manifest.json. Once injected, the script can read and modify the page's DOM — create elements, change styles, add event listeners, extract text — exactly as if it were the page's own JavaScript. From the DOM's perspective, content script code is indistinguishable from page code. But from the JavaScript engine's perspective, they are in entirely different worlds.

Think of it this way: the DOM is a shared whiteboard. Both the page's JavaScript and your content script can draw on it, erase from it, and read what's on it. But each party has their own private notepad (the JavaScript heap) that the other cannot see or touch. This is the fundamental mental model for Module 02. Master it now and the rest of content script development becomes predictable.

Content scripts are declared in manifest.json under the content_scripts array. Each entry specifies which URLs to inject into (the matches pattern), which files to inject (js and css arrays), and when to inject relative to the page lifecycle (run_at). Chrome handles all the injection mechanics — you never call an "inject" function yourself from a content script perspective. The script simply starts running when the matching page loads.

Tip — Content Scripts Are Cheap
A common misconception is that injecting a content script into every page is expensive. It is not. Chrome injects the script's bytes once per matching page load. If the script is small and fast to execute, the overhead is negligible. NeuralTab's content.js adds roughly 2ms to page load time on a modern machine. The cost only becomes significant if your script does heavy synchronous work on startup — which is why NeuralTab defers all DOM operations until after document_idle.

Isolated Worlds — The Most Important Concept in This Module

Understanding isolated worlds is not optional. Every confusing content script bug you will ever encounter — "why can't I read that variable?", "why did my prototype modification not affect the page?", "why does the page not see my global function?" — has isolated worlds as its root cause. Let's understand it precisely.

Chrome's JavaScript engine (V8) organises execution using two primitives: an Isolate (a completely independent JavaScript VM with its own heap) and a Context (a sandboxed environment within an Isolate that has its own global object). A tab gets one Isolate. Inside that Isolate, Chrome creates multiple Contexts — one for the page (the main world, world 0), one for each content script that injects (each gets its own isolated world, starting at world 1). Each Context has its own global window object, its own prototype chain for built-in types, and its own variable bindings.

The DOM is not a JavaScript object — it is a C++ object tree maintained by Chrome's Blink rendering engine. Both the main world and isolated worlds hold JavaScript wrappers around the same underlying C++ DOM nodes. When your content script reads document.title, it gets a JS wrapper that calls into Blink to retrieve the title. When the page reads document.title, it gets a different JS wrapper that calls the same Blink getter. Same underlying data. Different wrapper objects in different heaps. That is why both can see the same DOM but neither can see the other's variables.

What Each World Can and Cannot Do

World 0 — Main World — inject.js runs here
✓ Read page JS variables: window.React, window.__NEXT_DATA__, window.myVar
✓ Access the DOM — read and write nodes, attributes, styles
✓ Run synchronously with page JavaScript — can intercept function calls
✗ Access chrome.* APIs — chrome.runtime, chrome.storage are all undefined
✗ Access content script variables — the other world's heap is invisible
✗ Receive messages from chrome.runtime.sendMessage directly
World 1 — Isolated World — content.js runs here
✓ Access chrome.* APIs — full chrome.runtime, chrome.storage, chrome.tabs
✓ Access the DOM — same nodes as world 0, different JS wrappers
✓ Receive messages via chrome.runtime.onMessage
✗ Read page JS variables — window.React, window.__data__ are undefined
✗ Affect the page's prototype chain — modifications stay in world 1
✗ Access variables set by page scripts in world 0
Key Insight — Prototype Pollution Cannot Cross Worlds
This is V8's security guarantee. If a malicious page runs Object.prototype.toString = () => 'hacked', your content script's Object.prototype.toString is unaffected — it still works correctly because it references a different prototype object in a different Context. This is why you can trust your content script to behave correctly on any page, no matter how aggressively that page modifies its own JavaScript environment.

Crossing the World Boundary

There are exactly two ways to move data between world 0 and world 1:

MethodDirectionHow it worksLimitation
window.postMessage() Either direction The window object is shared between worlds (as a DOM concept, not a JS object). Events fired on it propagate to both worlds' event listeners. Anyone on the page can listen — tag your messages with a source field to filter them.
DOM data attributes Either direction Set element.dataset.myValue = 'x' in world 0 — world 1 can read it via the same DOM node, because both worlds wrap the same C++ element. Page JavaScript can read your data attributes — do not store secrets here.
Custom DOM events Either direction dispatchEvent(new CustomEvent('nt-ready', { detail: data })) on a DOM element — both worlds' listeners receive it. Same visibility issue as postMessage — page scripts can intercept.

NeuralTab uses window.postMessage for world-0 → world-1 communication. inject.js (world 0) sends a message with source: 'neuraltab-inject'. content.js (world 1) listens and filters by that source field, ignoring all other messages on the window.

Web Accessible Resources — Sharing Extension Files With Pages

By default, every file inside your extension package is completely hidden from the web. If a content script tries to load a font file using a relative path like ./assets/fonts/inter.woff2, it will get a 404 — the page's origin (https://example.com) cannot resolve extension-internal paths.

Web Accessible Resources (WAR) is the solution. It is a manifest.json key that explicitly whitelists specific files for access by specific URL patterns. Chrome generates a unique URL for each listed resource in the format:

Generated URL formattext
chrome-extension://[your-extension-id]/[resource-path]

Example:
chrome-extension://abcdefghijklmnopqrstuvwxyzabcdef/assets/inject.js
chrome-extension://abcdefghijklmnopqrstuvwxyzabcdef/assets/fonts/inter-regular.woff2

Your content script generates this URL by calling chrome.runtime.getURL('assets/inject.js'). This function returns the full chrome-extension:// URL for the current extension. The page can then load that URL as a normal web resource — Chrome intercepts the request and serves the file from the extension package.

manifest.json — web_accessible_resourcesJSON
"web_accessible_resources": [
  {
    // Which files to expose to the web
    "resources": [
      "assets/inject.js",
      "assets/fonts/inter-regular.woff2",
      "assets/fonts/inter-bold.woff2"
    ],

    // Which pages are allowed to load these resources.
    // "<all_urls>" means any page can load them.
    // You can narrow this to specific domains for security:
    // e.g., ["https://example.com/*"] restricts to one site.
    "matches": ["<all_urls>"]
  }
]
Warning — WAR Enables Extension Fingerprinting
Every file listed in web_accessible_resources is accessible by any page on the internet at its chrome-extension:// URL. A page can probe for the existence of your extension by trying to load one of these files and checking whether it gets a response or a 404. If it loads, the extension is installed. This is Extension Fingerprinting — we cover detection and countermeasures in depth in Module 11. For now, understand that WAR is a necessary tradeoff: we need inject.js to be web-accessible so it can run in world 0, but this makes our extension detectable by any site that probes for it.

Injecting Fonts Into Web Pages

The same mechanism works for fonts. If you want NeuralTab's injected UI to use a specific font that is guaranteed to look correct regardless of what the host page does, you ship the font inside the extension package, list it in WAR, and load it from content.js using a @font-face rule pointing to the chrome-extension:// URL. Shadow DOM's style isolation ensures the font applies only inside your panel, not to the rest of the page.

content.js — loading an extension font into Shadow DOMJavaScript
// chrome.runtime.getURL() converts a relative path to the full
// chrome-extension:// URL for this extension's package.
const fontUrl = chrome.runtime.getURL('assets/fonts/inter-regular.woff2');

const style = document.createElement('style');
style.textContent = `
  @font-face {
    font-family: 'Inter';
    src: url('${fontUrl}') format('woff2');
    font-weight: 400;
    font-display: swap;
  }
`;

// Inject into the Shadow Root — font loads from extension package,
// applies only inside the shadow tree. Zero impact on the host page.
shadowRoot.appendChild(style);

Code Walkthrough — Every New File Explained

manifest.json — Three New Keys

Module 02 adds three new sections to the manifest. Each one is a declarative instruction that Chrome reads at extension load time — no code needed to trigger the injection itself.

manifest.json — new additions highlightedJSON
{
  "manifest_version": 3,
  "name": "NeuralTab",
  "version": "0.2.0",     // ← bumped from 0.1.0

  // ... action and icons same as Module 01 ...

  // ── NEW ─────────────────────────────────────────────────────
  // Chrome reads this array and automatically injects the listed
  // files into every page whose URL matches the pattern.
  // No JavaScript call is needed — this is purely declarative.
  "content_scripts": [
    {
      // "<all_urls>" matches every http://, https://, ftp://, file:// URL.
      // Chrome automatically excludes chrome://, chrome-extension://,
      // and the Chrome Web Store regardless of this pattern.
      "matches": ["<all_urls>"],

      // JS files to inject — loaded in the order listed.
      // Each runs in a separate isolated world (world 1).
      "js": ["content.js"],

      // CSS to inject into the page's real DOM style scope.
      // Applied BEFORE content.js runs — no FOUC.
      "css": ["content.css"],

      // When to inject relative to page lifecycle:
      // "document_start"  — before any HTML is parsed (DOM not ready)
      // "document_end"    — after HTML parsed, before subresources load
      // "document_idle"   — after DOMContentLoaded AND page is idle ← safest
      "run_at": "document_idle",

      // false = only inject into the TOP-LEVEL frame.
      // true  = also inject into iframes (risky — iframes can be anything).
      // Always start with false.
      "all_frames": false
    }
  ],

  // ── NEW ─────────────────────────────────────────────────────
  // Whitelist specific files for web access.
  // Without this, inject.js cannot be loaded as a <script src> tag.
  "web_accessible_resources": [
    {
      "resources": ["assets/inject.js", "assets/fonts/inter-regular.woff2"],
      "matches": ["<all_urls>"]
    }
  ]
}

content.js — Shadow DOM Injection and DOM Surgery

Let's walk through the four most important functions in content.js, explaining the why behind each decision.

Part 1 — Shadow DOM Host Creation

content.js — injectFloatingButton()JavaScript
injectFloatingButton() {
  // Step 1: Create a host element in the REAL DOM.
  // This element is visible to the page, to DevTools, and to
  // the page's CSS. We give it a unique ID so we can find it
  // again if needed (e.g., to hide it from the popup).
  const host = document.createElement('div');
  host.id = 'neuraltab-host';

  // Step 2: Attach a Shadow DOM to the host.
  // Everything inside this shadow root is INVISIBLE to the page's CSS.
  // mode: 'open' allows JS to reach inside via host.shadowRoot.
  // mode: 'closed' blocks that — use 'closed' in production.
  this.shadowRoot = host.attachShadow({ mode: 'open' });

  // Step 3: Inject styles INTO the shadow root.
  // These styles are completely isolated — they cannot affect
  // anything outside the shadow boundary.
  const style = document.createElement('style');
  style.textContent = this.getButtonStyles();
  this.shadowRoot.appendChild(style);

  // Step 4: Build the button INSIDE the shadow root.
  // It is rendered by the browser but styled only by our shadow CSS.
  this.floatingBtn = document.createElement('button');
  this.floatingBtn.id = 'nt-btn';
  this.floatingBtn.addEventListener('click',
    () => this.onSummarizeClick());
  this.shadowRoot.appendChild(this.floatingBtn);

  // Step 5: Mount the host into the REAL page DOM.
  // This is the single moment we touch document.body.
  // content.css handles the host's real-DOM positioning.
  document.body.appendChild(host);
}

Part 2 — DOM TreeWalker Word Count

content.js — countWords()JavaScript
countWords() {
  // createTreeWalker traverses the DOM tree visiting only the
  // node types specified by the second argument.
  // NodeFilter.SHOW_TEXT = visit only text nodes (no elements).
  // This is faster than recursing the element tree manually.
  const walker = document.createTreeWalker(
    document.body,
    NodeFilter.SHOW_TEXT,
    {
      acceptNode(node) {
        const parent = node.parentElement;
        if (!parent) return NodeFilter.FILTER_REJECT;

        // FILTER_REJECT skips the node AND its subtree.
        // FILTER_SKIP skips only the node, not its children.
        // FILTER_ACCEPT includes the node in results.
        const tag = parent.tagName.toLowerCase();
        if (['script', 'style', 'noscript'].includes(tag))
          return NodeFilter.FILTER_REJECT;

        // Skip our own injected host element — don't count
        // the label text inside our Summarize button.
        if (parent.closest('#neuraltab-host'))
          return NodeFilter.FILTER_REJECT;

        return NodeFilter.FILTER_ACCEPT;
      }
    }
  );

  let count = 0;
  let node;
  // walker.nextNode() returns the next matching text node
  // or null when the traversal is complete.
  while ((node = walker.nextNode())) {
    // Split on whitespace and filter empty strings from
    // leading/trailing spaces.
    const words = node.textContent
      .trim()
      .split(/\s+/)
      .filter(w => w.length > 0);
    count += words.length;
  }
  return count;
}

Part 3 — SPA Navigation Detection

content.js — watchForSPANavigation()JavaScript
watchForSPANavigation() {
  let lastUrl = location.href;

  // MutationObserver fires a callback every time the observed
  // node's subtree changes. We observe document.body because
  // SPA frameworks replace large DOM subtrees on navigation.
  this.observer = new MutationObserver(() => {
    const currentUrl = location.href;

    // The URL changed → this is a route change, not just
    // a DOM update on the same page (e.g., infinite scroll).
    if (currentUrl !== lastUrl) {
      lastUrl = currentUrl;
      this.onSPANavigate();
    }
  });

  this.observer.observe(document.body, {
    childList: true,   // watch for added/removed child elements
    subtree:   true    // apply recursively to all descendants
  });
}

Part 4 — Main World Script Injection

content.js — injectMainWorldScript()JavaScript
injectMainWorldScript() {
  // chrome.runtime.getURL() converts the relative path to the full
  // chrome-extension://[id]/assets/inject.js URL.
  // This URL works because we listed "assets/inject.js" in
  // web_accessible_resources in manifest.json.
  const scriptUrl = chrome.runtime.getURL('assets/inject.js');

  const script = document.createElement('script');
  script.src = scriptUrl;

  // Remove the script tag after it executes — no need to keep
  // it in the DOM. This is cosmetic cleanup only; removing the
  // element does not stop the script from having run.
  script.onload = () => script.remove();

  // Append to documentElement (html), not body.
  // body may not exist yet at document_start.
  // documentElement always exists by the time content scripts run.
  document.documentElement.appendChild(script);

  // Listen for the postMessage that inject.js sends after running.
  // This crosses the world boundary — world 0 sends, world 1 receives.
  window.addEventListener('message', (event) => {
    // Security: only handle messages from our own window,
    // not from iframes or other origins.
    if (event.source !== window) return;
    if (!event.data?.source === 'neuraltab-inject') return;

    console.log('[NeuralTab] Main world data:', event.data.payload);
  });
}

assets/inject.js — Running in the Page's Main World

This file runs in world 0. It cannot call any chrome.* API. Its only job is to read world-0-only data and report it back to the content script via window.postMessage.

assets/inject.js — key partsJavaScript
// IIFE wraps everything so we do not pollute window with our locals
(function () {
  'use strict';

  const payload = {};

  // These variables ARE accessible here because we are in world 0.
  // The same lines in content.js would return undefined.
  payload.frameworks = [];
  if (window.React)         payload.frameworks.push('React');
  if (window.__NEXT_DATA__)  payload.frameworks.push('Next.js');
  // ... more framework detection ...

  // Send results back to world 1 (content.js).
  // The '*' targetOrigin means the message is delivered regardless
  // of the window's current origin. For a same-page postMessage
  // this is fine. Passing location.origin is more secure if
  // you need to prevent cross-origin relay.
  window.postMessage({
    source:  'neuraltab-inject',  // filter key for content.js listener
    payload: payload
  }, '*');
})();

Debugging the Content Script

The content script runs in its own JavaScript context. To inspect it in DevTools:

  1. Open DevTools on any page where NeuralTab is injected.

  2. In the Console tab, find the context selector dropdown (top-left of the console, usually shows "top"). Click it.

  3. You will see an entry like "NeuralTab (content script)" or the extension's name. Select it.

  4. Now you are in the isolated world context. Type window.NeuralTabContent and press Enter. You should see the NeuralTabContent object. Type window.myPageSecret (defined in the demo page) and see undefined — isolated worlds proven live.

Exercises

Warm-Up Exercise 1 — Prove Isolated Worlds Live in DevTools

This exercise makes isolated worlds tangible rather than theoretical.

  • Open the demo page in Chrome. Open DevTools → Console.
  • In the top (page) context, type: window.myPageSecret. You should see "I am only in world 0".
  • Switch the console context to NeuralTab (content script) using the dropdown.
  • Type the same: window.myPageSecret. You should see undefined.
  • Now type window.__neuraltab_injected__ in the content script context. You should see true.
  • Switch back to the top context and type window.__neuraltab_injected__. You should see undefined.
  • Write a short note explaining in your own words why the same variable name returns different values in each context.
What you just proved: The same window keyword returns a different global object depending on which Context (world) the code runs in. They look the same but they are distinct JavaScript objects in distinct V8 Contexts.
Warm-Up Exercise 2 — Change the run_at and See the Difference

run_at: "document_idle" is the safest injection timing, but understanding the alternatives teaches you the page lifecycle.

  • In manifest.json, change "run_at": "document_idle" to "run_at": "document_start". Reload the extension.
  • Open the demo page. What happens? Does the button appear? Check the console for errors.
  • Try to explain why it fails (hint: document.body does not exist yet at document_start).
  • Change it to "document_end". Does the button appear now? Does it appear at the same time as before?
  • Change it back to "document_idle" when you are done.
Expected result at document_start: TypeError: Cannot read properties of null (reading 'appendChild') — because document.body is null when the HTML has not been parsed yet. This is why we use document_idle for all UI injection.
Core Exercise 3 — Add a "Reading Progress" Bar

Inject a thin progress bar at the very top of any page that fills from 0% to 100% as the user scrolls from the top to the bottom of the article. This must be injected via content.js and must survive across SPA route changes.

  • In content.js, create a new <div> with id="nt-progress-bar" and append it to document.body (not inside the Shadow DOM — the progress bar should be in the real DOM so it inherits the page's scroll context).
  • Style it with inline styles: position: fixed; top: 0; left: 0; height: 3px; width: 0%; background: #f5c842; z-index: 2147483646; transition: width 0.1s;
  • Add a scroll event listener on window that computes: const pct = (window.scrollY / (document.body.scrollHeight - window.innerHeight)) * 100
  • Update the bar's style.width to pct + '%' on every scroll event.
  • In onSPANavigate(), reset the bar width to '0%'.
Stretch: Add a debounce to the scroll listener so it only updates every 50ms instead of on every pixel of scroll. This is a preview of the performance optimisation techniques we cover in Module 20.
Core Exercise 4 — Detect a React App From inject.js and Report to content.js

inject.js already detects window.React. Extend it to also find the root React component's state and pass it to the content script.

  • Open https://reactjs.org or any React-based site in Chrome with NeuralTab loaded.
  • In the browser console (top/main world context), type: document.querySelector('#root').__reactFiber$ followed by Tab to autocomplete — find the React fiber property name (it has a random suffix like __reactFiber$abc123).
  • In assets/inject.js, after detecting React, add code to find the root element's fiber property and extract the type.displayName of the root component.
  • Include this in the payload sent via postMessage.
  • Verify the component name appears in the [NeuralTab] Main world data: console log in your content script context.
Why this matters: This is exactly how React DevTools works. It reads the __reactFiber property from DOM nodes to reconstruct the component tree — a world-0-only operation that requires being in the main world. You just built the foundation of a React inspector.

Options Page, chrome.storage & Permissions UX Psychology

NeuralTab now injects into every page, but it has no memory. Close the browser and reopen it — any preference the user had is gone. The Summarize button is always gold even if the user wanted blue. There's no way to configure the highlight colour, disable injection on certain domains, or remember anything between sessions. Module 03 fixes all of this by introducing options.html — NeuralTab's settings page — backed by chrome.storage.local, the persistent key-value store that survives browser restarts. You will learn the critical distinction between chrome.storage.local (device-only, 10MB), chrome.storage.sync (syncs across devices, 100KB limit), and chrome.storage.session (cleared on browser restart). Alongside storage, we tackle one of the most overlooked skills in extension development: Permissions UX Psychology — the science of why users deny permission requests, the exact moment in the user journey to ask, and how to implement the "warm ask" pattern so that users grant permissions rather than clicking "Block" out of instinct. The new files added in Module 03 are options.html, options.css, options.js, and storage_manager.js.
