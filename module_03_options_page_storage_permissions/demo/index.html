Long article — for word count and highlight testing

The relationship between persistence and ephemerality is central to understanding browser extension architecture. A JavaScript variable declared in a popup script is ephemeral — it lives only as long as the popup is open, typically a few seconds. A value stored in chrome.storage.local is persistent — it survives popup closes, browser restarts, and even Chrome updates. Understanding which category a piece of data falls into is the foundational skill of stateful extension development.

The chrome.storage API is deliberately asynchronous. Every read and write returns either a Promise (in MV3) or accepts a callback (legacy pattern). This asynchronous character reflects the underlying implementation: Chrome serialises your data to disk using SQLite, a transactional database format. The serialisation happens off the main thread to avoid blocking the browser's rendering pipeline. When you call chrome.storage.local.set(), Chrome queues a database write operation and resolves your Promise only after the write is confirmed. This means the data is genuinely durable — not just buffered in memory — by the time your Promise resolves.

The three storage tiers serve different purposes at different scales. Session storage is the fastest because it lives entirely in memory — no disk write occurs. It disappears when the browser closes, making it appropriate for ephemeral state like "the user has already seen the tutorial this session" or "we are currently processing a network request." Local storage persists to disk and survives browser restarts, with a 10MB quota per extension. Sync storage replicates across all Chrome profiles signed in with the same Google account, but at a severe size penalty: only 100KB total, with individual item keys capped at 8KB. Sync is appropriate for settings that should feel consistent across devices, not for data that grows proportionally with usage.

Optional permissions represent one of the most psychologically nuanced aspects of extension development. Research from the Chrome Extensions team consistently shows that users are significantly more likely to grant a permission when they understand exactly what feature it enables and are asked at the moment they try to use that feature, rather than during installation. An install-time permission request feels like a toll booth — you pay before you know what you are getting. A contextual permission request, triggered by the user's own action, feels like a reasonable exchange — you understand the value proposition and you are already committed to the feature. The difference in grant rate can be dramatic, sometimes reaching three times higher for the contextual pattern compared to the upfront pattern.
