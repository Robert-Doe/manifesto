Part 1 — Why chrome.storage and Not localStorage?

Almost every beginner's first instinct is to use localStorage for persistence. It is synchronous, simple, and it works in the browser — so why not? The answer is in how storage is partitioned. The browser partitions localStorage by origin. Your popup and options page run at the origin chrome-extension://[extensionId]/. Your content script is injected into https://example.com/. Even though the content script's JavaScript runs inside your extension's process, it is injected into a page at a different origin — which means if your content script writes to localStorage, it writes to that page's localStorage partition, not your extension's.

The popup cannot read from a page's localStorage without first scripting into that page. The options page cannot either. If you had three browser tabs open with three different websites, each content script would read from a completely different localStorage. There is no shared store. This is fatal for any feature that needs to know a setting regardless of which page it is running on.

chrome.storage is different in a fundamental way: it is extension-scoped. Every context inside your extension — popup, options page, content scripts on any page, background worker, side panel — reads and writes the same key-value database. The origin of the host page is irrelevant. This is the only API that can serve as a shared source of truth across all extension contexts.

popup.html chrome-extension://id/popup.html options.html chrome-extension://id/options.html content.js injected into https://news.ycombinator.com content.js injected into https://github.com background.js service worker ALL of these access the same chrome.storage.local database. localStorage would give each a DIFFERENT partition.

The Three Storage Tiers

chrome.storage has three separate stores, each designed for different use cases. Mixing them up is a common source of subtle bugs.

Store Quota Persists across restart? Syncs across devices? Use for
chrome.storage.local 10 MB Yes No All NeuralTab settings, history, cached data
chrome.storage.sync 100 KB total / 8 KB per item Yes Yes — across all Chrome profiles with same Google account User preferences that should follow them across machines (tiny data only)
chrome.storage.session 10 MB No — cleared when browser closes No Per-session ephemeral state: "user dismissed tutorial", "current request in flight"

NeuralTab uses chrome.storage.local for everything in this module. We introduce chrome.storage.session in Module 07 for caching DOM analysis results so we do not re-process a page if the user clicks Summarize twice. chrome.storage.sync is seductive but dangerous — the 8 KB per-item limit means you cannot store a list of blocked domains there without careful chunking. We cover sync chunking strategies in Module 07 as well.

The Asynchronous Requirement

Every chrome.storage operation is asynchronous. There is no synchronous variant. This is by design: writes are committed to SQLite on disk, which cannot happen on the main thread without freezing the browser's rendering pipeline. The consequence for your code is that you cannot read a setting at the top level of a content script and use it immediately. You must structure your code around async/await: 

// ✗ WRONG — cannot read storage synchronously at top level
const settings = chrome.storage.local.get('highlightColor'); // returns a Promise
highlight(settings); // settings is a Promise object, not the value

// ✓ CORRECT — use async init() and await the result
async function init() {
  const settings = await chrome.storage.local.get({ highlightColor: '#f5c842' });
  highlight(settings.highlightColor); // now this is the actual colour string
}
init();

The get() call in the correct version passes an object as the argument. This object serves double duty as both the list of keys to read AND the default values to use if those keys do not exist in storage yet. This is how Chrome's storage API handles defaults natively — no if (value === undefined) guards needed.

Part 2 — The StorageManager Abstraction

Calling chrome.storage.local.get() and .set() directly throughout your codebase creates a fragile system. The default values are duplicated wherever you read a key. The key strings are scattered across files. There is no single place to see "what settings does this extension have?" StorageManager solves all of this.

The DEFAULTS Object — Your Single Source of Truth

const DEFAULTS = {
  highlightColor:  '#f5c842',   // gold — matches NeuralTab brand
  highlightMinLen: 8,            // highlight words ≥ 8 chars
  buttonVisible:  true,         // show the floating ⚡ button
  buttonPosition: 'bottom-right',
  readingSpeed:   200,           // words per minute
  blockedDomains: [],            // hostnames where NeuralTab is disabled
  theme:          'dark',
  clickCount:     0,
  installDate:    null,
  totalSummaries: 0,
};

Every setting lives here once. The default value is self-documenting. When you add a new setting in a later module, you add it here and every existing read immediately gets the correct default without any migration code. Chrome's storage API merges this object with stored values when you call get(DEFAULTS) — the stored value wins for keys that exist, the default wins for keys that don't.

get() — Reading Settings with Defaults

const StorageManager = {
  DEFAULTS,

  async get(keys = null) {
    if (keys === null) {
      // No argument → return all settings with defaults merged
      return chrome.storage.local.get(DEFAULTS);
    }
    // Specific keys requested — build a partial defaults object
    const subset = {};
    (Array.isArray(keys) ? keys : [keys]).forEach(k => {
      if (k in DEFAULTS) subset[k] = DEFAULTS[k];
    });
    return chrome.storage.local.get(subset);
  },
  // ... set, reset, onChange, etc.
};

Notice that get() with no arguments reads ALL settings in a single chrome.storage.local.get() call. This is deliberately efficient: one storage read on page load fetches everything, and the result is used throughout the session. Making individual storage reads for each setting is wasteful — each call is an async database query.

onChange() — The Pub/Sub Bridge Between Contexts

onChange(callback) {
  chrome.storage.onChanged.addListener((changes, areaName) => {
    if (areaName !== 'local') return; // ignore sync/session changes
    // Chrome gives us: { keyName: { oldValue, newValue } }
    // We flatten to: { keyName: newValue } for simpler consumers
    const newValues = {};
    for (const [key, change] of Object.entries(changes)) {
      newValues[key] = change.newValue;
    }
    callback(newValues, changes);
  });
},

chrome.storage.onChanged is Chrome's built-in reactive pub/sub mechanism for storage. It fires in every extension context simultaneously — the popup, the options page, every content script in every tab — whenever any value changes. The callback receives both the old and the new value, which is essential for knowing what changed so you can apply only the necessary DOM update rather than re-rendering the entire UI.

User changes highlight colour in options.html options.js calls: chrome.storage.local.set({ highlightColor: '#38bdf8' }) Chrome fires chrome.storage.onChanged in ALL contexts simultaneously: ┌──────────────────────────────────────┐ │ popup.js onChange listener │ │ → updates colour picker to #38bdf8 │ └──────────────────────────────────────┘ ┌──────────────────────────────────────┐ │ content.js onChange listener │ │ → re-highlights words in #38bdf8 │ │ (NO page reload required) │ └──────────────────────────────────────┘ ┌──────────────────────────────────────┐ │ options.js onChange listener │ │ → updates the live preview box │ └──────────────────────────────────────┘

This single mechanism replaces what would otherwise require polling, a message-passing protocol between contexts, or page reloads. It is one of the most powerful primitives in the Chrome extension API, and it is drastically underused by beginner extension developers.

Part 3 — Options Page Anatomy

How Chrome Integrates the Options Page

Declaring "options_page": "options.html" in the manifest tells Chrome to integrate your options page into its extensions UI. This gives the user three ways to reach it:

  • 1
    Right-click the toolbar icon → select "Options". Available only if options_page is declared. Missing this declaration is the #1 reason developers wonder "where did the Options menu item go?"
  • 2
    chrome://extensions → Details → Extension options. Always available after installation.
  • 3
    Programmatically from your extension via chrome.runtime.openOptionsPage(). This is what NeuralTab's popup's Settings button calls.

The options page is just an HTML page hosted at chrome-extension://[id]/options.html. It has full access to all extension APIs — the same as popup.html. The key difference is lifecycle: the popup is destroyed every time the user clicks away; the options page persists until the user explicitly closes the tab.

The options_page vs options_ui Choice

// Option A — opens in a new tab (what NeuralTab uses)
{
  "options_page": "options.html"
}

// Option B — embeds inside chrome://extensions (small fixed iframe)
{
  "options_ui": {
    "page": "options.html",
    "open_in_tab": false
  }
}

// Option C — equivalent to options_page but more explicit API
{
  "options_ui": {
    "page": "options.html",
    "open_in_tab": true
  }
}

options_ui with open_in_tab: false was introduced to reduce context-switching for simple extensions. The tradeoff is a fixed viewport of roughly 640×480px inside the Extensions panel — no sidebar navigation, no charts, no room for permission cards. NeuralTab's options page is too rich for that constraint, so we use options_page for full-page layout.

Autosave — The Correct Pattern for Settings Pages

NeuralTab's options page has no Save button. Every setting is saved the instant the user interacts with its control. This is not laziness — it is the correct UX pattern for a settings page backed by an async, durable store. 

// Colour picker — save immediately on every colour change
document.getElementById('highlight-color').addEventListener('input', async (e) => {
  await StorageManager.set({ highlightColor: e.target.value });
  updatePreview(e.target.value);
  // chrome.storage.onChanged fires in content script → highlights update live
});

// Textarea — debounce to avoid saving on every keystroke
let debounceTimer;
document.getElementById('blocked-domains').addEventListener('input', (e) => {
  clearTimeout(debounceTimer);
  debounceTimer = setTimeout(async () => {
    const domains = e.target.value
      .split('\n')
      .map(d => d.trim().toLowerCase())
      .filter(Boolean);
    await StorageManager.set({ blockedDomains: domains });
  }, 400); // 400ms debounce — user likely still typing
});

Note the debounce on the textarea. A colour picker emits an input event roughly once every 16ms while the user drags the slider — roughly 60 events per second. Each event triggers a storage write, and each write triggers onChanged in the content script, which re-highlights all words on the page. This is actually fine for the colour picker because the write is cheap and the visual feedback is valuable. But for a textarea where the user types a domain name character by character, saving on every keystroke wastes writes and makes the content script update unnecessarily. The 400ms debounce waits for a natural pause in typing before committing.

Part 4 — Permissions UX Psychology

The Chrome permission model divides permissions into two categories: required (declared in "permissions" in the manifest, shown at install time) and optional (declared in "optional_permissions", requested at runtime). The distinction seems technical, but its implications for user acquisition are profound.

Why Upfront Permission Requests Fail

When a user installs an extension, they see a modal dialog listing every required permission. Chrome's phrasing is deliberately alarming: "Read your browsing history", "Read and change all your data on all websites." Users encounter this dialog at the moment of lowest trust — they just found the extension and have not yet experienced any of its value. Cognitive research on permission dialogs consistently shows that users' primary heuristic when faced with a scary-sounding permission is not "do I trust this extension?" but rather "does the permission sound like it matches what this extension should need?" An ad blocker asking to read all URLs makes sense. A colour-picker extension asking for the same permission is alarming. Extensions that declare too many required permissions at install time see significantly lower install completion rates.

The Optional Permission Pattern

// manifest.json — declare as optional, NOT required
{
  "optional_permissions": ["tabs", "bookmarks", "history"]
}

// options.js — check current status
async function checkPermission(name) {
  return chrome.permissions.contains({ permissions: [name] });
}

// options.js — request ONLY from a user gesture (button click)
grantBtn.addEventListener('click', async () => {
  // chrome.permissions.request() REQUIRES a user gesture — calling it
  // programmatically from a timeout or promise chain will throw silently
  const granted = await chrome.permissions.request({ permissions: ['tabs'] });
  updatePermissionUI('tabs', granted);
});

// options.js — revoke (can be called without a user gesture)
revokeBtn.addEventListener('click', async () => {
  await chrome.permissions.remove({ permissions: ['tabs'] });
  updatePermissionUI('tabs', false);
});
Critical Constraint

chrome.permissions.request() must be called from a user gesture — a direct event handler for a click, keypress, or similar interaction. If you call it from a Promise chain, a setTimeout, or any code path that is not directly triggered by the user's action, Chrome silently refuses the request and returns false without showing any dialog. This is a security measure that prevents extensions from trigger-harvesting permissions without the user's active participation. The "warm ask" pattern works precisely because the Grant button's click handler is a user gesture.

The Three-Step Warm Ask

The warm ask pattern has three steps that must happen in order:

  • 1
    Show the value first. Before the permission card shows a Grant button, it shows a description of exactly what feature the permission enables. "This lets NeuralTab see which tabs you have open so it can build a tab dashboard." The user understands the exchange before being asked to make it.
  • 2
    Require deliberate intent. The Grant button is not shown until the user navigates to the Permissions section of settings — they actively sought out this page. An automatically shown modal would be premature.
  • 3
    Degrade gracefully on denial. If the user clicks Grant and then denies the Chrome dialog, or clicks Revoke later, the feature that uses that permission must fall back cleanly. It must not throw errors or show broken UI.

The content.js onChange Handler

onSettingsChange(changes) {
  if (changes.highlightColor !== undefined) {
    settings.highlightColor = changes.highlightColor;
    // Only re-highlight if the summary panel is currently visible
    if (document.querySelector('#neuraltab-host')?.shadowRoot
                 ?.querySelector('#summary-panel')?.style.display !== 'none') {
      clearHighlights();
      highlightLongWords();
    }
  }
  if (changes.highlightMinLen !== undefined) {
    settings.highlightMinLen = changes.highlightMinLen;
  }
  if (changes.buttonVisible !== undefined) {
    settings.buttonVisible = changes.buttonVisible;
    const host = document.getElementById('neuraltab-host');
    if (host) host.style.display = changes.buttonVisible ? '' : 'none';
  }
  if (changes.buttonPosition !== undefined) {
    settings.buttonPosition = changes.buttonPosition;
    applyButtonPosition(changes.buttonPosition);
  }
},

The guard checking whether the summary panel is visible before re-highlighting is an important performance consideration. If the user is rapidly dragging the colour picker slider, onChanged fires at ~60 events/second. Running the TreeWalker word highlighter 60 times per second on a large article would cause noticeable jank. The guard ensures we only re-highlight when the panel is visible and the user can actually see the result. We add full highlight debouncing in Module 20's performance optimization pass.

Part 6 — Annotated Code: storage_manager.js

Let's read through the full StorageManager carefully, paying attention to every design choice. The full file is ~80 lines. Study it until you understand why each line exists. 

// storage_manager.js — NeuralTab Module 03
// Loaded by: content scripts (via manifest), popup.html, options.html

// ① DEFAULTS is the schema of our storage.
//   Adding a new setting here is the ONLY place you need to touch.
//   chrome.storage.local.get(DEFAULTS) returns the default for any key
//   that hasn't been explicitly set yet — zero migration code needed.
const DEFAULTS = {
  highlightColor:  '#f5c842',
  highlightMinLen: 8,
  buttonVisible:  true,
  buttonPosition: 'bottom-right',
  readingSpeed:   200,
  blockedDomains: [],
  theme:          'dark',
  clickCount:     0,
  installDate:    null,
  totalSummaries: 0,
};

const StorageManager = {
  DEFAULTS,

  // ② get(null) → all settings with defaults merged
  //   get(['a','b']) → just those keys with their defaults
  //   get('a')       → single key with its default
  async get(keys = null) {
    if (keys === null) return chrome.storage.local.get(DEFAULTS);
    const subset = {};
    (Array.isArray(keys) ? keys : [keys]).forEach(k => {
      if (k in DEFAULTS) subset[k] = DEFAULTS[k];
    });
    return chrome.storage.local.get(subset);
  },

  // ③ set() wraps chrome.storage.local.set().
  //   Returns a Promise so callers can await it.
  //   After the Promise resolves, the write IS durable.
  async set(data) {
    return chrome.storage.local.set(data);
  },

  // ④ reset() restores defaults for either specific keys or ALL keys.
  //   Useful for the "Reset to defaults" button in the Storage section.
  async reset(keys = null) {
    if (keys === null) return chrome.storage.local.set(DEFAULTS);
    const subset = {};
    (Array.isArray(keys) ? keys : [keys]).forEach(k => {
      if (k in DEFAULTS) subset[k] = DEFAULTS[k];
    });
    return chrome.storage.local.set(subset);
  },

  // ⑤ getQuota() — returns { used, total, pct } for the UI quota bar.
  //   getBytesInUse(null) measures ALL keys, not just NeuralTab's.
  //   In practice this is fine since NeuralTab owns this storage area.
  async getQuota() {
    const used = await chrome.storage.local.getBytesInUse(null);
    const total = chrome.storage.local.QUOTA_BYTES; // 10,485,760 (10 MB)
    return { used, total, pct: Math.round((used / total) * 100) };
  },

  // ⑥ onChange() wraps chrome.storage.onChanged.addListener.
  //   Filters to 'local' only — we don't want sync/session events.
  //   Flattens { key: { oldValue, newValue } } → { key: newValue }
  //   because most callers only need the new value.
  onChange(callback) {
    chrome.storage.onChanged.addListener((changes, areaName) => {
      if (areaName !== 'local') return;
      const newValues = {};
      for (const [key, change] of Object.entries(changes)) {
        newValues[key] = change.newValue;
      }
      callback(newValues, changes); // raw changes available if needed
    });
  },

  // ⑦ isBlocked() checks if a hostname is in the blocked list.
  //   Content script calls this before injecting the UI.
  async isBlocked(hostname) {
    const { blockedDomains } = await this.get(['blockedDomains']);
    return blockedDomains.some(d => hostname.endsWith(d));
  },

  // ⑧ recordSummary() increments the lifetime summary counter.
  //   Uses a read-then-write pattern. Not atomic — if two contexts
  //   call this simultaneously, one increment could be lost.
  //   We address atomic counters with IndexedDB in Module 07.
  async recordSummary() {
    const { totalSummaries } = await this.get(['totalSummaries']);
    return this.set({ totalSummaries: totalSummaries + 1 });
  },

  _formatBytes(bytes) {
    if (bytes < 1024) return bytes + ' B';
    if (bytes < 1048576) return (bytes / 1024).toFixed(1) + ' KB';
    return (bytes / 1048576).toFixed(2) + ' MB';
  },
};

Luminance Check for Preview Text Colour

function isLightColor(hex) {
  // Parse hex to RGB, compute perceived luminance (ITU-R BT.709)
  // Values above 0.5 are "light" — use dark text on them
  const r = parseInt(hex.slice(1,3), 16) / 255;
  const g = parseInt(hex.slice(3,5), 16) / 255;
  const b = parseInt(hex.slice(5,7), 16) / 255;
  const luminance = 0.2126 * r + 0.7152 * g + 0.0722 * b;
  return luminance > 0.5;
}

function updatePreview(color) {
  const preview = document.getElementById('color-preview');
  preview.style.background = color;
  // Ensure preview text remains readable regardless of chosen colour
  preview.style.color = isLightColor(color) ? '#000' : '#fff';
  preview.textContent = color;
}

The luminance formula here is the ITU-R BT.709 weighted average, which reflects how humans perceive brightness differently in each colour channel: green contributes ~72% of perceived brightness, red ~21%, and blue only ~7%. Without weighting, a colour like #0000ff (pure blue) would appear "bright" despite being quite dark visually. With weighting, the formula correctly identifies it as dark and uses white text over it.

Storage Export

document.getElementById('btn-export').addEventListener('click', async () => {
  const data = await StorageManager.get();
  const json = JSON.stringify(data, null, 2);
  const blob = new Blob([json], { type: 'application/json' });
  const url  = URL.createObjectURL(blob);
  const a    = document.createElement('a');
  a.href     = url;
  a.download = `neuraltab-settings-${new Date().toISOString().slice(0,10)}.json`;
  a.click();
  URL.revokeObjectURL(url); // release memory — blob URL is no longer needed
});

URL.createObjectURL() creates a temporary blob: URL pointing to the in-memory Blob. The browser treats it like a file download when assigned to an anchor element's href with a download attribute. Calling URL.revokeObjectURL() immediately after the click is important: the object URL holds a reference to the Blob in memory. Without revoking, the Blob remains in memory until the page is closed. For a small JSON file this is trivial, but in Module 07 when we export full reading histories (potentially megabytes of data), the revoke call becomes essential for memory hygiene.

Part 9 — Common Mistakes and How to Avoid Them

MistakeSymptomFix
Calling chrome.permissions.request() outside a user gesture Dialog never appears; function returns false silently Ensure the call is in a direct click event handler, not in a Promise chain or setTimeout
Declaring "tabs" in "permissions" instead of "optional_permissions" Chrome adds it to the install-time permission dialog, reducing install conversion Move sensitive permissions to "optional_permissions" and use the warm-ask pattern
Using localStorage in a content script to communicate with the popup Popup reads undefined; localStorage partitioned by page origin, not extension Use chrome.storage.local for all cross-context state
Adding the onChange listener inside a function that runs multiple times Multiple duplicate listener calls; settings change triggers the handler N times Add StorageManager.onChange() once, at module initialization, not inside event handlers
Not listing storage_manager.js before content.js in manifest content_scripts Content script throws StorageManager is not defined Scripts in the js array execute in order — shared utilities must come first
Forgetting "storage" in "permissions" chrome.storage is undefined or throws; extension silently fails Add "storage" to "permissions" in manifest.json

Part 10 — Exercises

Warm-Up Exercise 1

Storage inspector. Open DevTools on the NeuralTab options page (right-click → Inspect). In the Console, type:

chrome.storage.local.get(null, console.log)

You should see all NeuralTab storage keys and their current values. Now type:

chrome.storage.local.set({ totalSummaries: 42 })

Without reloading anything, open the popup. The "Summaries total" counter should display 42 immediately. This confirms chrome.storage.onChanged fired in the popup context and the onChange listener updated the UI.

What you learn: You can use DevTools Console to directly manipulate extension storage during development. This is invaluable for testing edge cases without needing to click through the UI 42 times.

Core Exercise 2

Add a "font size" setting. Add a new setting summaryFontSize with a default value of 14 (pixels) to StorageManager.DEFAULTS. Add a range input to the Appearance section of options.html (range: 11–20, step: 1). Wire it up in options.js with autosave. Then update content.js's getButtonStyles() function to apply the font size to the summary panel's text. Finally, add it to the onSettingsChange() handler so changing the slider in the options page updates the open summary panel in real time.

Files to modify: storage_manager.js, options.html, options.css, options.js, content.js

What you learn: The full lifecycle of adding a new setting — from DEFAULTS through storage through options UI through live content script reaction.

Core Exercise 3

Reset with undo toast. The current Reset button immediately writes all defaults to storage. This is destructive — the user loses their custom colour, blocked domains, etc. with no way to recover. Implement the "toast with undo" pattern: (1) When Reset is clicked, snapshot the current settings into a local variable. (2) Write defaults to storage. (3) Show a notification bar at the top of the options page: "Settings reset. Undo" with a 5-second countdown. (4) If the user clicks Undo within 5 seconds, write the snapshot back to storage. (5) After 5 seconds, remove the notification bar.

What you learn: The snapshot-undo pattern for destructive settings operations. This pattern appears in Gmail, Notion, Linear, and virtually every production settings page.

Stretch Exercise 4

Settings import. Build the inverse of the Export button: an Import button that accepts a JSON file (via a hidden <input type="file"> click), reads it with the FileReader API, validates that it contains only known keys (keys present in StorageManager.DEFAULTS), rejects invalid keys with a visible error message, and writes valid keys to storage. After import, reload all form controls using loadSettings().

Bonus: Add a version field to the export JSON ("_version": 3) and handle the case where a user imports a settings file from an older version of NeuralTab that is missing keys introduced in later modules.

What you learn: File input handling, FileReader API, input validation as a security boundary (never trust imported data), forward-compatibility design.

Stretch Exercise 5

Per-domain settings. The current blocked-domains list completely disables NeuralTab on blocked hostnames. Build a richer per-domain override system: store a domainOverrides object in storage where each key is a hostname and each value is a partial settings object (e.g., { "github.com": { "highlightMinLen": 12 } }). In content.js's init(), after loading global settings, check whether location.hostname has an entry in domainOverrides and merge those values over the global settings. Add a simple UI to the options page where the user can add domain-specific overrides.

What you learn: Hierarchical settings — global defaults, user preferences, per-site overrides — which is the architecture used by Grammarly, uBlock Origin, and every major extension with per-site behaviour.

What's Next — Module 04: Tab API, Bookmarks & Browser API Survey

Module 03 wired up the optional "tabs" permission with a Grant button — but never actually used it. In Module 04, we use it. The chrome.tabs API unlocks a completely different level of extension capability: NeuralTab gains a tab manager that can see all open tabs, group them by domain, detect which tabs have been idle for more than 30 minutes, and move or close them programmatically.

Module 04 also surveys the full browser API surface — chrome.bookmarks for reading and writing the bookmark tree, chrome.history for querying the browser's visit history, chrome.alarms for scheduling periodic tasks that survive service worker restarts, and chrome.notifications for desktop-level toast notifications. Each API gets a feature added to NeuralTab and a warm-ask permission card added to the options page.

Key concepts you will learn in Module 04: The difference between chrome.tabs.query() with and without the "tabs" permission (URLs are redacted to empty strings without it). The chrome.tabs.onUpdated and chrome.tabs.onRemoved events. The structure of the bookmark tree (folders vs leaves, the special "Other Bookmarks" node ID). How chrome.alarms schedules persistent periodic work even after the service worker has been killed by the 5-minute idle timer. How to compose multiple APIs into a feature (e.g., use history to find articles read in the last week and bookmark the ones that were visited for more than 2 minutes).

By the end of Module 04, you will understand why extension developers describe the Chrome API surface as "the web with superpowers" — and why getting a user to grant the right permissions, using the warm-ask pattern you learned here, is the critical unlock to building truly powerful experiences.
