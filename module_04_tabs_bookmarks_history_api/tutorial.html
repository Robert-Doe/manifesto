Part 1 — The Background Service Worker

Every non-trivial Chrome extension needs a background context — a JavaScript environment that runs independently of any open tab or popup, capable of responding to browser events (a tab closing, an alarm firing, a download completing) even when the user has not interacted with the extension in hours.

In Manifest V2, this was a persistent background page: an invisible HTML page that ran continuously, kept alive for the entire browser session. It was powerful but expensive — every extension with a persistent background page consumed memory and CPU even when completely idle. In Manifest V3, persistent background pages are removed entirely. The replacement is a service worker — the same technology that powers Progressive Web App offline caching, adapted for the extension context.

The Service Worker Lifecycle

A service worker is not always running. It has a lifecycle driven entirely by events:

Extension installed / updated → chrome.runtime.onInstalled fires → Service worker runs handlers → Worker goes idle → Chrome terminates worker (~5 min idle timeout) Alarm fires at scheduled time → Chrome WAKES the service worker process → chrome.alarms.onAlarm fires → Service worker runs handler → Worker goes idle again → Chrome terminates User clicks extension icon → Chrome WAKES service worker if dead → Worker runs message handlers, popup connects → Popup closes → Worker can idle out again Browser closes → Service worker is terminated (no onDestroy callback) → All JS variables are lost → chrome.storage data persists (it's on disk, not in the worker)
Critical — The 5-Minute Trap

If you store state in a module-level JavaScript variable in background.js, that state is lost when the service worker is terminated. This is the single most common source of confusing MV3 bugs. The only durable storage available to background code is chrome.storage. Any state that must survive the idle timeout must be written to storage before the worker dies — which is why NeuralTab writes lastTabAnalysis to storage after every alarm, not to a variable.

Declaring a Service Worker in the Manifest

{
  "background": {
    "service_worker": "background.js"
    // Optional: "type": "module" enables ES import syntax
    // Without it, classic mode — use importScripts() to load shared files
  }
}

The service worker is a single file. It cannot use <script src> tags or DOM APIs. It has access to the full chrome.* namespace, the Fetch API, IndexedDB, and the Web Crypto API. It does not have access to document, window, localStorage, or any DOM method.

onInstalled — The Right Place to Set Up Alarms

chrome.runtime.onInstalled.addListener(async ({ reason }) => {
  if (reason === 'install') {
    // First install only — record the install date
    const existing = await chrome.storage.local.get({ installDate: null });
    if (!existing.installDate) {
      await chrome.storage.local.set({ installDate: Date.now() });
    }
    // Create the recurring alarm — persists across service worker restarts
    await chrome.alarms.create('tab-analysis', { periodInMinutes: 30 });
  }
  if (reason === 'update') {
    // On extension update, Chrome may have cleared alarms — recreate if missing
    const existing = await chrome.alarms.get('tab-analysis');
    if (!existing) {
      await chrome.alarms.create('tab-analysis', { periodInMinutes: 30 });
    }
  }
});

onInstalled fires in exactly three situations: first install (reason === 'install'), extension update (reason === 'update'), and Chrome update (reason === 'chrome_update'). It is the correct and canonical place to create alarms, because chrome.alarms.create() creates a persistent alarm record in Chrome's alarm scheduler — independent of the service worker. Once created, the alarm survives service worker terminations, browser restarts, and even extension updates (though we guard for the update case because Chrome may clear alarms during an update).

Part 2 — chrome.alarms: Scheduling Work That Survives Everything

The alarm system is Chrome's equivalent of cron — a mechanism for scheduling future work that operates independently of the JavaScript runtime. Understanding it deeply is what separates extensions that work reliably from extensions that silently stop working after an hour.

Creating Alarms

// One-shot alarm: fires once, 5 minutes from now
chrome.alarms.create('check-update', { delayInMinutes: 5 });

// Recurring alarm: fires every 30 minutes, starting immediately
chrome.alarms.create('tab-analysis', { periodInMinutes: 30 });

// Recurring alarm with an initial delay: fires after 2 min, then every 30 min
chrome.alarms.create('tab-analysis', {
  delayInMinutes:  2,
  periodInMinutes: 30,
});

// Alarm at an absolute time (Unix timestamp in milliseconds)
chrome.alarms.create('midnight-sync', {
  when: new Date().setHours(24, 0, 0, 0), // next midnight
});

Listening and Responding

chrome.alarms.onAlarm.addListener(async (alarm) => {
  // alarm.name — the string name you gave it on create()
  // alarm.scheduledTime — when it was supposed to fire (ms epoch)
  // alarm.periodInMinutes — for recurring alarms, the period

  if (alarm.name === 'tab-analysis') {
    await runTabAnalysis();
  }
  if (alarm.name === 'midnight-sync') {
    await syncHistory();
  }
});

Inspecting and Clearing Alarms

// Get a specific alarm
const alarm = await chrome.alarms.get('tab-analysis');
console.log(alarm); // { name, scheduledTime, periodInMinutes }

// Get all alarms
const allAlarms = await chrome.alarms.getAll();

// Clear a specific alarm
await chrome.alarms.clear('tab-analysis');

// Clear all alarms
await chrome.alarms.clearAll();
Alarm Firing Accuracy

Chrome does not guarantee exact alarm timing. If the computer is asleep, the alarm fires when the computer wakes. If Chrome is throttled (e.g., the laptop is on battery saver mode), alarms may be delayed by up to a few minutes. The minimum alarm period is 30 seconds in newer Chrome versions (raised from 1 minute in Chrome 120). Your alarm handlers must be idempotent — running them twice must produce the same result as running them once — because Chrome may fire an alarm that already fired but was not acknowledged.

Part 3 — chrome.tabs: The Full Tab Control Surface

The tabs API is the most commonly used API in the Chrome extension ecosystem, and also the most frequently misunderstood. There are three distinct capability levels depending on which permissions are granted.

Permission level What you can read from Tab objects What you can do
No permission (base) id, windowId, index, active, audible, pinned, status, incognito, width, height — but url and title are empty strings Count tabs, close tabs by ID, move tabs, duplicate tabs, group tabs
"tabs" optional permission granted Everything above PLUS url, title, pendingUrl, favIconUrl Everything above PLUS read the URL/title of every tab
"activeTab" permission (required) Grants url + title for the current active tab ONLY, without showing a prompt at install time. Permission is automatically revoked when the user switches away from the tab. Access the active tab's URL/title without triggering the scary install-time warning. Used for the popup's "Active Tab" display.

Querying Tabs

// The active tab in the current window — works without "tabs" permission
// (activeTab covers this specific query)
const [tab] = await chrome.tabs.query({ active: true, currentWindow: true });

// All tabs — url/title are "" without "tabs" permission
const allTabs = await chrome.tabs.query({});

// Tabs in a specific window
const windowTabs = await chrome.tabs.query({ windowId: windowId });

// Pinned tabs only
const pinned = await chrome.tabs.query({ pinned: true });

// Tabs playing audio
const audible = await chrome.tabs.query({ audible: true });

// Tabs matching a specific URL pattern (requires "tabs" permission)
const githubTabs = await chrome.tabs.query({ url: '*://github.com/*' });

Modifying and Creating Tabs

// Make a tab active and bring its window to the foreground
await chrome.tabs.update(tabId, { active: true });
await chrome.windows.update(windowId, { focused: true });

// Close one or more tabs
await chrome.tabs.remove(tabId);          // single tab
await chrome.tabs.remove([id1, id2, id3]); // multiple tabs in one call

// Open a new tab
await chrome.tabs.create({ url: 'https://example.com', active: true });

// Open an extension page in a new tab
await chrome.tabs.create({ url: chrome.runtime.getURL('tab_manager.html') });

// Move a tab to a different position in the same window
await chrome.tabs.move(tabId, { index: 0 }); // move to front

// Duplicate a tab
const newTab = await chrome.tabs.duplicate(tabId);

Tab Groups API (Chrome 89+)

// Group multiple tab IDs together — returns the new group ID
const groupId = await chrome.tabs.group({ tabIds: [id1, id2, id3] });

// Customise the group (requires no extra permission)
await chrome.tabGroups.update(groupId, {
  title:     'github.com',
  color:     'blue',   // 'grey'|'blue'|'red'|'yellow'|'green'|'pink'|'purple'|'cyan'|'orange'
  collapsed: false,
});

// Ungroup tabs
await chrome.tabs.ungroup([id1, id2]);

Tab Event Listeners

// Fired when any tab's status, url, or title changes
chrome.tabs.onUpdated.addListener((tabId, changeInfo, tab) => {
  // changeInfo only contains the CHANGED properties, not all tab properties
  if (changeInfo.status === 'complete') {
    console.log(`Tab ${tabId} finished loading: ${tab.url}`);
  }
  if (changeInfo.url) {
    // Tab navigated to a new URL
  }
});

// Fired when the user switches active tab
chrome.tabs.onActivated.addListener(({ tabId, windowId }) => {
  console.log(`User switched to tab ${tabId} in window ${windowId}`);
  // This is where you'd track "last accessed" timestamps (Module 05)
});

// Fired when a tab is closed
chrome.tabs.onRemoved.addListener((tabId, { windowId, isWindowClosing }) => {
  console.log(`Tab ${tabId} closed. Window closing: ${isWindowClosing}`);
});

// Fired when a new tab is created
chrome.tabs.onCreated.addListener((tab) => {
  console.log(`New tab created: ${tab.id}`);
});

Part 4 — chrome.bookmarks: The Full Bookmark Tree

The bookmarks API exposes Chrome's entire bookmark database as a tree structure. Understanding the tree layout is essential before writing any bookmark code.

Root (id: "0") ├── Bookmarks bar (id: "1") ← chrome.bookmarks.BOOKMARK_BAR_ID │ ├── BookmarkTreeNode { title: "GitHub", url: "https://github.com" } │ └── BookmarkTreeNode { title: "Work", children: [...] } ← this is a folder │ ├── Other Bookmarks (id: "2") ← chrome.bookmarks.OTHER_BOOKMARKS_ID │ └── NeuralTab Saves/ │ ├── { title: "Article I saved", url: "..." } │ └── { title: "Another article", url: "..." } │ └── Mobile Bookmarks (id: "3") ← synced from Chrome on Android/iOS └── { title: "Some mobile page", url: "..." } BookmarkTreeNode fields: id — string (unique, assigned by Chrome) parentId — string (id of the parent folder) title — string url — string | undefined (undefined for folders) children — BookmarkTreeNode[] | undefined (undefined for bookmarks) dateAdded — number (epoch ms) index — number (position within parent)

Reading Bookmarks

// Get the entire tree (can be large — use sparingly)
const tree = await chrome.bookmarks.getTree();

// Get a specific node and its children
const [node] = await chrome.bookmarks.get(nodeId);

// Get subtree rooted at a node (includes all descendants)
const [subtree] = await chrome.bookmarks.getSubTree(nodeId);

// Get children of a specific folder
const children = await chrome.bookmarks.getChildren(folderId);

// Get recently added bookmarks (newest first)
const recent = await chrome.bookmarks.getRecent(10);

// Search by title, url, or query string
const results = await chrome.bookmarks.search({ query: 'github' });
const byTitle = await chrome.bookmarks.search({ title: 'NeuralTab Saves' });

Writing Bookmarks

// Create a folder in "Other Bookmarks" (no parentId → defaults to "2")
const folder = await chrome.bookmarks.create({ title: 'NeuralTab Saves' });

// Create a bookmark inside that folder
const bookmark = await chrome.bookmarks.create({
  parentId: folder.id,
  title:    'Interesting article',
  url:      'https://example.com/article',
});

// Move a bookmark to a different folder
await chrome.bookmarks.move(bookmark.id, { parentId: otherFolderId });

// Update a bookmark's title or URL
await chrome.bookmarks.update(bookmark.id, { title: 'Better title' });

// Delete a bookmark (not a folder)
await chrome.bookmarks.remove(bookmark.id);

// Delete a folder and all its contents
await chrome.bookmarks.removeTree(folder.id);

Part 5 — chrome.history: Querying the Browser's Visit Log

The history API gives read/write access to Chrome's browsing history database. Each visited URL is represented as a HistoryItem, and each individual visit to that URL is a VisitItem. The distinction matters: if you visit the same URL three times, there is one HistoryItem with three VisitItem records. 

// Search history — text matches title and URL
const results = await chrome.history.search({
  text:        'github',
  maxResults:  20,            // default 100, max 100
  startTime:   Date.now() - 7 * 86400000,  // last 7 days
  endTime:     Date.now(),
});
// Returns: [{ id, url, title, lastVisitTime, visitCount, typedCount }]

// Get all individual visits to a specific URL
const visits = await chrome.history.getVisits({ url: 'https://github.com' });
// Returns: [{ id, visitId, visitTime, referringVisitId, transition }]

// Delete a specific URL from history
await chrome.history.deleteUrl({ url: 'https://embarrassing.example.com' });

// Delete history in a time range
await chrome.history.deleteRange({
  startTime: start,
  endTime:   end,
});

// Add a synthetic visit (useful for importing history from another browser)
await chrome.history.addUrl({ url: 'https://example.com' });
Privacy Consideration

The history permission is the most sensitive of NeuralTab's four optional permissions. Users' browsing history is deeply personal — it reveals medical searches, financial research, relationship status, and political views. Extensions that request history permission face higher CWS review scrutiny. Only request it when the feature clearly justifies the sensitivity, explain exactly what you do with history data in both the warm-ask UI and your privacy policy, and never send history data to external servers without explicit user consent. NeuralTab uses history exclusively for the local search panel — no data leaves the device.

Part 6 — chrome.notifications: Desktop-Level Alerts

Desktop notifications are the highest-priority communication channel available to a Chrome extension — they appear outside the browser, at the operating system level, even when Chrome is minimised. They require user permission (declared as optional_permissions) because they can interrupt the user's work. 

// Basic notification — the most common type
chrome.notifications.create('notif-id', {
  type:     'basic',
  iconUrl:  chrome.runtime.getURL('icons/icon48.png'),
  title:    'NeuralTab — Tab Check',
  message:  'You have 12 idle tabs open.',
  priority: 0,   // 0 = default, 1 = high, 2 = requires interaction
});

// Image notification — shows a preview image
chrome.notifications.create('article-saved', {
  type:     'image',
  iconUrl:  chrome.runtime.getURL('icons/icon48.png'),
  imageUrl: '...', // must be a data: URL or extension URL
  title:    'Saved!',
  message:  'Article bookmarked to NeuralTab Saves.',
});

// Handle notification click → open relevant page
chrome.notifications.onClicked.addListener((notifId) => {
  if (notifId === 'notif-id') {
    chrome.tabs.create({ url: chrome.runtime.getURL('tab_manager.html') });
    chrome.notifications.clear(notifId);
  }
});

// Handle notification button click
chrome.notifications.onButtonClicked.addListener((notifId, buttonIndex) => {
  if (notifId === 'notif-id' && buttonIndex === 0) {
    // User clicked the first button
  }
});

Part 7 — The Message Relay Pattern

Content scripts cannot call certain APIs that are only available in extension pages and background workers. chrome.runtime.openOptionsPage() is one — it silently does nothing when called from a content script. The message relay pattern solves this: the content script sends a message to the background worker, which then calls the restricted API on its behalf. 

// content.js — cannot call openOptionsPage() directly
shadow.getElementById('nt-btn-settings').addEventListener('click', () => {
  chrome.runtime.sendMessage({ action: 'openOptions' });
  // Does not need a response — fire and forget
});

// background.js — the relay
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.action === 'openOptions') {
    chrome.runtime.openOptionsPage();
    sendResponse({ ok: true });
    return false; // synchronous response — no need to return true
  }
  if (msg.action === 'triggerTabAnalysis') {
    runTabAnalysis().then(() => sendResponse({ ok: true }));
    return true; // ← IMPORTANT: return true to keep the channel open for async response
  }
});
Common Bug: Forgetting "return true" for Async Responses

If your onMessage handler calls sendResponse asynchronously (inside a Promise, a setTimeout, or after an await), you must return true synchronously from the listener. Returning true signals to Chrome that the message channel should be kept open for a delayed response. If you return false or undefined (by not returning anything), Chrome closes the channel immediately, and calling sendResponse later will throw an error: "The message port closed before a response was received." This is one of the top 5 most confusing bugs in Chrome extension development.

Part 8 — Tab Manager Architecture

The Tab Manager is NeuralTab's first full-page extension UI. It uses all four APIs from this module simultaneously. Let's trace how it works from load to interaction. 

// tab_manager.js — init() flow
async function init() {
  // 1. Check if "tabs" permission is granted
  const hasPermission = await chrome.permissions.contains({ permissions: ['tabs'] });

  if (!hasPermission) {
    // Show the permission banner with a Grant button
    document.getElementById('permission-banner').classList.add('visible');
    renderEmptyState('Grant the tabs permission above to view your open tabs.');
    return;
  }

  // 2. Load tabs — one chrome.tabs.query() call returns everything
  allTabs = await chrome.tabs.query({});

  // 3. Render stats sidebar (count by domain, idle count, pinned count)
  renderStats();

  // 4. Group tabs by domain using a Map, render each group as a collapsible card
  renderTabGroups();

  // 5. Wire button event handlers
  wireControls();
}

Grouping Tabs by Domain

// Group tabs using a Map — O(n) linear pass, no sorting needed
const groups = new Map();
for (const tab of tabs) {
  const domain = extractDomain(tab.url);
  if (!groups.has(domain)) groups.set(domain, []);
  groups.get(domain).push(tab);
}

// Sort: most tabs first (largest groups are the most actionable)
const sorted = [...groups.entries()].sort((a, b) => b[1].length - a[1].length);

// Helper: safely extract hostname from any URL including chrome://, file://, etc.
function extractDomain(url) {
  if (!url) return '(unknown)';
  try {
    const u = new URL(url);
    if (u.protocol === 'chrome:') return 'chrome://';
    if (u.protocol === 'chrome-extension:') return 'extension://';
    return u.hostname || url;
  } catch {
    return url.slice(0, 40);
  }
}

The try/catch around new URL(url) is essential. Not all tab URLs are valid URLs according to the WHATWG URL parser. chrome://newtab/ parses fine, but some internal Chrome pages use URL schemes that throw. The catch block falls back to showing the first 40 characters of the raw URL string.

Part 9 — Build and Run

  1. 1
    Copy all Module 04 files into your extension folder. The new files are background.js, tab_manager.html, tab_manager.css, and tab_manager.js. All other files replace their Module 03 counterparts.

    In chrome://extensions, click the reload button for NeuralTab. After reloading, look for a "Service worker" link in the NeuralTab card — this confirms the background worker is registered.

    Grant the history permission. Type something in the History search field and click Go. Results appear.
  8. 8
    In Options → Tabs & Alarms, click "Run analysis now". Check the service worker console for the storage update.

Warm-Up Exercise 1

Alarm inspector. Open the service worker DevTools console and run these commands in order:

// 1. Create a one-shot alarm 1 minute from now
chrome.alarms.create('test-alarm', { delayInMinutes: 1 });

What you learn: The full alarm CRUD cycle, hands-on. Notice that creating an alarm with the same name as an existing alarm silently replaces it — no error is thrown.

Core Exercise 2

Last-accessed tracking. In background.js, add a chrome.tabs.onActivated listener. When any tab is activated, write { tabId: Date.now() } into a tabAccessTimes object in chrome.storage.local. Core Exercise 3

After 7 days, show a second notification: "Permanent cleanup: delete 8 saved tabs from [date]?" with Yes/No buttons.

What you learn: Undo via bookmark-as-state — a real pattern used by Session Buddy. Multi-step notification flows. chrome.notifications button handlers. Time-gated follow-up alarms.

Stretch Exercise 5

Tab session snapshot. Add a "Save session" button to the Tab Manager. Clicking it reads all current tabs (URLs + titles + order), serialises them as JSON, and stores them in chrome.storage.local under a key sessions[timestamp]. Add a "Sessions" section to the Tab Manager sidebar that lists saved sessions by date. What you learn: chrome.windows.create(), full session management, storage with nested objects, and the patterns behind extensions like Session Buddy and Tab Session Manager — some of the most popular extensions in the Chrome Web Store.
