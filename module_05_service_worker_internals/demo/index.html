Every restart: all module-level variables reset to initial values. Only chrome.storage survives.
The Critical Insight: MV3 service workers are event-driven, not persistent. The browser terminates them to save RAM and battery. You must treat every wake-up as a cold start — re-read state from chrome.storage.local at the top of every handler.

What Module 05 Builds
Four major additions on top of the M04 foundation.
🔌

importScripts() — Shared Code

Module 04's background.js duplicated StorageManager logic inline. Module 05 fixes this with importScripts('storage_manager.js') as the very first line of background.js. Classic-mode service workers (no type:"module") support this synchronous import, making StorageManager a true global shared between the background and every extension page.

🧠

logSwEvent() — Lifecycle Audit Trail

A new method on StorageManager writes timestamped events to swLifecycleLog[] (capped at 50 entries). Event types include START, HEARTBEAT, ALARM, PORT_OPEN, PORT_CLOSE. Both the SW Monitor page and the Options page read and render this log with color-coded event types, giving you a full audit trail across worker restarts.

🏓

Keepalive Port + 25-Second Ping

An open chrome.runtime.connect() port counts as an active event, preventing the idle countdown from starting. The SW Monitor page connects a named port ('neuraltab-keepalive') and sends a ping every 25 seconds. The background responds with pong. As long as the port is open, the worker stays alive indefinitely.

📺

SW Monitor Page — Live Visualization

A new full-page dashboard (sw_monitor.html) polls getWorkerState every 2 seconds and renders: animated status dot, in-memory counter, uptime, total wakes, keepalive toggle, next alarm time, and a color-coded lifecycle event log. New entries flash with a fade-in animation. The log auto-scrolls if you're near the bottom.

Without the port: idle for 30s → Chrome starts the 5-minute countdown → worker killed → all in-memory state lost.
With the port open: every ping resets the idle timer. Worker lives as long as the port lives.
// sw_monitor.js — keepalive port pattern let port = null; let pingInterval = null; function openKeepalivePort() { port = chrome.runtime.connect({ name: 'neuraltab-keepalive' }); port.onMessage.addListener(msg => { if (msg.type === 'pong') updateLastHeartbeat(); }); port.onDisconnect.addListener(() => { port = null; }); pingInterval = setInterval(() => { if (port) port.postMessage({ type: 'ping' }); }, 25000); // safely under the ~30s idle threshold } // background.js — port handler chrome.runtime.onConnect.addListener(port => { if (port.name !== 'neuraltab-keepalive') return; keepalivePorts.add(port); StorageManager.logSwEvent('PORT_OPEN', `ports: ${keepalivePorts.size}`); port.onMessage.addListener(msg => { if (msg.type === 'ping') port.postMessage({ type: 'pong' }); }); port.onDisconnect.addListener(() => { keepalivePorts.delete(port); StorageManager.logSwEvent('PORT_CLOSE', `ports: ${keepalivePorts.size}`); }); });
importScripts() — The Shared Code Bridge
How background.js gets StorageManager without copying code.
// background.js — MUST be the very first line importScripts('storage_manager.js'); // After this line, StorageManager is a global — exactly like on pages const s = await StorageManager.get(['swStartCount']); await StorageManager.set({ swStartCount: (s.swStartCount || 0) + 1 });
Why classic mode? Chrome extension service workers default to "classic" module format (no type:"module" in manifest.json). Classic workers support the synchronous importScripts() call. If you want ES module import statements you must add "type":"module" to the background entry — but that breaks importScripts() and requires a bundler for multi-file setups. For NeuralTab, classic mode is the right choice: simple, synchronous, no build step.

Why NOT copy-paste?

If you duplicate StorageManager in background.js, both copies must be updated every time you add a new DEFAULTS key. With 8+ keys in M05, that's two places to maintain. One source file means one place to edit.

Why NOT ES modules?

ES module service workers (type:"module") require every import to be a static URL. They work but add complexity: you need relative paths, and Chrome has had minor bugs with module SW re-imports. Classic + importScripts() has zero sharp edges for this use case.

Why NOT a bundler?

Webpack/Rollup would bundle everything into one file, eliminating the need for importScripts(). That's the right call for a production extension. For a learning curriculum, keeping files separate makes debugging easier — you can read each file in isolation.
