Service Worker Internals

The 5-Minute Kill & Keepalive Patterns

Module 04 gave your extension a background script that runs tab analysis, fires alarms, and relays messages. But it had a dirty secret: Chrome kills that script after about five minutes of inactivity, wiping all in-memory state. In this module you will understand exactly why that happens, when it happens, and how to work with it — or, when necessary, how to prevent it. You will build the SW Monitor page: a live dashboard that makes the worker's lifecycle visible in real time, proving with numbers that the restart actually happened.

The 5-Minute Kill

When Google designed Manifest V3, they replaced the persistent background page with a service worker. The decision was driven by battery life and memory: persistent background pages kept code running 24/7 even when the extension had nothing to do. On a laptop with 30 extensions, that meant 30 JavaScript environments consuming RAM constantly. MV3's service worker is event-driven — it wakes up, handles an event, and goes back to sleep.

The lifecycle works like this:

Chrome MV3 Service Worker Lifecycle

Active (running)
→
No events ~30s
→
5-min countdown
KILLED by Chrome
←
Countdown expires
Next event arrives
→
Wake from cold start
→

Every cold start: all module-level variables reset to their initial values. Only chrome.storage survives a restart.

The specific timing is: Chrome starts a 5-minute idle countdown after your worker has had no active events for approximately 30 seconds. If you keep firing events (messages, alarm callbacks, storage reads), the countdown resets. If you go quiet, Chrome terminates the process when the countdown hits zero.

Critical Misconception
The 5-minute timer does not start the moment your last handler completes. It starts after a period of inactivity, roughly 30 seconds. The exact threshold is implementation-defined and has changed across Chrome versions. Do not hardcode assumptions about 5 minutes — design your extension to handle a restart at any time.

What Survives a Restart

This is the most important table in the entire module. Before you write any background code, ask: "Does this state need to survive a worker restart?" If yes, it must go in storage. If no, a module-level variable is fine.

State typeSurvives restart?Where to store it
Module-level variable (let x = 0)No — resets to 0Only if you don't need it after restart
chrome.storage.localYesTab data, user settings, history, large blobs
chrome.storage.syncYes (+ cross-device)User preferences ≤ 8 KB
chrome.storage.sessionSession onlyTemporary cross-context state (Chrome 102+)
chrome.alarmsYesScheduled work — alarms survive restarts
Open chrome.runtime.connect() portNo — port closes on killUsed as keepalive, not for data
WebSocket / fetch in-flightNo — killedMust be re-opened after restart
The Golden Rule of MV3 Background Code

Every handler in your service worker must be re-entrant. It must work correctly even if the worker has just restarted from a cold start. Read the values you need from chrome.storage at the start of every handler. Never assume in-memory state from a previous invocation is still there.

Proving a Restart With Numbers

The way NeuralTab Module 05 makes restarts tangible is with two counters that diverge after every restart:

0
inMemoryEventCounter
Module-level variable. Resets to 0 on every worker kill. Counts messages since this worker instance started.
47
swStartCount
Stored in chrome.storage.local. Increments on every onWorkerStart(). Never resets. Counts total lifetime restarts.

When you open the SW Monitor page with keepalive disabled and wait 5–6 minutes, you will see: inMemoryEventCounter jumps back to 0 the next time you interact with the extension, while swStartCount increments by 1. Those two numbers together prove, with no ambiguity, that a cold-start restart just happened.

importScripts() — The Code Sharing Bridge

Module 04 had a serious maintainability problem: storage_manager.js had one copy of the DEFAULTS object, and background.js had another copy (partially duplicated). Every time you added a new storage key, you had to remember to update both files. That's how bugs get born.

The solution in MV3 classic-mode service workers is importScripts():

// background.js — this MUST be the very first statement
importScripts('storage_manager.js');

// After this line, StorageManager is a global — just like in popup.js
const SW_START_TIME = Date.now();
let inMemoryEventCounter = 0;

async function onWorkerStart() {
  const s = await StorageManager.get(['swStartCount']);
  await StorageManager.set({
    swStartCount: (s.swStartCount || 0) + 1,
    swLastStart: Date.now(),
  });
  StorageManager.logSwEvent('START', `wake #${s.swStartCount + 1}`);
}

onWorkerStart();

Classic Mode vs ES Module Mode

Chrome extension service workers support two module formats. The choice affects everything about how you share code:

NeuralTab uses classic mode throughout modules 01–17 because it requires zero tooling, files remain individually readable in DevTools, and importScripts() is a direct mental model of what's happening. Module 18 (React + Vite + TypeScript) migrates to a bundler and ES modules for the production build.

Why importScripts() must be first
importScripts() is synchronous — it runs the imported file's code immediately and blocks until complete. If you place it after some async code, you risk a race condition where a message handler fires before StorageManager is defined. Always put it on the first line of background.js.

The Keepalive Port Pattern

Sometimes you genuinely need the service worker to stay alive — for example, while a user has the SW Monitor page open and is actively watching the worker metrics. The established pattern for this in MV3 is the keepalive port.

The mechanism: chrome.runtime.connect() creates a persistent message channel (a Port) between a page and the background worker. While a port is open, Chrome counts it as an active connection and holds off the idle timeout. When the port closes (the page closes, or you call port.disconnect()), the idle countdown resumes.

Port Mechanics

// background.js — onConnect handler
const keepalivePorts = new Set();

chrome.runtime.onConnect.addListener(port => {
  if (port.name !== 'neuraltab-keepalive') return;

  keepalivePorts.add(port);
  StorageManager.logSwEvent('PORT_OPEN', `total ports: ${keepalivePorts.size}`);

  port.onMessage.addListener(msg => {
    if (msg.type === 'ping') {
      inMemoryEventCounter++;
      port.postMessage({ type: 'pong', counter: inMemoryEventCounter });
    }
  });

  port.onDisconnect.addListener(() => {
    keepalivePorts.delete(port);
    StorageManager.logSwEvent('PORT_CLOSE', `total ports: ${keepalivePorts.size}`);
  });
});

A few things to notice:

  • The Set means multiple pages can simultaneously hold keepalive ports. The worker stays alive until all ports close.
  • The port name 'neuraltab-keepalive' is a convention. The onConnect listener receives all connect calls from all extension pages. The if (port.name !== ...) guard ensures unrelated ports (from other features) don't accidentally enter the keepalive Set.
  • port.onDisconnect fires automatically when the connecting page is closed — you don't need to manually call disconnect() for cleanup (though you can).

The 25-Second Ping Loop

An open port alone is not enough. Chrome has been observed closing "idle" ports (ports that receive no messages) after a period of inactivity. To ensure the port stays active, the SW Monitor page sends a ping message every 25 seconds:

// sw_monitor.js — keepalive port with ping loop
let port = null;
let pingInterval = null;

function openKeepalivePort() {
  port = chrome.runtime.connect({ name: 'neuraltab-keepalive' });

  port.onMessage.addListener(msg => {
    if (msg.type === 'pong') {
      document.getElementById('last-heartbeat').textContent = new Date().toLocaleTimeString();
    }
  });

  port.onDisconnect.addListener(() => {
    port = null;
    clearInterval(pingInterval);
    // Port closed — the worker may have been killed. UI shows "Dead".
  });

  pingInterval = setInterval(() => {
    if (port) port.postMessage({ type: 'ping' });
  }, 25000); // 25s — safely under the ~30s idle threshold
}

function closeKeepalivePort() {
  if (port) { port.disconnect(); port = null; }
  clearInterval(pingInterval); pingInterval = null;
}
Why 25 seconds and not 30?
Chrome's idle threshold is approximately 30 seconds. If you ping every 30 seconds, timer jitter and CPU scheduling delays could occasionally push the ping to second 31 — after the idle window has already started. A 25-second interval provides a 5-second safety margin that absorbs all practical variation.
Keepalive is not unconditional
Keeping the worker alive burns memory and prevents Chrome from reclaiming resources when the extension is idle. Only open the keepalive port when the user is actively looking at the SW Monitor page. Disconnect it the moment the page closes (handled automatically by port.onDisconnect when the page unloads).

background.js Deep Dive

Module 05's background.js has three new responsibilities beyond what Module 04 built. Let's read each one carefully.

onWorkerStart() — Registering Every Wake

This function runs unconditionally at the top level of background.js, so it executes on every single cold start. It does three things:

async function onWorkerStart() {
  const s = await StorageManager.get(['swStartCount']);
  await StorageManager.set({
    swStartCount: (s.swStartCount || 0) + 1,  // lifetime counter
    swLastStart:  Date.now(),                  // timestamp for uptime calc
  });
  StorageManager.logSwEvent('START', `wake #${(s.swStartCount || 0) + 1}`);
}

onWorkerStart(); // called at module level, not inside any handler

The fact that this call is at the module level is intentional. Module-level code in a service worker runs once when the worker starts — whether that start is due to install, update, alarm, message, or any other event. This is the correct place to record "the worker just woke up."

The Heartbeat Alarm

Alongside the existing 'tab-analysis' alarm, Module 05 adds a second alarm:

chrome.runtime.onInstalled.addListener(() => {
  chrome.alarms.create('tab-analysis', { periodInMinutes: 30 });
  chrome.alarms.create('sw-heartbeat',  { periodInMinutes: 0.5 }); // 30s minimum
});

chrome.alarms.onAlarm.addListener(alarm => {
  inMemoryEventCounter++;
  if (alarm.name === 'sw-heartbeat') {
    StorageManager.logSwEvent('HEARTBEAT', `counter: ${inMemoryEventCounter}`);
    return;
  }
  if (alarm.name === 'tab-analysis') runTabAnalysis();
});

The heartbeat alarm serves two purposes: (1) It wakes the worker every 30 seconds even without a keepalive port, ensuring the background can process storage changes. (2) It generates a visible "HEARTBEAT" event in the lifecycle log, letting you watch the worker's rhythm in the SW Monitor page.

logSwEvent() — Persistent Audit Trail

This new StorageManager method writes timestamped events to swLifecycleLog[] in storage. The cap at 50 entries prevents unbounded storage growth:

// storage_manager.js addition
async logSwEvent(event, detail = '') {
  const s = await this.get(['swLifecycleLog']);
  const log = s.swLifecycleLog || [];
  log.push({ ts: Date.now(), event, detail });
  if (log.length > 50) log.splice(0, log.length - 50); // keep newest 50
  await this.set({ swLifecycleLog: log });
},

Every event is typed so the UI can color-code them: START (green), HEARTBEAT (cyan), ALARM (gold), PORT_OPEN (purple), PORT_CLOSE (orange). The Options page and the SW Monitor both read this log and render the same color scheme, giving you a consistent audit trail wherever you look.

The SW Monitor Page

The SW Monitor is a full-page developer tool built into the extension. You open it from the popup or Options page. It is a live, continuously updating view of the service worker's internal state.

The Polling Strategy: Why 2 Seconds

The SW Monitor uses a 2-second setInterval to call sendMessage({ action: 'getWorkerState' }) and update the live metrics panel. You might wonder: why not use StorageManager.onChange() like the Options page does?

The answer is that the most important metrics are in-memory:

  • inMemoryEventCounter — a module-level variable, not in storage
  • uptime — calculated as Date.now() - SW_START_TIME each time it's read
  • keepalivePorts — a Set of live port objects, not serializable to storage

These cannot trigger storage.onChanged because they never touch storage. The only way to read them is to send a message to the live worker and ask. So the SW Monitor uses a hybrid approach: storage.onChange for the lifecycle log and swStartCount, plus a 2-second poll for everything ephemeral.

// sw_monitor.js — polling loop
setInterval(async () => {
  try {
    const resp = await chrome.runtime.sendMessage({ action: 'getWorkerState' });
    if (resp) {
      setWorkerAlive(true);
      document.getElementById('counter').textContent   = resp.inMemoryEventCounter;
      document.getElementById('uptime').textContent     = formatUptime(resp.uptime);
      document.getElementById('kl-ports').textContent   = resp.keepalivePorts;
    }
  } catch {
    // sendMessage throws if the worker is dead — show "Dead" status
    setWorkerAlive(false);
  }
}, 2000);
Reading the worker status from the UI
When sendMessage throws (the worker is dead), the catch block sets the status to "Dead." When it succeeds, the worker is alive. This is a clean liveness check: if the worker can respond to a message, it's alive; if it can't, it's dead. No other mechanism is needed.

Log Rendering — Delta Updates

The lifecycle log can have up to 50 entries. Re-rendering all 50 every 2 seconds would cause DOM thrashing. Instead, the SW Monitor tracks lastLogLength and only renders new entries:

let lastLogLength = 0;

async function refreshLog() {
  const s = await StorageManager.get(['swLifecycleLog']);
  const log = s.swLifecycleLog || [];
  if (log.length === lastLogLength) return; // nothing new

  const newEntries = log.slice(lastLogLength);
  lastLogLength = log.length;

  const container = document.getElementById('log-container');
  for (const entry of newEntries) {
    const el = buildLogEntry(entry);
    el.classList.add('event-NEW'); // flashes gold, fades after 800ms
    container.appendChild(el);
    setTimeout(() => el.classList.remove('event-NEW'), 800);
  }
  // Auto-scroll if user is near the bottom
  if (container.scrollHeight - container.scrollTop < container.clientHeight + 80) {
    container.scrollTop = container.scrollHeight;
  }
}

The .event-NEW CSS class applies a brief gold background that fades to transparent over 800ms, drawing the eye to new log entries without requiring the user to scan the entire list.

Tab Last-Access Tracking

Module 04's Tab Manager labeled tabs as "idle" using a proxy metric: !tab.active && !tab.audible. That's a rough approximation — a tab could have been active 2 seconds ago and still look "idle" by that definition.

Module 05 fixes this with true last-access timestamps recorded in the background:

// background.js — record exact timestamp when each tab becomes active
chrome.tabs.onActivated.addListener(async ({ tabId }) => {
  inMemoryEventCounter++;
  const s = await StorageManager.get(['tabAccessTimes']);
  const times = s.tabAccessTimes || {};
  times[tabId] = Date.now();

  // Cap at 200 entries — evict oldest
  const entries = Object.entries(times).sort(([,a],[,b]) => a - b);
  while (entries.length > 200) entries.shift();
  await StorageManager.set({ tabAccessTimes: Object.fromEntries(entries) });
});

In tab_manager.js, buildTabEl() reads this map and displays the elapsed time:

const lastAccess = tabAccessTimes[tab.id];
const agoMin = lastAccess ? Math.floor((Date.now() - lastAccess) / 60000) : null;
const isStale = agoMin !== null && agoMin > 30; // orange warning at 30+ minutes

lastAccessHtml = lastAccess
  ? `<div class="tab-last-access${isStale ? ' stale' : ''}">
       Last active: ${agoMin === 0 ? 'just now' : agoMin + 'm ago'}
     </div>`
  : ''; // no data yet — tab was never activated during this session

The "stale" threshold is 30 minutes, shown in orange. This is configurable in a future module — for now it's hardcoded to match the tab-analysis alarm period.

Exercises

Exercise 01

Prove the 5-Minute Kill

  1. Load the Module 05 extension. Open the SW Monitor page (sw_monitor.html).
  2. Disable the keepalive toggle. Note the current inMemoryEventCounter value.
  3. Go to chrome://extensions, find NeuralTab, and click the "Service Worker" link to open the background inspector. Note the "Alive" indicator.
  4. Wait 5–7 minutes without interacting with the extension. The background inspector should show the worker going offline.
  5. Click anywhere in the NeuralTab popup. The worker wakes from a cold start. Open SW Monitor again — inMemoryEventCounter should have reset to 0 or 1, while swStartCount incremented.
What to look for: The exact moment inMemoryEventCounter resets is the exact moment a new worker instance started. Every instance starts at 0.
Exercise 02

Add a PORT_MULTI_OPEN Log Event

  1. Modify background.js's onConnect handler to log a special 'PORT_MULTI' event when keepalivePorts.size > 1.
  2. Open SW Monitor in two separate browser tabs. Verify PORT_MULTI appears in the log.
  3. Close one tab. Verify PORT_CLOSE appears and keepalivePorts.size drops to 1.
Why this matters: Multi-page extensions (several sidebars, options, and popups all open simultaneously) all connect ports. Tracking the Set size tells you how many "active users" the worker has right now.
Exercise 03

Add an ALARM_MISSED Detection

  1. In background.js, read swLastStart and swLastHeartbeat (a new storage key you'll add) on every heartbeat alarm.
  2. If the gap between now and swLastHeartbeat is more than 2 minutes, log an 'ALARM_MISSED' event with the gap duration in seconds.
  3. Test by disabling keepalive and waiting >2 minutes, then waking the worker.
Real-world use: This is how production extensions detect "the worker was dead and we missed alarms." A gap of more than 2× the alarm period means at least one firing was missed.
Exercise 04

Make the Log Exportable

  1. Add an "Export log" button to sw_monitor.html.
  2. In the click handler, read swLifecycleLog from storage, convert it to a JSON file with Blob, and trigger a download.
  3. Open the downloaded file and verify all 50 (or fewer) events are present with correct timestamps.
Pattern to use: URL.createObjectURL(new Blob([JSON.stringify(log, null, 2)], { type: 'application/json' })) — the same pattern used in options.js's export button.
Exercise 05

Build a Worker Crash Counter

  1. Add a new storage key: swCrashCount: 0.
  2. In onWorkerStart(), check if swLastStart exists and the gap between swLastStart and now is greater than 6 minutes (which indicates a kill, not a graceful restart).
  3. If the gap exceeds 6 minutes, increment swCrashCount and log a 'UNEXPECTED_KILL' event.
  4. Display the crash count in the SW Monitor's live metrics sidebar.
Caveats: Chrome restarting (browser close + open) also creates large gaps. A robust implementation would also store the last browser session ID to distinguish extension kills from browser restarts.

Module Summary

What You Built in Module 05

  • importScripts() pattern — StorageManager is now a true shared global in the service worker, eliminating code duplication.
  • onWorkerStart() — records every cold start with a persistent counter and timestamp, giving you full restart history.
  • logSwEvent() — a persistent, capped audit trail of the worker's lifecycle events, accessible from any extension page.
  • Keepalive port pattern — chrome.runtime.connect() + 25-second ping loop prevents the idle timeout while the SW Monitor is open.
  • SW Monitor page — live dashboard with 2-second poll for ephemeral metrics + reactive storage.onChange for persistent state.
  • Heartbeat alarm — 30-second minimum-period alarm as background keepalive fallback when no port is open.
  • tabAccessTimes tracking — real last-access timestamps from chrome.tabs.onActivated, displayed with stale warnings in Tab Manager.
The Core Mental Model
A MV3 service worker is not a daemon. It is a function that Chrome calls when events arrive. Between calls, it does not exist. Every piece of state you care about across calls must live in chrome.storage, in chrome.alarms, or in another persistent API. Once you fully internalize this, MV3 stops feeling like a limitation and starts feeling like a clean architecture.
