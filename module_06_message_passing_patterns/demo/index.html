The 4 Communication Patterns
Each pattern exists because the others are insufficient for a specific use case. You need all four.
Pattern 01 · One-Way
Fire & Forget

Send a message and immediately move on. No waiting, no response. Use when the sender doesn't need confirmation — logging events, firing analytics, notifying background of page events.

// Sender — no await, no .then()
chrome.runtime.sendMessage({ action: 'oneWayLog', text });

// Background — no sendResponse call
if (msg.action === 'oneWayLog') {
  StorageManager.logMessage('IN', 'oneWayLog', ctx, msg.text);
  return false; // no response
}
Pattern 02 · Request/Response
Async Await + return true

Sender awaits a reply. Background must call sendResponse asynchronously AND return true before the async work begins — or the channel closes and the promise rejects.

// Sender
const result = await chrome.runtime.sendMessage({
  action: 'echoRequest', payload
});

// Background — the return true is CRITICAL
if (msg.action === 'echoRequest') {
  doAsync().then(data => sendResponse(data));
  return true; // ← keeps channel open
}
Pattern 03 · Port
Persistent Streaming Channel

A long-lived bidirectional channel. Background streams chunks over time; client controls the stream. Perfect for live data feeds, progress updates, real-time monitoring.

// Client — connect once, receive many
const port = chrome.runtime.connect({ name: 'neuraltab-stream' });
port.onMessage.addListener(msg => renderChunk(msg));
port.postMessage({ action: 'startStream', chunks: 20 });

// Background — sends chunks asynchronously
setInterval(() => port.postMessage({ type: 'chunk', data }), 150);
Pattern 04 · Storage
Pub/Sub via onChanged

Write to chrome.storage.local in one context — every other open page reacts via storage.onChanged. Zero-infrastructure pub/sub. No message routing, no port management.

// Publisher: any context
await chrome.storage.local.set({ demoCounter: n });

// Subscriber: EVERY open extension page
chrome.storage.onChanged.addListener(changes => {
  if (changes.demoCounter)
    updateDisplay(changes.demoCounter.newValue);
});
The Key Experiment: Load the extension, open the Message Lab in two separate tabs. Increment the counter in Tab 1. Watch it instantly update in Tab 2. That update crossed a tab boundary with zero message sending — just a storage write and an onChanged event. That is Pattern 4 in action.
Who Can Message Whom
The context matrix — not all message directions are available to all contexts.
From → → Background → Popup / Options → Content Script → Inject Script
Background Self (no need) Storage.onChanged only chrome.tabs.sendMessage(tabId) Cannot (no chrome.* in page)
Popup / Options sendMessage Storage.onChanged chrome.tabs.sendMessage(tabId) Cannot directly
Content Script sendMessage Storage.onChanged Cannot (different tab/context) window.postMessage
Inject Script Cannot (no chrome.*) Cannot window.postMessage Same page = same world
The 3-Hop Relay Chain
When a page-world script needs to reach the background, it takes three hops.
inject.js
page world
window.postMessage
source: 'neuraltab-inject'
→
content.js
isolated world
validates source
then chrome.runtime.sendMessage
→
background.js
service worker
action: 'relayFromPage'
full chrome.* access
Security Warning: The content script must validate e.data.source === 'neuraltab-inject' before relaying to background. A malicious page can call window.postMessage with any source. Always validate the message origin and schema before acting on page-world data.
When to Use Each Pattern
Use One-Way when
  • Logging events
  • Firing analytics pings
  • Notifying background of page actions (no confirmation needed)
  • Sender doesn't need to know if it succeeded
Use Req/Res when
  • Sender needs data back
  • Sender needs confirmation of success/failure
  • One-time query (tab stats, worker state, API call)
  • Response fits in a single message
Use Port when
  • Response is chunked over time
  • Bidirectional control signals needed
  • Streaming data (progress bars, live feeds)
  • Keepalive connection needed
Use Storage when
  • Multiple pages need the same data
  • Data must survive worker restarts
  • Publisher doesn't know who is listening
  • Fan-out to N subscribers at once
