Before We Write a Single Message

You cannot understand Chrome extension messaging without first understanding who is doing the talking. An extension is not a single program. It is a constellation of separate JavaScript contexts, each running in its own V8 isolate, each with different API access and different lifetimes. When one context sends a message to another, it is genuinely crossing a security boundary.

Here is the full picture of NeuralTab's contexts by the end of Module 06:

background.js (Service Worker)
← Full chrome.* API. Ephemeral. Dies when idle. Lives in its own thread.
popup.html + popup.js
← Extension page. Closes when popup closes. Shares chrome.* access.
options.html + options.js
← Extension page. Lives as long as the tab is open.
message_lab.html + message_lab.js
← Extension page. Can be open in multiple tabs simultaneously.
content.js
← Injected into every web page. Isolated world. Limited chrome.* API.
assets/inject.js
← Page world. Injected via content.js. NO chrome.* API at all.

Each row is a separate JavaScript execution context. They cannot share variables, cannot share function references, cannot reach into each other's memory. The only way to communicate is through Chrome's message passing APIs — and through window.postMessage for the page-world boundary.

This is not an accident. This isolation is the security model. A malicious web page cannot call your background's functions directly. It cannot read your storage directly. Every crossing is mediated, and that mediation is where both power and danger live.

The Four Mechanisms Chrome Provides

Chrome gives you exactly four ways to move data between contexts:

Mechanism API Direction Persistent? Best for
One-way message sendMessage Any → background / background → content No Fire & forget events, logging
Request/response sendMessage + sendResponse Same as above No Queries, data fetches, confirmations
Port channel connect + postMessage Bidirectional, long-lived Yes (until disconnect) Streaming, keepalive, real-time data
Storage event storage.set + storage.onChanged Any → storage → all listeners Yes (persists across restarts) Shared state, multi-page sync, pub/sub

Plus window.postMessage — not a Chrome API, but a browser DOM API — used specifically to cross the page-world / isolated-world boundary between inject.js and content.js.

01
Pattern
Fire & Forget — One-Way Message

The simplest pattern. You send a message. You don't wait for a reply. You don't check if it arrived. You don't care. This sounds careless — but it is exactly the right choice for a large class of operations.

When is fire & forget correct? When the event itself is the whole point and confirmation would be noise. Logging is the canonical example. When the user opens a new tab, content.js fires an event to background so background can track it. If that log write fails, what would you do? Retry? Pop an alert? No. You accept best-effort semantics and move on. Analytics pings, heartbeat signals, page lifecycle notifications — all of these are naturally fire & forget.

The Sender Side

// content.js or message_lab.js — sender sends and immediately continues
function logEventToBackground(action, text) {
  chrome.runtime.sendMessage({ action, text });
  // No await. No .then(). No response variable.
  // Execution continues on the next line immediately.
}

Notice there is no await, no .then(), no error handler. The message is dispatched into the Chrome runtime queue and we proceed. Chrome will deliver it asynchronously to the registered listener.

You might see a console warning: "A listener indicated an asynchronous response by returning true, but the message channel closed before a response was received." If you see this on a fire & forget sender, it means the background returned true by mistake when it should have returned false. We'll cover that in Pattern 2.

The Background Receiver

// background.js — receiver handles and returns false (or nothing)
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.action === 'oneWayLog') {
    // Do the work synchronously or fire-and-forget an async operation
    StorageManager.logMessage('IN', 'oneWayLog', 'popup', msg.text);
    // Return false: we will NOT call sendResponse.
    // Chrome can clean up the channel immediately.
    return false;
  }
});

The critical rule: if you are not going to call sendResponse, return false (or return nothing). This tells Chrome that the channel can be torn down immediately. If you accidentally return true, Chrome holds the channel open waiting for a response that never comes — for about 30 seconds before timing out. That is a resource leak.

Common mistake: Using one big onMessage listener where the final line is return true to handle ALL actions, including fire & forget ones. The return true will cause Chrome to hold the channel open even for actions that will never call sendResponse. Each action branch should return explicitly: return false for no-reply actions, return true for async reply actions.

02
Pattern
Async Request/Response — The return true Danger

This is where most extension developers make their first serious mistake. The pattern looks simple — send a message, get a response back — but it has an invisible tripwire that causes cryptic errors and hours of debugging.

The scenario: the popup wants live statistics from the service worker. How many messages have been processed? How long has the worker been alive? What is its memory usage? None of this is in storage yet — it is the worker's current live state. The popup must ask and wait for an answer.

The Sender

// popup.js — sends a request and awaits the response
async function fetchStats() {
  try {
    const result = await chrome.runtime.sendMessage({
      action: 'getMessageStats'
    });
    renderStats(result);
  } catch (err) {
    console.error('Stats fetch failed:', err.message);
  }
}

The await suspends fetchStats until the background calls sendResponse. If sendResponse is never called, the await hangs for ~30 seconds then rejects with a "port closed" error. If return true is not returned from the listener, the channel closes before sendResponse is ever reached, and the await rejects immediately.

The Background Receiver

Here is the correct implementation. Read it carefully:

// background.js — async handler with the critical return true
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.action === 'getMessageStats') {
    // ↓ MUST start the async work here, NOT before return true
    StorageManager.get(['messageLog', 'messageCount'])
      .then(s => sendResponse({
        messageCount:   s.messageCount || 0,
        swStartTime:    swStartTime,
        inMemoryCount:  inMemoryEventCounter,
        streamPortCount: streamPorts.size
      }))
      .catch(e => sendResponse({ error: e.message }));

    return true; // ← THIS IS THE CRITICAL LINE. It must execute BEFORE
                 //   the .then() resolves. It keeps the channel open.
  }
});
⚠ The Most Dangerous Line in Extension Development
return true must be reached synchronously before any async operation resolves. Here is what happens if you get it wrong:

If you forget return true: The listener returns undefined (falsy). Chrome tears down the message channel synchronously. When your async code eventually calls sendResponse, the channel is gone. The sender's await rejects immediately with: Error: The message port closed before a response was received.

If you call sendResponse twice: The second call silently fails with no error. This happens when you have both a .then() and a .catch() that both call sendResponse, and both run somehow. Use a let responded = false guard if necessary.

If you return true but never call sendResponse: The sender hangs for ~30 seconds, then rejects with the same "port closed" error. Always call sendResponse on both success and error paths.

Why Can't Chrome Just Handle This Automatically?

Because Chrome cannot know whether your listener is synchronous or asynchronous before it runs. The return true is an explicit signal to Chrome: "I have started an async operation; please keep this channel open until I explicitly call sendResponse." Without that signal, Chrome would need to hold open every single message channel indefinitely, which is a resource nightmare at scale.

The alternative would be to use Promises natively in onMessage — but Chrome's onMessage predates modern JavaScript async/await idioms and the API contract was designed for callback-style code. There is an open Chromium feature request to support returning a Promise directly, but as of 2025 it is not in the stable channel.

One Listener to Rule Them All

Chrome fires ALL registered onMessage listeners for every single incoming message. If you have two listeners and both return true, they both try to handle sendResponse. The first call wins; the second silently fails. The sender gets the first response, which may be wrong depending on which listener resolved first.

NeuralTab uses the single listener / action routing pattern:

// background.js — one listener, all routing inside
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  switch (msg.action) {
    case 'oneWayLog':
      StorageManager.logMessage('IN', 'oneWayLog', 'bg', msg.text);
      return false;

    case 'echoRequest':
      StorageManager.logMessage('IN', 'echoRequest', 'bg', '')
        .then(() => sendResponse({
          echo: msg.payload,
          swTimestamp: Date.now()
        }));
      return true; // ← async: keep channel open

    case 'getMessageStats':
      StorageManager.get(['messageCount'])
        .then(s => sendResponse(s))
        .catch(e => sendResponse({ error: e.message }));
      return true; // ← async: keep channel open

    default:
      return false;
  }
});

Design principle: Every case must return explicitly. Cases that call sendResponse asynchronously return true. Cases that don't return false. The default case always returns false — unknown actions are silently ignored rather than hanging the sender.

03
Pattern
Port-Based Streaming — Persistent Channels

Patterns 1 and 2 share a fundamental characteristic: they are one-shot. One message in, zero or one message out, channel closes. This is fine for point queries and fire-and-forget events. But what if you need to stream 50 chunks of data over 5 seconds? Opening 50 separate sendMessage channels is expensive. return true doesn't work across multiple responses — sendResponse can only be called once per message.

Ports solve this. A port is a long-lived, bidirectional channel. You open it once; you can exchange unlimited messages in both directions; you close it explicitly or it closes when either end disconnects. The Message Lab's streaming panel uses a port to demonstrate a real-time chunk feed.

The Client (Message Lab)

// message_lab.js — open a port, send control messages, receive chunks
let streamPort = null;

function startStream(chunks, delayMs) {
  // Connect: background's onConnect fires immediately
  streamPort = chrome.runtime.connect({ name: 'neuraltab-stream' });

  // Listen for chunks coming back from background
  streamPort.onMessage.addListener(msg => {
    if (msg.type === 'chunk')    renderChunk(msg);
    if (msg.type === 'complete') renderComplete(msg);
    if (msg.type === 'pong')     renderPong(msg);
  });

  // Handle disconnection (background crashed, SW restarted, etc.)
  streamPort.onDisconnect.addListener(() => {
    streamPort = null;
    renderDisconnected();
  });

  // Send the start command — background begins streaming
  streamPort.postMessage({ action: 'startStream', chunks, delayMs });
}

function stopStream() {
  streamPort?.postMessage({ action: 'stopStream' });
}

The Background (Streaming Server)

// background.js — port server using a Set for multi-client support
const streamPorts = new Set(); // NOT a single reference — supports N simultaneous clients

chrome.runtime.onConnect.addListener(port => {
  if (port.name !== 'neuraltab-stream') return;

  streamPorts.add(port);
  let streamInterval = null;

  port.onMessage.addListener(msg => {
    if (msg.action === 'startStream') {
      let sent = 0;
      streamInterval = setInterval(() => {
        sent++;
        port.postMessage({ type: 'chunk', index: sent, total: msg.chunks, data: generateChunkData() });
        if (sent >= msg.chunks) {
          clearInterval(streamInterval);
          port.postMessage({ type: 'complete', totalSent: sent });
        }
      }, msg.delayMs || 150);
    }
    if (msg.action === 'stopStream') {
      clearInterval(streamInterval);
    }
  });

  port.onDisconnect.addListener(() => {
    clearInterval(streamInterval); // stop streaming if client disconnects mid-stream
    streamPorts.delete(port);
  });
});

Why a Set and not a single streamPort variable? The Message Lab can be open in multiple tabs simultaneously. Each tab connects its own port. With a single variable, the second tab's connection would overwrite the first, and the first tab would stop receiving chunks. The Set stores every active connection independently. Each port's onMessage and onDisconnect are closures that capture that specific port object, so they are fully self-contained.

Port Lifecycle

Event Who fires it What to do
chrome.runtime.connect() Client Background's onConnect fires. Add port to Set. Register handlers.
port.postMessage() Either side Other side's port.onMessage fires.
port.disconnect() Either side Other side's port.onDisconnect fires. Remove from Set. Stop intervals.
Service worker death Chrome (involuntary) Client's port.onDisconnect fires. Reconnect if needed.
Tab close / popup close Chrome (involuntary) Background's port.onDisconnect fires. Clean up intervals.

Interval leak: If the client disconnects mid-stream and you do not clearInterval in port.onDisconnect, the background keeps firing the interval and calling port.postMessage on a dead port. In MV3 this does not crash, but it burns CPU and keeps the service worker alive unnecessarily.

Ports vs sendMessage — The Decision Boundary

Use a port when any of these are true:

  • You will send more than one response to a single request (streaming)
  • You need bidirectional control (client can send stop/pause signals during streaming)
  • You need the connection to stay alive across multiple operations (keepalive port)
  • You are streaming data where the number of chunks is unknown upfront

Use sendMessage when any of these are true:

  • You need exactly one response to one request
  • The exchange is infrequent (opening a port has overhead)
  • You are doing fire & forget (zero responses)
04
Pattern
Storage Pub/Sub — Zero-Infrastructure Broadcasting

Here is a problem that Patterns 1-3 cannot elegantly solve: the popup, the options page, and the Message Lab are all open at the same time. A counter increments somewhere. All three pages need to update simultaneously. How do you route that update?

With Patterns 1-3, you would need to know who is open, maintain a list of listeners, and broadcast to each one. That is pub/sub infrastructure — subscriber registration, message routing, unsubscription on tab close. It is non-trivial code, and you have to re-implement it every time.

Pattern 4 makes this trivial. chrome.storage.onChanged fires in every open extension page simultaneously when storage changes. The publisher writes once. Every subscriber reacts. Zero routing code.

The Publisher — Any Context

// message_lab.js — the "+" button. Direct storage write. No background involved.
async function incrementCounter() {
  const s = await StorageManager.get(['demoCounter']);
  const next = (s.demoCounter || 0) + 1;
  await StorageManager.set({ demoCounter: next });
  // That's it. Every open page will receive the onChanged event.
}

The Subscriber — Every Open Extension Page

// message_lab.js — listens for changes. Fires when ANY storage key changes.
StorageManager.onChange(changes => {
  if (changes.demoCounter !== undefined) {
    onDemoCounterChange(changes.demoCounter);
  }
});

// popup.js — same pattern, different page, same event
StorageManager.onChange(changes => {
  if (changes.demoCounter) updateCounterDisplay(changes.demoCounter.newValue);
  if (changes.messageCount) updateMsgDisplay(changes.messageCount.newValue);
});

The changes object contains only the keys that changed, with { oldValue, newValue } for each. If you have 50 storage keys and only demoCounter changed, the event fires with a changes object containing only demoCounter. You check for the keys you care about and ignore the rest.

The StorageManager.onChange Wrapper

// storage_manager.js — wraps chrome.storage.onChanged
onChange(callback) {
  chrome.storage.onChanged.addListener((changes, areaName) => {
    if (areaName !== 'local') return; // only react to 'local' area
    const flat = {};
    for (const [key, { oldValue, newValue }] of Object.entries(changes)) {
      flat[key] = newValue;
    }
    callback(flat); // simplified: just newValues keyed by name
  });
}

The Key Experiment (do this now): Load the extension. Open the Message Lab (chrome://extensions → NeuralTab → click the ⚗ icon in the popup). Now open a second Message Lab tab by right-clicking the icon and opening in a new tab, or pressing the Open Lab button in options. In Tab 1, click the counter increment button. Watch Tab 2's counter update without any page refresh, without any socket, without any polling. That is Pattern 4. Storage is the message bus.

When NOT to Use Pattern 4

Pattern 4 is deceptively powerful, but it has constraints:

  • No ordering guarantees across multiple writers. If Tab 1 and Tab 2 both increment the counter simultaneously (read-modify-write), you have a race condition. The last write wins, and you lose increments. For correctness under concurrent writes, route all writes through the background (which processes them sequentially).
  • Storage size limits. chrome.storage.local has a 5 MB default limit. Do not use Pattern 4 to stream high-frequency data (use a port instead). Use it for shared state that is small and infrequently written.
  • Content scripts do not receive onChanged events by default in some older Chrome versions. Test explicitly if you need content scripts to react to storage changes.
  • Persistence = baggage. Everything in storage survives extension restarts. Make sure the data you are pub/subbing is something you actually want to persist. Use chrome.storage.session (MV3 only) for ephemeral shared state.

The 3-Hop Relay Chain

Module 06 introduces a fourth "who" in the messaging picture: assets/inject.js, running in the page world. This script is injected into every web page via executeScript. It sits in the same JavaScript context as the page's own scripts — it can read and write page variables, call page APIs, intercept events. But it has no chrome.* API access at all.

This is the fundamental isolation in Chrome's extension architecture. The page world and the extension world are separate. To bridge them, we need a relay chain:

HOP 1
inject.js
window.postMessage({ source: 'neuraltab-inject', type: 'RELAY_TO_BACKGROUND', payload })
→
HOP 2
content.js
Validates source. chrome.runtime.sendMessage({ action: 'relayFromPage', payload })
→
HOP 3
background.js
Full chrome.* access. Acts on payload. sendResponse({ result })

The inject.js Side — Publishing into the DOM

// assets/inject.js — runs in page world, no chrome.* available
window.__neuralTab = {
  relayToBackground(payload) {
    return new Promise((resolve, reject) => {
      const requestId = Math.random().toString(36).slice(2);
      const timeout = setTimeout(() => reject(new Error('Relay timeout')), 3000);

      window.addEventListener('message', function handler(e) {
        if (e.data?.type !== 'RELAY_RESPONSE' || e.data?.requestId !== requestId) return;
        window.removeEventListener('message', handler);
        clearTimeout(timeout);
        resolve(e.data.result);
      });

      window.postMessage({ source: 'neuraltab-inject', type: 'RELAY_TO_BACKGROUND', payload, requestId }, '*');
    });
  }
};

The content.js Side — Validation and Forwarding

// content.js — listens for page world messages, validates, relays
function listenForPageMessages() {
  window.addEventListener('message', async e => {
    // Security: ONLY relay messages from our own inject script
    if (e.data?.source !== 'neuraltab-inject') return;
    if (e.data?.type !== 'RELAY_TO_BACKGROUND') return;

    const { payload, requestId } = e.data;
    try {
      const result = await chrome.runtime.sendMessage({
        action: 'relayFromPage', payload, requestId
      });
      // Echo the result back into the page world
      window.postMessage({ type: 'RELAY_RESPONSE', requestId, result }, '*');
    } catch (err) {
      window.postMessage({ type: 'RELAY_RESPONSE', requestId, error: err.message }, '*');
    }
  });
}

Security critical: The content script must validate e.data.source === 'neuraltab-inject'. Any script on the web page — including malicious third-party scripts — can call window.postMessage. Without the source check, a malicious page could craft fake relay messages and trick your content script into forwarding arbitrary payloads to your background. The source field is not cryptographically secure (any page can set it), but it raises the bar above casual exploitation. For sensitive operations, add schema validation on the payload as well.

Error Handling Across All Four Patterns

Each pattern has distinct failure modes. Here is how to defend against them:

Pattern 1 (Fire & Forget) — Errors Are Silent

By design, fire & forget gives you no feedback. If the background is not running, the message is silently dropped. If storage write fails inside the background handler, you never know. This is acceptable for logging and analytics — if a log entry is lost, the system continues. Do not use Pattern 1 for operations that must succeed.

Pattern 2 (Request/Response) — Catch Everything

// Always wrap in try/catch — the promise rejects on channel close
try {
  const result = await chrome.runtime.sendMessage({ action: 'echoRequest', payload });
  if (result?.error) showError(result.error); // background sent back an error payload
  else handleResult(result);
} catch (err) {
  // Catches: port closed, SW not running, no listener registered
  if (err.message.includes('Could not establish connection')) {
    showWarning('Background worker is not running. Try again.');
  } else {
    showError(err.message);
  }
}

Pattern 3 (Port) — Handle onDisconnect

// Always register onDisconnect BEFORE postMessage
const port = chrome.runtime.connect({ name: 'neuraltab-stream' });
port.onDisconnect.addListener(() => {
  const error = chrome.runtime.lastError;
  if (error) console.error('Port disconnected with error:', error.message);
  // SW may have died. Reconnect logic here if needed.
  streamPort = null;
});

Pattern 4 (Storage) — Concurrent Write Races

// Wrong: read-modify-write is a race condition when two tabs do this simultaneously
const s = await StorageManager.get(['demoCounter']);
await StorageManager.set({ demoCounter: s.demoCounter + 1 });

// Right (for correctness): route through background to serialize writes
await chrome.runtime.sendMessage({ action: 'incrementDemoCounter' });
// Background processes these one at a time; no race condition

  6. Question: This is Pattern 1 (fire & forget) from background to content. How would you turn it into Pattern 2 (request/response) so the background collects all tab responses before reporting success?

Summary: The Decision Framework

When you need to move data between extension contexts, ask these questions in order:

  1. Does the sender need a response? No → Pattern 1. Yes → continue.
  2. Is the response a single value, or a stream of values over time? Single → Pattern 2 (with return true). Stream → Pattern 3 (port).
  3. Does multiple receivers need to know about the data simultaneously? Yes → Pattern 4 (storage.onChanged). No → Pattern 1 or 2.
  4. Does the sender live in the page world (no chrome.* access)? Yes → 3-hop relay through content script.

These four patterns are exhaustive. Every inter-context communication in NeuralTab — and in every Chrome extension ever written — is one of these four. Knowing them completely, including their failure modes, their performance characteristics, and their security implications, is the foundation of everything that follows.
