Storage Mastery:
local · sync · session · IndexedDB

Four mechanisms, four different contracts. Understanding which one to reach for — and why the wrong choice silently degrades performance at scale — is what separates extension hobbyists from extension engineers.

Why Four Storage Types?

Chrome gives extension developers four different storage APIs, and they exist because four genuinely different problems require four different solutions. Using chrome.storage.local for everything is like storing both your house keys and your tax returns in the same drawer — it works until the drawer gets too full and you can't find anything.

chrome.storage.local — The Workhorse

chrome.storage.local is available in every extension context: service worker, popup, options page, content script, extension pages. It is the right default for small-to-medium shared state that must survive extension restarts.

The key constraint to internalize: every read deserializes the entire value from the browser's internal storage into JavaScript memory. If you store a 10,000-entry array in a single key and call get('myKey'), Chrome deserializes all 10,000 entries into a JavaScript array, hands it to you, and then you throw most of it away. This is O(n) on every read. At 1,000 entries it is invisible. At 100,000 entries it causes jank.

The correct mitigation: keep individual storage values small. NeuralTab caps `messageLog` at 100 entries and `swLifecycleLog` at 50 entries. If you need to store more, switch to IndexedDB.

The getBytesInUse API

This is the most underused API in the chrome.storage suite. It tells you exactly how much storage you are consuming without deserializing a single value:

// Fast: single IPC call, no deserialization
const used  = await chrome.storage.local.getBytesInUse(null); // null = all keys
const quota = chrome.storage.local.QUOTA_BYTES; // 5242880 (5 MB)
console.log(`Using ${Math.round(used / 1024)} KB of ${Math.round(quota / 1024)} KB`);

NeuralTab's `StorageManager.getQuotaInfo()` wraps this into a rich object with percentage. The popup displays a live quota bar using it. When usage crosses 80%, the heartbeat alarm writes `storageQuotaWarned: true` to storage, which triggers `storage.onChanged` in all open pages — a real-world application of Pattern 4 from Module 06 applied to operational monitoring.

chrome.storage.sync — The Cross-Device Bridge

chrome.storage.sync is seductive. You write to it the same way as `storage.local`, but Chrome automatically synchronizes the data to the user's Google account and makes it available on every device where they're signed in. This sounds like a free feature until you hit the limits.

The constraints are real and enforced:

  • 100 KB total across all sync keys combined
  • 8 KB per individual item — a single key-value pair
  • 512 items maximum
  • 1800 write operations per hour — roughly one every 2 seconds
  • 120 write operations per minute burst

Exceeding these limits causes QUOTA_EXCEEDED errors on writes. Chrome does not queue excess writes — they fail silently unless you check chrome.runtime.lastError.

The correct use case for sync: user preferences that are small, infrequently changed, and genuinely should follow the user across devices. NeuralTab's `theme`, `fontSize`, and `showWordCount` are good candidates. The entire preferences object serializes to under 1 KB — well within limits. The message log, visit history, and operational counters are explicitly wrong for sync.

Never put arrays of unbounded size in storage.sync. A developer who stores the message log in sync will hit the 8 KB per-item limit within minutes of normal usage. Chrome will start silently dropping writes. The user will see their preferences reset on reload. This is not a hypothetical — it is one of the most common extension bugs reported in the Chrome Web Store reviews.

chrome.storage.session — The MV3 Newcomer

chrome.storage.session is MV3-only, available since Chrome 102. It works identically to `storage.local` from an API perspective, but its data is cleared when the browser session ends (close and reopen Chrome). It also fires `storage.onChanged` events, so Pattern 4 works with it.

When session storage is the right tool:

  • Tokens or credentials that must not survive a browser restart (security requirement)
  • Per-session UI state: "user has dismissed this banner this session"
  • Scratch space for in-progress operations in the service worker that the page needs to poll
  • Race-condition-free communication between service worker and extension pages where persistence is undesirable

NeuralTab uses `StorageManager.sessionGet` and `sessionSet` wrappers that gracefully degrade (return empty objects) on Chrome versions before 102 where `chrome.storage.session` does not exist.

IndexedDB — Structured Data at Scale

IndexedDB is a full client-side database engine built into every modern browser. It is not a Chrome extension API — it is the standard Web API that Chrome exposes to extension pages, service workers, and content scripts alike. If you have used it in a web app, the same API works here.

The key concepts:

  • Database: a named, versioned container. NeuralTab uses `neuraltab-history` at version 1.
  • Object store: like a table. The `page_visits` store has a `keyPath: 'id'` (the primary key) and `autoIncrement: true` (IDB assigns IDs automatically).
  • Index: an auxiliary B-tree over a non-key field. The `timestamp` index lets us open a reverse cursor to read visits newest-first. The `domain` index lets us find all visits to a specific domain without scanning every record.
  • Transaction: all reads and writes happen inside a transaction. A `'readonly'` transaction can overlap other reads. A `'readwrite'` transaction is exclusive.
  • Cursor: an iterator over a range of records in key or index order.

The Promise Wrapper Pattern

IDB's native API is callback-based. Every operation returns an `IDBRequest` with an `onsuccess` and `onerror`. Working with raw callbacks in 2025 is painful. NeuralTab's `idb_manager.js` wraps every request in a promise:

// The core wrapper — converts any IDBRequest into a Promise
function idbReq(req) {
  return new Promise((resolve, reject) => {
    req.onsuccess = e => resolve(e.target.result);
    req.onerror   = e => reject(e.target.error);
  });
}

// Usage: await any IDB operation
const count = await idbReq(store.count());
const id    = await idbReq(store.add(visit));

This pattern is standard in production code. Libraries like idb (by Jake Archibald) do the same thing at a larger scale. NeuralTab's `idb_manager.js` is a minimal version built specifically for this module so you understand what those libraries are doing under the hood.

The onupgradeneeded Handler

This is the only place you can create or modify object stores and indexes. It fires when you call `indexedDB.open(name, version)` with a version number higher than the currently stored one. If the database does not exist, it fires with version 0 → 1.

const req = indexedDB.open('neuraltab-history', 1);

req.onupgradeneeded = e => {
  const db    = e.target.result;
  const store = db.createObjectStore('page_visits', {
    keyPath: 'id', autoIncrement: true
  });
  store.createIndex('url',       'url',       { unique: false });
  store.createIndex('timestamp', 'timestamp', { unique: false });
  store.createIndex('domain',    'domain',    { unique: false });
};
// ↑ This runs ONCE (or when you bump the version number)

Module 08 (Update Mechanics) covers schema migrations in depth. The pattern is: bump the version number, check `e.oldVersion` inside `onupgradeneeded`, and run upgrade steps conditionally. NeuralTab's IDB is currently at version 1 with a flat schema — migrations will be the Module 08 teaching tool.

Searching the History with a Cursor

The `searchVisits` function demonstrates the power of IDB indexes. Reading visits newest-first without loading everything:

// Open a cursor on the timestamp index, descending (newest first)
const req = store.index('timestamp').openCursor(null, 'prev');

req.onsuccess = e => {
  const cursor = e.target.result;
  if (!cursor) { /* done */ resolve(); return; }

  const v = cursor.value;
  if (queryMatches(v)) all.push(v);

  cursor.continue(); // advance to next record
};

The `'prev'` direction is the IDB constant for descending order. The cursor visits records from highest timestamp to lowest — newest visits first. This is O(n) over the matching records, not O(n) over all records: if you only need the first 25 matches, you can call `cursor.advance(skip)` to jump forward and `break` when you have enough.

IDB in the service worker: `indexedDB` is available as a global in MV3 service workers. You do not need to import anything — it is part of the Web Workers API baseline. However, if the service worker dies mid-transaction, IDB handles this gracefully: the transaction rolls back automatically. No partial writes survive a service worker death.

Race Conditions in Storage Writes

Every extension developer eventually encounters the read-modify-write race condition. It looks like this:

// Tab A and Tab B both do this at the same time:
const s    = await chrome.storage.local.get('counter'); // both read 5
const next = s.counter + 1;                              // both compute 6
await chrome.storage.local.set({ counter: next });       // both write 6
// Expected: 7. Actual: 6. One increment was lost.

`chrome.storage.local` has no built-in transaction system for read-modify-write operations. If two extension contexts write the same key simultaneously, the last write wins and intermediate writes are lost.

The correct fix: Route all mutating writes through the background service worker, which processes messages sequentially in a single event loop. The background's `incrementDemoCounter` handler is the correct pattern for counters that multiple pages can increment.

IndexedDB transactions handle this correctly. A `'readwrite'` transaction on a store is exclusive — Chrome queues concurrent transactions and runs them one at a time. The increment inside a transaction is always atomic.

Exercise 1 — Inspect the IDB Schema in DevTools
  1. Load the extension. Browse 5-10 pages (any websites).
  2. Open DevTools on any page → Application → Storage → IndexedDB → neuraltab-history (chrome-extension://…) → page_visits.
  3. Observe: Each visited page appears as a record with id, domain, timestamp, title, url, wordCount.
  4. Click the three indexes (domain, timestamp, url) on the left sidebar. See how the same records appear in different sort orders.
  5. Click the "Start" button (cursor icon) next to the timestamp index and set direction to "prev". Observe: records appear newest-first.
  6. Write: Why is the timestamp index faster than sorting the results in JavaScript after reading them all?
Exercise 2 — Hit the storage.sync Quota
  1. Open the DevTools console on any extension page (e.g., the SW Monitor).
  2. Try: await chrome.storage.sync.set({ bigKey: 'x'.repeat(8193) })
  3. Observe: The promise rejects with QUOTA_EXCEEDED. The 8 KB per-item limit is enforced synchronously by Chrome.
  4. Now try: await chrome.storage.sync.set({ smallKey: 'NeuralTab theme' })
  5. Observe: Succeeds immediately. Check it appeared in DevTools → Application → Storage → Extension Storage → Sync.
  6. Write: What would happen if you stored NeuralTab's messageLog (which can reach 100 entries × ~100 bytes = 10 KB) in sync storage instead of local?
Exercise 3 — Add a wordCount Index to the History
  1. Open idb_manager.js. Find the onupgradeneeded handler.
  2. Add store.createIndex('wordCount', 'wordCount', { unique: false });
  3. Important: You must bump the database version from 1 to 2. Change indexedDB.open(DB_NAME, 1) to indexedDB.open(DB_NAME, 2).
  4. Add a migration guard: inside onupgradeneeded, check if (e.oldVersion < 2) before adding the index (so re-installing does not try to create it twice).
  5. Reload the extension. Open DevTools → IndexedDB. The database should now show a wordCount index alongside the existing three.
  6. In history_db.js, add a "Sort by word count" button that opens a cursor on the wordCount index in descending order and shows the 10 longest pages you have visited.
Exercise 4 — Reproduce the Read-Modify-Write Race
  1. Open the Message Lab in two tabs side by side.
  2. In both DevTools consoles, paste and run simultaneously (use two fingers on both Enter keys):
    const s = await StorageManager.get(['demoCounter']); await StorageManager.set({ demoCounter: (s.demoCounter || 0) + 1 });
  3. Observe: The counter may increment by only 1 even though you ran two increments. One write was lost.
  4. Now in both consoles, use the routed version: await chrome.runtime.sendMessage({ action: 'incrementDemoCounter' })
  5. Observe: Counter increments by 2 reliably. The background serializes the writes.
  6. Write: Why does the background approach prevent the race even though JavaScript is single-threaded?
Exercise 5 — Monitor Quota Growth in Real Time
  1. Open the Options page → Storage tab. Note the current quota usage percentage.
  2. Open the Message Lab. Send 50 fire-and-forget messages rapidly (keep clicking "Send One-Way").
  3. Switch back to Options → Storage tab, click Refresh.
  4. Observe: The quota bar has grown slightly. Each message log entry is ~80-100 bytes.
  5. Calculate: at 100 entries maximum × 100 bytes = 10 KB. At 5 MB total storage = 0.2% of quota. The cap is doing its job.
  6. Thought experiment: If you removed the 100-entry cap from StorageManager.logMessage(), how many messages would it take to fill 5 MB? At 100 bytes/message: 50,000 messages. How long would that take at one message per second? 13 hours. How long at 10 per second (a streaming page)? 83 minutes. The cap matters.
