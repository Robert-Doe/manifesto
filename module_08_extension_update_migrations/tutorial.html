Extension Update Mechanics:
Graceful Schema Migration

Your users are not all on the same version. Some installed last week. Some installed two years ago and never updated. When your extension ships a new version, every user's storage is in a different state. Migration is how you make "it just works" into a guarantee, not a hope.

The Problem: Your Data Lives in Their Browser

Here is a scenario every serious extension developer eventually faces. You ship version 0.7.0. Users install it. Version 0.7.0 stores history visits in IndexedDB with three indexes: `url`, `timestamp`, `domain`. A month later you ship 0.8.0, which adds a fourth index: `wordCount`. You also rename the `bookmarkFolderName` storage key to `savedFolder`.

What happens to existing users when they update? Their storage has the old schema. The old IndexedDB has three indexes. The old `chrome.storage.local` has the old key name. Your new code reads `savedFolder`, gets `undefined`, crashes.

There are three bad ways to handle this:

  • Ignore it: hope the new defaults kick in and users reset their data. Some do; most notice their settings disappeared and leave a 1-star review.
  • Delete everything: wipe storage on update. Correct behavior, guaranteed loss of user data.
  • Conditional code everywhere: every read checks "is this the old format or the new format?" The codebase becomes a graveyard of compatibility shims.

The correct approach: run migrations once at update time, bring all storage to the current schema, and let the rest of the code assume the current schema always exists.

The Three Lifecycle Events

Chrome gives you three distinct entry points for extension lifecycle management:

EventWhen it firespreviousVersionWhat to do
onInstalled (install)First install onlyundefinedSet all defaults. Run all migrations from scratch.
onInstalled (update)Extension version changedThe old version stringRun only new migrations.
onInstalled (chrome_update)Chrome itself updatedundefinedLog it. Do nothing to storage.
onStartupBrowser startsN/ASession-level setup only. Never run migrations here.

Never run migrations in onStartup. `onStartup` fires on every browser launch, every time — even when nothing has changed. Migrations must run at most once. `onInstalled` has the version context to know which migrations are needed. `onStartup` does not.

The Handler

// background.js — the correct structure
chrome.runtime.onInstalled.addListener(async ({ reason, previousVersion }) => {
  const currentVersion = chrome.runtime.getManifest().version;

  if (reason === 'install') {
    // Fresh install: run ALL migrations from null → currentVersion
    await MigrationManager.run(null, currentVersion);

  } else if (reason === 'update') {
    // Update: run only migrations between previousVersion and currentVersion
    await MigrationManager.run(previousVersion, currentVersion);

  } else if (reason === 'chrome_update') {
    // Chrome updated but extension did not — schema unchanged
    await StorageManager.logSwEvent('chrome_update', 'Chrome updated');
  }
});

The Migration Runner

NeuralTab's `MigrationManager` is a deterministic version-keyed runner. The design has four properties:

  1. Ordered: migrations run in version sort order, not insertion order.
  2. Filtered: only migrations between `previousVersion` and `currentVersion` run.
  3. Idempotent: each migration checks whether its keys already exist before writing. Running twice produces the same result as running once.
  4. Logged: every run (success or failure) is appended to `migrationLog` in storage. You can inspect the history in the Update Log page.
const MIGRATIONS = {

  '0.7.0': async (storage) => {
    // Idempotency check: only write if keys are missing
    if (!storage.historyVisitCount)
      await StorageManager.set({ historyVisitCount: 0, historyEnabled: true });
  },

  '0.8.0': async (storage) => {
    if (!storage.migrationLog)
      await StorageManager.set({ migrationLog: [], schemaVersion: '0.8.0' });
  }
};

Version Comparison

Comparing version strings correctly is non-obvious. The string `'0.10.0'` sorts before `'0.9.0'` lexicographically because `'1' < '9'`. This is wrong for version ordering. NeuralTab uses a 3-component numeric comparator:

function compareVersions(a, b) {
  const pa = a.split('.').map(Number);
  const pb = b.split('.').map(Number);
  for (let i = 0; i < 3; i++) {
    if (pa[i] > pb[i]) return  1;
    if (pa[i] < pb[i]) return -1;
  }
  return 0;
}

compareVersions('0.10.0', '0.9.0'); // → 1 (correct: 10 > 9)
compareVersions('0.9.0',  '0.10.0'); // → -1
compareVersions('0.8.0',  '0.8.0');  // → 0

IndexedDB Schema Migrations

IndexedDB has its own migration mechanism, separate from `chrome.storage`. The `onupgradeneeded` callback fires when you open the database with a higher version number. This is where you add indexes, rename stores, or restructure records.

const req = indexedDB.open('neuraltab-history', 2); // bump from 1 → 2

req.onupgradeneeded = e => {
  const db    = e.target.result;
  const store = e.target.transaction.objectStore('page_visits');

  // Guard: only create index if upgrading from a version that lacks it
  if (e.oldVersion < 2) {
    // e.oldVersion = 0 means fresh install (no previous DB)
    // e.oldVersion = 1 means upgrading from DB version 1
    store.createIndex('wordCount', 'wordCount', { unique: false });
  }
};

IDB version vs extension version: These are completely separate numbers. The IDB version is an integer that you control in `indexedDB.open(name, version)`. The extension version is the semver string in `manifest.json`. You can bump the IDB version independently of the extension version — they have no automatic relationship. NeuralTab's convention: bump the IDB version whenever you add or change an object store or index, and document it in `migration_manager.js` as part of the corresponding extension version migration.

Exercise 1 — See onInstalled Fire
  1. Load the extension. Open the SW Monitor.
  2. Open chrome://extensions. Click the reload icon on NeuralTab.
  3. Switch back to the SW Monitor (refresh it).
  4. Observe: There is no onInstalled event in the lifecycle log. Reloading in dev mode fires onStartup, not onInstalled.
  5. Now go to chrome://extensions, remove NeuralTab, then re-load unpacked from the module_08/dist folder.
  6. Observe: The lifecycle log now shows onInstalled reason=install followed by migrations. The Update Log page shows all migration entries.
Exercise 2 — Simulate a Version Skip
  1. Open the Update Log page (popup → Options → SW section → Open Monitor, or direct navigation to the extension's update_log.html).
  2. Click "Simulate Update from 0.5.0".
  3. Observe: The migration history shows 0.6.0, 0.7.0, and 0.8.0 migrations were run (in that order).
  4. Click the button again.
  5. Observe: The response says "none (already applied)". The alreadyRan check in the migration runner prevents double-execution.
  6. Write: What would happen if you removed the alreadyRan guard and clicked the button a third time? Which migrations are idempotent and which are not?
Exercise 3 — Write a Data-Transforming Migration
  1. Imagine NeuralTab 0.9.0 renames demoCounter to pubSubCounter. Write a migration for '0.9.0'.
  2. The migration must: read the current value of demoCounter, write it to pubSubCounter, then delete demoCounter.
  3. Make it idempotent: if pubSubCounter already exists, skip the migration (user already upgraded or fresh install ran this migration).
  4. Add the migration to migration_manager.js. Bump manifest.json version to 0.9.0.
  5. Simulate the update. Verify in DevTools → Application → Extension Storage → Local that demoCounter is gone and pubSubCounter has the old value.
