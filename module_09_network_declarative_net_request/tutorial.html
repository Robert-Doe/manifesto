Network Layer:
declarativeNetRequest & webNavigation

Every HTTP request your browser makes passes through a pipeline. Extensions can intercept that pipeline — blocking ads, redirecting URLs, injecting headers — without running a single line of JavaScript at intercept time. This is the architecture that makes ad blockers possible in MV3.

The Request Lifecycle

When you type a URL and press Enter, or when a page loads a script tag, Chrome's networking stack processes the request through a series of stages. Extensions can observe or modify requests at specific checkpoints:

StageAPICan block?Can modify?
Before navigation startswebNavigation.onBeforeNavigateNoNo (observe only)
Before request sentdeclarativeNetRequestYesYes (headers, redirect)
Before request sent (legacy)webRequest.onBeforeRequest (blocking)MV2 onlyMV2 only
Response headers receivedwebRequest.onHeadersReceivedObserve MV3MV2 blocking only
Navigation committedwebNavigation.onCommittedNoNo
DOM readywebNavigation.onDOMContentLoadedNoNo
Navigation completewebNavigation.onCompletedNoNo

The key shift from MV2 to MV3: blocking `webRequest` was removed. Everything that needs to modify or block a request must now use `declarativeNetRequest`. The observation APIs (`webNavigation`, non-blocking `webRequest`) still exist.

declarativeNetRequest — How It Works

DNR rules are not JavaScript. They are JSON objects that describe matching conditions and actions. Chrome's C++ networking engine reads them and applies them without starting your service worker, without any IPC latency, without running any of your code.

This is architecturally significant: an extension using only DNR rules can block millions of requests per hour without waking its service worker even once. The service worker's idle timer is never reset. This is why MV3 extensions can have much better battery and memory profiles than MV2 extensions that used blocking `webRequest`.

Rule Anatomy

{
  "id": 1,           // unique integer per ruleset, 1-indexed
  "priority": 1,    // higher number = higher priority when rules conflict
  "action": {
    "type": "block"  // block | redirect | modifyHeaders | allow | allowAllRequests
  },
  "condition": {
    "urlFilter": "||doubleclick.net^",
    "resourceTypes": ["script", "image", "xmlhttprequest"]
  }
}

The `urlFilter` syntax comes from uBlock Origin / Adblock Plus filter syntax, adopted directly by the DNR spec:

  • ||example.com^ — matches any URL whose domain is example.com or a subdomain. The `||` anchors to the domain start; `^` is a separator character (slash, query start, etc.).
  • *example* — wildcard matches anywhere in the URL.
  • |https://| — anchors to the literal start of the URL.
  • /tracking.js — matches the path component.

The Five Action Types

ActionWhat it doesCommon use
blockNetwork error returned to requesterAd blocking, tracker blocking
redirectSends browser to a different URLForced HTTPS, privacy-respecting search
modifyHeadersAdd/set/remove request or response headersCORS bypass (dev), custom auth headers
allowExplicitly allow — overrides lower-priority blocksAllow-listing specific resources
allowAllRequestsAllow all sub-requests from a document or frameWhite-list entire domains

Static vs Dynamic Rules

// Static rules: declared in manifest.json, loaded from dnr_rules.json
// Evaluated at install time. No runtime code needed.
// Quota: up to 30,000 rules per extension

// Dynamic rules: managed via API at runtime
await chrome.declarativeNetRequest.updateDynamicRules({
  addRules: [{
    id: 100, priority: 1,
    action: { type: 'block' },
    condition: { urlFilter: '||tracker.example.com^', resourceTypes: ['script'] }
  }],
  removeRuleIds: [99] // remove old rule if it exists
});
// Dynamic rules quota: 5,000 rules. Survive extension updates.

// Session rules: cleared on browser restart
await chrome.declarativeNetRequest.updateSessionRules({ addRules: [...] });
// Session rules quota: 5,000. Use for per-session overrides.

Priority and Conflict Resolution

Multiple rules can match the same request. Chrome resolves conflicts using priority + action precedence:

// Priority 3 allow beats priority 1 block — user's allow-list wins
{ id: 1, priority: 1, action: { type: 'block'  }, condition: { urlFilter: '||ads.com^' } }
{ id: 2, priority: 3, action: { type: 'allow'  }, condition: { urlFilter: '||ads.com/cdn^' } }
// Result: ads.com/cdn/* is allowed; all other ads.com/* is blocked

// If priorities are equal, Chrome uses action precedence:
// allow > allowAllRequests > block > redirect > modifyHeaders

The modifyHeaders action does not apply to cross-origin response headers. You can modify request headers (what you send) and same-origin response headers. Modifying Cross-Origin response headers (e.g., adding CORS headers to a third-party API) requires the `declarativeNetRequestWithHostAccess` permission and host permissions for the target origin.

webNavigation — Observation Without Blocking

While DNR handles interception, `chrome.webNavigation` handles observation. It fires events at each stage of the browser's navigation lifecycle. NeuralTab uses three of them:

// Fires when a navigation is about to begin (before any network request)
chrome.webNavigation.onBeforeNavigate.addListener(details => {
  if (details.frameId === 0) // main frame only — excludes iframes
    logNetworkEvent('beforenavigate', details.url);
});

// Fires when navigation is committed (page starts loading)
chrome.webNavigation.onCommitted.addListener(details => { /* ... */ });

// Fires when navigation is fully complete (all resources loaded)
chrome.webNavigation.onCompleted.addListener(details => { /* ... */ });

// Fires when navigation fails (network error, block, etc.)
chrome.webNavigation.onErrorOccurred.addListener(details => { /* ... */ });

The `details` object contains: `tabId`, `frameId`, `url`, `timeStamp`, `transitionType` (link/typed/auto_subframe/etc.), and `transitionQualifiers`.

NeuralTab stores navigation events in `chrome.storage.local` (capped at 500) and displays them in the Network Monitor via `storage.onChanged`. This is the same Pattern 4 (storage pub/sub) from Module 06, applied to network telemetry.

Testing DNR Rules

Unlike JavaScript code that you can set breakpoints in, DNR rules are opaque — when they fire, nothing in your JavaScript context runs. Testing requires external tools:

# In Chrome DevTools → Network tab:
# Filter by "blocked" to see requests killed by DNR
# Right-click a request → "View request details" shows which rule ID blocked it

# chrome://net-internals/#events shows raw DNR rule matches

# In the extension's background console:
const matched = await chrome.declarativeNetRequest.testMatchOutcome({
  url:          'https://doubleclick.net/ad.js',
  initiator:    'https://example.com',
  type:         'script',
  tabId:        chrome.tabs.TAB_ID_NONE,
  frameId:      chrome.tabs.TAB_ID_NONE
});
// Returns: { matchedRule: { ruleId: 1, rulesetId: 'neuraltab_rules' } }

declarativeNetRequestFeedback permission: Required to use `testMatchOutcome()` and to get rule match information via `onRuleMatchedDebug`. This is a developer-facing permission — the Chrome Web Store displays a warning to users if your published extension includes it. Remove it from production builds and only use it during development.

Exercise 1 — Watch a Block in Action
  1. Load the extension. Open the Network Monitor (popup → Network button, or direct URL).
  2. Navigate to any major news site (nytimes.com, theguardian.com, etc.).
  3. Open the Network Monitor. Observe: The beforenavigate event appears immediately when you click a link, before the page loads.
  4. Open DevTools on the news site → Network tab → filter by "blocked". Observe: Requests to doubleclick.net appear with a red blocked status.
  5. In the DevTools Network tab, right-click one blocked request → "View matching extension rules". Chrome shows which rule ID matched.
Exercise 2 — Add a Custom Block Rule
  1. Open dnr_rules.json. Add a rule with id=6 that blocks all requests to ||facebook.com/tr (Facebook tracking pixel).
  2. Rebuild and reload the extension.
  3. In the background console, call: chrome.declarativeNetRequest.testMatchOutcome({ url: 'https://www.facebook.com/tr?id=123', type: 'image', initiator: 'https://example.com', tabId: -1, frameId: -1 })
  4. Observe: The response shows matchedRule: { ruleId: 6, rulesetId: 'neuraltab_rules' }.
  5. Thought experiment: Why does the Facebook tracking pixel appear on thousands of websites that have nothing to do with Facebook? What are they tracking?
Exercise 3 — Dynamic Rule via Console
  1. Open the extension's background service worker console (chrome://extensions → NeuralTab → Inspect Views: service worker).
  2. Run: await chrome.declarativeNetRequest.updateDynamicRules({ addRules: [{ id: 100, priority: 1, action: { type: 'block' }, condition: { urlFilter: '||twitter.com/i/api^', resourceTypes: ['xmlhttprequest'] } }] })
  3. Navigate to twitter.com. Observe: The timeline fails to load. API calls to twitter.com/i/api/* are blocked.
  4. Remove the rule: await chrome.declarativeNetRequest.updateDynamicRules({ removeRuleIds: [100] })
  5. Reload twitter.com. Observe: Timeline loads again.
  6. Write: What is the difference between a dynamic rule you just added and the static rules in dnr_rules.json? Which survives an extension update? Which survives a browser restart?
