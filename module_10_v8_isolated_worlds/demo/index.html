Module 10 — V8 Isolated Worlds

Two separate V8 heaps. One shared DOM. The most misunderstood part of Chrome extension architecture.

The Mental Model

Isolated World
chrome.* API: ✅
page window vars: ❌
own window.x = 1 → private
document.title: ✅ (shared DOM)
⬌
MAIN World (page)
chrome.* API: ❌
page window vars: ✅
window.__secret readable
document.title: ✅ (shared DOM)
📄 document (DOM) — shared between both worlds

Crossing the Boundary

// Execute in page's JavaScript heap from extension background
await chrome.scripting.executeScript({
  target: { tabId },
  world: 'MAIN',   // ← key: enter page's V8 context
  func: () => window.__pageSecret
});

// Content scripts run in ISOLATED world automatically
// No chrome.scripting needed — just write your content.js

Why Isolation Matters

Imagine a page that does Array.prototype.push = () => null before your content script loads. Without isolation, your extension code calling arr.push(x) would silently do nothing. With isolation, your content script's Array.prototype is untouched — it lives in a different heap.

This is why Chrome chose isolation: extension code should not be corruptible by page content. Crossing to MAIN world (via executeScript) is an explicit, auditable escalation — not the default.

The Closure Trap

// ❌ WRONG — closure variable `myData` is NOT captured
const myData = { secret: 'abc' };
chrome.scripting.executeScript({
  target: { tabId },
  func: () => console.log(myData)  // ReferenceError in page context
});

// ✅ CORRECT — pass data via `args`
chrome.scripting.executeScript({
  target: { tabId },
  func: (data) => console.log(data),
  args: [myData]
});

The function is serialized to its source text and re-evaluated in a different V8 context. Closures don't survive serialization. Always use args for data.
