The Most Misunderstood Feature in Extension Development

Every experienced Chrome extension developer has hit this bug: their content script tries to call a function defined by the page, or read a variable the page set on window, and gets undefined. The code looks right. The page clearly has the variable. The console shows it. But the extension cannot see it.

The reason is isolated worlds — one of Chrome's most important and least understood architectural decisions. This module will give you a complete mental model so you never hit this surprise again.

V8 Contexts and Heaps

V8, Chrome's JavaScript engine, runs code inside contexts. Each context has its own JavaScript heap — its own set of global objects, its own window, its own prototype chain. When you assign window.foo = 1, that assignment is local to the current context's heap. Other contexts cannot see it.

Chrome runs multiple V8 contexts per tab:

  • The page context — runs the website's own JavaScript. Called the MAIN world.
  • One or more extension contexts — run content scripts. Called isolated worlds. Each extension gets its own.

Both contexts point at the same DOM tree. document.getElementById('foo') returns the same element from both worlds. But window.myVar in the page context and window.myVar in the isolated world are in different heaps — completely separate objects.

Key Mental Model

Think of the DOM as a database that both worlds can read and write. The JavaScript heap is a local variable store that neither world can access from the other. DOM: shared. JS variables: private to each world.

Why Chrome Built Isolation

The fundamental threat model: a page might be malicious, or might be running third-party scripts that have been compromised. If extension content scripts shared a heap with the page, an attacker could poison the environment before the extension runs:

// Malicious page code — runs before content script
Object.defineProperty(Array.prototype, 'push', {
  value: function() { sendDataToAttacker(this); }
});
// Now every array.push() in the extension leaks data to the attacker

With isolation, the extension's Array.prototype is in a different heap and cannot be affected. The extension's code is safe from page-level prototype pollution, redefined globals, or overridden built-ins.

The secondary benefit: extensions cannot accidentally break page behavior by setting window.onload or redefining global functions. Isolation is a two-way protection.

Crossing the Boundary: chrome.scripting.executeScript

The deliberate escape hatch is chrome.scripting.executeScript with the world parameter. This runs a function in the target world of a specific tab, from your background service worker:

// From background.js — inject into page's JS heap
const results = await chrome.scripting.executeScript({
  target: { tabId: someTabId },
  world: 'MAIN',          // ← enter page context
  func: () => {
    return window.__pageSecret;   // can read page variables
  }
});
const value = results[0].result;  // returned to background

You can also inject into world: 'ISOLATED' to add code to your extension's context dynamically — useful for injecting helper libraries after the fact.

The Closure Trap (Memorize This)

This is the mistake every developer makes exactly once:

// ❌ WRONG — closures don't work across serialization
const userId = '12345';
chrome.scripting.executeScript({
  target: { tabId },
  func: () => console.log(userId)  // ReferenceError: userId not defined
});

The func is serialized to its source code text, sent to the target tab, and re-evaluated. The closure binding to userId does not survive this process. The function arrives in the target context as a standalone function with no access to the outer scope.

// ✅ CORRECT — use args for data
chrome.scripting.executeScript({
  target: { tabId },
  func: (id) => console.log(id),   // parameter, not closure
  args: ['12345']                  // serialized and passed explicitly
});

args are JSON-serialized and passed as function parameters. They survive the round-trip because they're explicit data, not implicit scope.

world: 'MAIN' Without chrome.scripting

In your manifest, you can declare content scripts to run in MAIN world directly:

{
  "content_scripts": [{
    "matches": ["<all_urls>"],
    "js": ["inject.js"],
    "world": "MAIN"      // ← runs in page heap, no chrome.* access
  }]
}

Use this when you need to hook page functions (intercept fetch, wrap XMLHttpRequest, observe framework internals) but don't need chrome APIs. The tradeoff: no extension API access, meaning your injected script must communicate back to the isolated world via DOM events or window.postMessage.

Security Warning

Code running in MAIN world is fully exposed to the page. A compromised page can call your functions, overwrite your variables, and intercept your DOM events. Never put sensitive logic (auth tokens, user data, extension secrets) in MAIN world scripts.

The Messaging Bridge Pattern

The most robust architecture when you need data from the page heap inside your extension:

// inject.js — runs in MAIN world (no chrome.* access)
window.addEventListener('message', e => {
  if (e.data.type !== 'NEURALTAB_REQUEST') return;
  const data = window.__frameworkState;   // reads page variable
  window.postMessage({ type: 'NEURALTAB_RESPONSE', data }, '*');
});

// content.js — runs in ISOLATED world
window.postMessage({ type: 'NEURALTAB_REQUEST' }, '*');
window.addEventListener('message', e => {
  if (e.data.type !== 'NEURALTAB_RESPONSE') return;
  chrome.runtime.sendMessage({ type: 'pageData', data: e.data.data });
});

// background.js
chrome.runtime.onMessage.addListener((msg) => {
  if (msg.type === 'pageData') {
    // msg.data came from page heap, safely bridged to extension
  }
});

The DOM event system is the shared communication bus between worlds. Both worlds can dispatch and listen to DOM events — they're part of the shared DOM, not the private heap.

Exercise 10-B — DOM Proof

From the World Demo, click "Read document.title" in the ISOLATED panel. Then set a new page title from MAIN world (document.title = 'HACKED') and read it again from ISOLATED. Confirm both worlds see the same DOM mutation. This is the proof that DOM is shared.

Exercise 10-C — Fix the Closure Bug

In world_demo.js, execInWorld uses new Function('return ' + code). This works for simple expressions but is a code injection risk in production. Refactor it to accept a static function and an args array instead. Keep the same UI but replace the dynamic string approach with typed functions for each specific button action.

Exercise 10-D — The Bridge

Build a minimal bridge: add a MAIN-world content script declaration to the manifest for assets/inject.js. In that file, listen for window.postMessage({ type: 'PING' }) and respond with the current window.location.href (which the isolated world could also read, but this demonstrates the pattern). In content.js, send the PING and log the response. Verify it works by checking the console on any page.
