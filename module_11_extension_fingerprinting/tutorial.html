Module 11 — Extension Fingerprinting

NeuralTab Curriculum · Module 11 of 25

Your Extension Has a Fingerprint

Every installed Chrome extension leaks information about itself to any page that knows how to look. The mechanism is simple: web_accessible_resources. Any file listed there can be fetched by any web page using the extension's ID in the URL. If the fetch succeeds, the page knows the extension is installed.

// Any page can probe your extension:
const img = new Image();
img.onload  = () => console.log('Extension installed!');
img.onerror = () => console.log('Not installed');
img.src = 'chrome-extension://abcdefghijklmnopqrstuvwxyzabcdef/icon.png';

NeuralTab exposes 14+ files in WAR. Each one is a data point a fingerprinter can use. Security-conscious users and anti-fingerprinting tools watch for exactly this pattern.

What the Extension ID Reveals

Unpacked extensions get a random ID that changes on reinstall. But published extensions have a permanent ID tied to the signing key used for the first CWS upload. This ID never changes. Any page can hardcode it and probe reliably. Privacy extensions like uBlock Origin are fingerprinted this way by ad-tech companies tracking their own blockers.

The chrome.runtime.id Exposure

Content scripts can read chrome.runtime.id — the extension's own ID. This is intentional. But it means any page that successfully communicates with your content script via window.postMessage can learn your extension's ID. From there, WAR probing is trivial.

API Availability as a Capability Map

The fingerprint.html page probes API availability: !!chrome.debugger, !!chrome.sidePanel, !!chrome.storage?.session. These aren't just detection — they're a capability map that tells you exactly which Chrome version and manifest features are available at runtime. This same technique is how you implement graceful degradation.

The Detectability Score

NeuralTab calculates a stealth score: 100 points minus penalties for WAR count and sensitive permissions. It's a teaching metaphor, not a security audit. The real lesson: every WAR entry is a public API. Add them only when genuinely required.

Key Insight

The minimum viable WAR list for NeuralTab is just assets/inject.js — the MAIN-world injection script. Everything else (the HTML pages) is opened via chrome.tabs.create and doesn't need WAR listing. Reducing WAR entries is a privacy improvement with zero feature cost.

Storage as a Behavioral Fingerprint

getBytesInUse(null) combined with swInstallTime reveals: how long the extension has been installed and how actively it's been used. A brand-new install has near-zero bytes. A year-old install with heavy history usage has 1-5MB. This behavioral fingerprint is useful for onboarding flows (detect first-time users) and abuse detection (detect automated test installs).

Open NeuralTab's manifest.json. Remove every entry from web_accessible_resources except assets/inject.js. Reload the extension. Which features break? Which features still work? Document which pages need WAR vs. which are opened via chrome.tabs.create and therefore don't.

Exercise 11-B — Probe Your Own Extension

Open any web page's DevTools console. Type the probe code from the top of this tutorial, substituting NeuralTab's extension ID (visible at chrome://extensions). Confirm the probe succeeds for files in WAR and fails for files not in WAR.

Exercise 11-C — Add a New Probe

Add a probe to fingerprint.js that checks whether chrome.storage.session is available AND whether chrome.sidePanel is available AND derives the minimum Chrome version from the combination. Chrome 116+ has both; 114-115 has sidePanel but no session; below 114 has neither.
