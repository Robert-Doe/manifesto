Why Extensions Need Their Own OAuth Flow

Web apps use the OAuth2 authorization code flow with a backend server that holds the client secret. Extensions have no backend — they're entirely client-side. Chrome provides chrome.identity.launchWebAuthFlow specifically for this: it opens a popup browser window to the OAuth provider, captures the redirect, and returns the token URL to your extension without any server involvement.

The chromiumapp.org Redirect

The key to the extension OAuth flow is the redirect URI: https://<ext-id>.chromiumapp.org/. Chrome intercepts any redirect to this domain and returns the full URL (including token in the fragment) to launchWebAuthFlow. The extension ID in the subdomain ensures that only the specific extension can receive that redirect — it's cryptographically bound to the signing key.

// The redirect URI Chrome will intercept:
const REDIRECT = `https://${chrome.runtime.id}.chromiumapp.org/`;

// Google sees this as a valid registered redirect URI
// Chrome intercepts the redirect — your server never sees it
const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?` +
  `client_id=CLIENT_ID&redirect_uri=${encodeURIComponent(REDIRECT)}&` +
  `response_type=token&scope=email+profile`;

Parsing the Token from the Redirect

Google's implicit flow puts the access token in the URL fragment: https://abc123.chromiumapp.org/#access_token=ya29.xxx&token_type=Bearer&expires_in=3599. Your extension must parse this from the redirect URL that launchWebAuthFlow returns.

const redirectUrl = await chrome.identity.launchWebAuthFlow({
  url: buildAuthUrl(),
  interactive: true   // show popup to user
});
// redirectUrl = "https://ABC.chromiumapp.org/#access_token=ya29...&..."
const token = new URL(redirectUrl).hash
  .slice(1)                              // remove leading #
  .split('&')
  .find(p => p.startsWith('access_token='))
  ?.split('=')[1];

Token Storage Strategy

Tokens go in chrome.storage.local — never sync. Tokens are device-bound sessions. Syncing them across devices creates a situation where revoking on one device leaves stale tokens on others, causing mysterious 401 failures.

Handling Expiration

Google access tokens expire after 3600 seconds. The cleanest handling: treat every 401 response as an expiration signal, clear the stored token, and re-run the login flow. With interactive: false, Chrome will re-authenticate silently if the user has an active Google session — no popup, instant new token.

Security Note

Never log or transmit access tokens. They're bearer tokens — whoever holds one can call the API as the user. Store them only in chrome.storage.local, which is not accessible to web pages or other extensions.

Exercise 12-A — Complete the Setup

Follow the demo page's setup instructions: create a Google Cloud project, enable the People API, create OAuth2 Web Application credentials, add the chromiumapp.org redirect URI, and replace the CLIENT_ID placeholder in auth_manager.js. Complete a full login flow and verify the userinfo endpoint returns your email address.

Exercise 12-B — Add Silent Re-auth

Modify AuthManager.callAPI() to attempt launchWebAuthFlow({ interactive: false }) on a 401 before falling back to interactive: true. This gives users a seamless re-auth experience when their token expires overnight.

Exercise 12-C — Cache User Info

Add a cachedUserInfo function that stores the getUserInfo() response in chrome.storage.session with a 5-minute TTL. The popup should show the user's name and avatar without making a network request on every open.
