Module 13 — WebAssembly in Extensions

NeuralTab Curriculum · Module 13 of 25

Why Wasm in an Extension?

Chrome extensions run JavaScript — always. But JavaScript has performance limits, particularly for CPU-intensive work: cryptography, compression, image processing, signal processing, or running code originally written in C/C++/Rust. WebAssembly bridges this gap: compile native code to a binary format that V8 executes near-natively, without sacrificing the extension sandbox.

The CSP Exception for Binary Wasm

MV3 extension pages have a strict Content Security Policy that blocks eval(), new Function(string), and remote script loading. This might seem like it would block WebAssembly compilation too — after all, you're generating executable code at runtime. But the CSP spec carves out an explicit exception: compiling a binary buffer is not "dynamic code generation from strings." WebAssembly.instantiate(buffer) is allowed everywhere, including MV3 service workers.

// ❌ Blocked by MV3 CSP:
eval("function add(a,b){return a+b}");
new Function('a', 'b', 'return a + b');

// ✅ Allowed by MV3 CSP:
const wasmBytes = new Uint8Array([0x00, 0x61, 0x73, 0x6d, ...]);
const { instance } = await WebAssembly.instantiate(wasmBytes.buffer);
instance.exports.fibonacci(40);  // fast!

Three Ways to Load a Wasm Module

1. Inline Binary (small modules only)

Embed the .wasm bytes as a Uint8Array literal in a .js file. Works well under ~2KB. No extra file, no fetch needed. Used in wasm_runner.js for the fibonacci module.

2. Fetch from Extension URL

const url = chrome.runtime.getURL('assets/neuraltab.wasm');
const response = await fetch(url);
const buffer = await response.arrayBuffer();
const { instance } = await WebAssembly.instantiate(buffer);

List the .wasm file in web_accessible_resources if it needs to be loaded from content scripts or web pages. For background SW only, WAR is not required.

3. instantiateStreaming (fastest, for fetched files)

const { instance } = await WebAssembly.instantiateStreaming(
  fetch(chrome.runtime.getURL('assets/module.wasm'))
);
// Compiles while streaming — faster than fetch → arrayBuffer → instantiate

Caching Across SW Restarts

Wasm compilation is expensive for large modules. Since service workers restart frequently in MV3, avoid recompiling on every restart. Cache the compiled WebAssembly.Module in the Cache API:

const CACHE_NAME = 'neuraltab-wasm-v1';
async function getWasmModule(url) {
  const cache = await caches.open(CACHE_NAME);
  let response = await cache.match(url);
  if (!response) {
    response = await fetch(url);
    await cache.put(url, response.clone());
  }
  const buffer = await response.arrayBuffer();
  return WebAssembly.compile(buffer);   // returns Module (not instance)
}
// Then instantiate from the cached module (fast):
const instance = await WebAssembly.instantiate(cachedModule);

Exercise 13-A — Verify the CSP

Open the wasm_demo.html page from NeuralTab. Click "Run Benchmark" with n=40. Verify in DevTools → Console that there are no CSP violations. Then try adding eval("1+1") to wasm_runner.js and confirm it throws a CSP error. This proves Wasm is in a different category than eval.

Exercise 13-B — Iterative vs. Recursive

Add an iterative fibonacci function to wasm_runner.js and the WAT source. Compare: recursive Wasm vs. iterative Wasm vs. recursive JS vs. iterative JS. The iterative versions should be orders of magnitude faster. What does this tell you about the value of Wasm for well-written algorithms?
