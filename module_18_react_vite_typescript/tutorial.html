Why a Build Pipeline?

Vanilla JS extensions are fine up to a point. At some point your popup has 30 conditional renders, your background.js is 800 lines, and you're copying string template IDs between files hoping they match. TypeScript catches the mismatch at compile time. React turns the popup into a component tree instead of a DOM mutation soup. Vite makes the build instant — typically under a second for a full rebuild.

The tradeoff: a build step means the files Chrome loads are generated, not the files you edit. The dist/ directory is what gets packed and submitted to CWS. Never submit the src/ directory.

vite-plugin-web-extension

Standard Vite doesn't know what a manifest.json is. The vite-plugin-web-extension plugin reads your manifest and builds each entry point (popup, background, content scripts, options page) as separate Vite entry bundles. It handles the quirks: background service workers get their own chunk, content scripts don't get HMR (because that would require eval), and web_accessible_resources are copied as-is.

// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import webExtension from 'vite-plugin-web-extension';

export default defineConfig({
  plugins: [
    react(),
    webExtension({
      manifest: () => require('./manifest.json'),
    }),
  ],
  build: {
    outDir: 'dist',
    sourcemap: false,         // no source maps in production build
    minify: 'terser',
    rollupOptions: {
      output: {
        entryFileNames: '[name].js',   // predictable output names
      },
    },
  },
});

TypeScript for chrome.*

The @types/chrome package provides TypeScript definitions for all Chrome extension APIs. With this package installed and "types": ["chrome"] in tsconfig.json, you get autocomplete and type-checking for every chrome.* call. Typos in method names, wrong parameter shapes, and missing required fields all become compile-time errors instead of runtime surprises.

// TypeScript catches this at compile time:
const tabs = await chrome.tabs.query({ active: true, currentWindow: true });
//   ^-- Tab[] — TypeScript knows the return type

tabs[0].url;   // string | undefined — URL may not be available without "tabs" permission
//          ^-- TypeScript reminds you to check for undefined

Service Worker: type:module vs type:classic

MV3 background service workers can be declared as "type": "module" in the manifest. Module workers support import statements at the top level — you can split your background into multiple files and import them. However, module workers cannot use importScripts(). If any of your dependencies use importScripts (some older polyfills do), you must stay with classic SW.

// manifest.json:
"background": {
  "service_worker": "dist/background.js",
  "type": "module"   // enables ESM imports, disables importScripts
}

// src/background.ts (module style):
import { StorageManager } from './storage_manager';
import { handleMessage } from './message_router';
chrome.runtime.onMessage.addListener(handleMessage);

React in the Popup

// src/popup/Popup.tsx
import { useEffect, useState } from 'react';

export default function Popup() {
  const [tab, setTab] = useState<chrome.tabs.Tab | null>(null);

  useEffect(() => {
    chrome.tabs.query({ active: true, currentWindow: true })
      .then(([tab]) => setTab(tab ?? null));
  }, []);

  return (
    <div className="popup">
      <h1>NeuralTab</h1>
      <p>{tab?.title ?? 'Loading...'}</p>
    </div>
  );
}
CWS Source Code Submission

When submitting to the Chrome Web Store, you upload a ZIP of your dist/ folder — the compiled output, not your source. However, CWS reviewers may request your source code separately to verify the build is reproducible. Always keep your src/ directory and ensure npm run build produces the exact same output from a clean checkout.

Then fix it by adding a null check. This exercise demonstrates the value of @types/chrome: it knows favIconUrl is string | undefined.
