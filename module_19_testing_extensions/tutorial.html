The Testing Problem

Extension code calls chrome.* APIs that don't exist in Node.js — where Jest runs. There's no real browser, no tabs, no storage, no message passing. The solution: manually stub the entire chrome global with jest.fn() mocks that you control. You're not testing Chrome; you're testing your logic that calls Chrome.

This distinction matters. Unit tests verify that given certain inputs, your code calls the right APIs with the right arguments, and handles the responses correctly. Whether the API actually works in a browser is a separate concern — that's what manual testing and E2E tests are for.

The Chrome Mock Pattern

// __tests__/setup.js (or inline in each test file)
const store = {};   // in-memory storage backing

global.chrome = {
  storage: {
    local: {
      get: jest.fn((keys, callback) => {
        const result = {};
        const keyList = typeof keys === 'string' ? [keys] : (keys || Object.keys(store));
        keyList.forEach(k => { if (k in store) result[k] = store[k]; });
        callback(result);
      }),
      set: jest.fn((items, callback) => {
        Object.assign(store, items);
        callback?.();
      }),
      clear: jest.fn((callback) => {
        Object.keys(store).forEach(k => delete store[k]);
        callback?.();
      }),
      getBytesInUse: jest.fn((keys, callback) => callback(0)),
    },
  },
  runtime: {
    lastError: null,
    onMessage: { addListener: jest.fn() },
    sendMessage: jest.fn(),
  },
};

Testing Storage Logic

// __tests__/storage_manager.test.js
describe('StorageManager', () => {
  beforeEach(() => chrome.storage.local.clear(jest.fn()));

  test('set and get round-trip', async () => {
    await StorageManager.set('key', 'value');
    const val = await StorageManager.get('key');
    expect(val).toBe('value');
  });

  test('getQuotaInfo returns numbers', async () => {
    const info = await StorageManager.getQuotaInfo();
    expect(typeof info.bytesInUse).toBe('number');
    expect(typeof info.quotaBytes).toBe('number');
  });
});

Testing Pure Functions — No Mock Needed

The best code to test has no side effects. compareVersions in MigrationManager is a pure function: given two version strings, it returns -1, 0, or 1. No chrome APIs, no state. This is the easiest thing to test and often the most valuable — it's the logic that determines which migrations run.

describe('compareVersions', () => {
  test('equal versions return 0', () => {
    expect(compareVersions('1.0.0', '1.0.0')).toBe(0);
  });
  test('higher major returns 1', () => {
    expect(compareVersions('2.0.0', '1.9.9')).toBe(1);
  });
  test('version sorting', () => {
    const versions = ['0.10.0', '0.9.0', '1.0.0', '0.2.0'];
    versions.sort(compareVersions);
    expect(versions[0]).toBe('0.2.0');
    expect(versions[3]).toBe('1.0.0');
  });
});

Coverage Thresholds

NeuralTab's jest.config.js requires 70% line and function coverage. This is deliberately moderate — the goal is to catch regressions in core logic, not to achieve 100% coverage by writing trivial tests. Coverage under 70% indicates that large chunks of code run with no automated validation. Coverage approaching 100% often indicates tests that add no real signal.

What Tests Can't Cover

Unit tests cannot verify: that your manifest.json permissions match what your code actually calls, that content scripts inject at the right time relative to page load, that the service worker wakes up on the right events, or that your UI renders correctly in the extension popup. These require manual testing or Playwright E2E tests against a real Chrome instance.

Exercises

Exercise 19-A — Run the Test Suite

In module_19, run npm install and npm test. All tests should pass. Then run npm test -- --coverage and find the coverage report. Which functions are below the 70% threshold? Which file has the lowest coverage?

Exercise 19-B — Write a Failing Test First

Add a test for a function that doesn't exist yet: StorageManager.setWithExpiry(key, value, ttlMs) that stores a value with a timestamp. Write the test first (it should fail). Then implement the function in storage_manager.js so the test passes. This is TDD — test-driven development.

Exercise 19-C — Mock sendMessage

Write a test for a message handler function extracted from background.js. The handler receives { type: 'getStorageQuota' } and calls sendResponse with the quota info. Mock chrome.storage.local.getBytesInUse to return 1024, and assert that sendResponse was called with { bytesInUse: 1024 }.
