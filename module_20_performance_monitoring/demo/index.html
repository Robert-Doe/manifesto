Module 20 — Performance Monitoring

MV3 service workers restart constantly. Measuring this is the first step to optimizing for it.

Message Latency Interpretation

LatencyMeaningStatus
< 5msSW was already running, responded immediatelyHealthy
5–20msSW was sleeping, woke up to handle messageNormal
20–100msSW startup + heavy initialization codeOptimize SW init
> 100msSW blocked on heavy synchronous work or storage I/OFix required

Minimizing SW Startup Time

// Bad: heavy work at module scope
const data = JSON.parse(fs.readFileSync('big-file.json')); // blocks startup

// Good: lazy initialization inside message handlers
chrome.runtime.onMessage.addListener((msg, _, sendResponse) => {
  if (msg.type === 'heavyOperation') {
    initIfNeeded().then(doWork).then(sendResponse);
    return true;
  }
});

The performance.mark() Pattern

// In background.js — instrument your own code
performance.mark('idb-start');
const results = await IDBManager.ready().then(m => m.searchVisits(q));
performance.mark('idb-end');
performance.measure('idb-search', 'idb-start', 'idb-end');
const [entry] = performance.getEntriesByName('idb-search');
console.log('IDB search took', entry.duration, 'ms');

Storage Monitoring Strategy

NeuralTab calls getBytesInUse(null) periodically. The 10MB local storage limit is generous for most extensions, but history + network events can grow fast. The rolling window pattern (Module 07: 10,000 IDB entries max; Module 09: 500 network events max) prevents unbounded growth without needing a quota monitor.
