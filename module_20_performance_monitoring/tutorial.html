What "Performance" Means in an Extension

Extension performance has two dimensions: latency (how long individual operations take) and overhead (how much the extension costs in CPU, memory, and storage, passively). A fast popup that opens instantly is latency. An extension that slows down every page load is overhead. Users notice both, but overhead complaints dominate reviews — "this extension makes Chrome slow" is a one-star killer.

performance.now() in the Service Worker

performance.now() is available in MV3 service workers, but with an important caveat: it returns milliseconds since the service worker started, not since Chrome launched. Every time the SW wakes up from sleep, the clock resets. This means you can't use it to measure total uptime — only elapsed time within a single SW activation.

// In background.js — capture start time at module scope:
const SW_START = Date.now();   // wall-clock time, persists in module scope

// Measure message handler latency:
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  const t0 = performance.now();
  handleMessage(msg).then(result => {
    const latencyMs = performance.now() - t0;
    recordLatency(latencyMs);
    sendResponse(result);
  });
  return true;
});

Measuring SW Uptime

Since performance.now() resets on each SW start, measure uptime using wall-clock time: record Date.now() at module scope, persist it to chrome.storage.session on first start, and compute uptime as Date.now() - firstStartTime. Also increment a counter in session storage to track how many times the SW has restarted.

const SW_START = Date.now();

// On first run in this browser session:
chrome.storage.session.get(['swStartTime', 'swStartCount'], (data) => {
  if (!data.swStartTime) {
    chrome.storage.session.set({
      swStartTime: SW_START,
      swStartCount: 1,
    });
  } else {
    chrome.storage.session.set({
      swStartCount: (data.swStartCount || 0) + 1,
    });
  }
});

Why No performance.memory

performance.memory — which shows heap size, used heap, and total heap — is available in browser tabs but not in service workers. To see extension memory usage, open Chrome's Task Manager (Shift+Esc) and look for "Extension: NeuralTab." The service worker and each page (popup, options, sidepanel) get separate rows.

setInterval vs. chrome.alarms

Never use setInterval in a service worker to keep it alive or do periodic work. Chrome will terminate idle service workers after 30 seconds of inactivity. A setInterval that fires every 5 seconds will keep the SW alive — consuming CPU and preventing the browser from reclaiming resources — in direct violation of Chrome's guidance and CWS policy.

// ❌ Keeps SW alive permanently — CWS policy violation:
setInterval(() => { doPeriodicWork(); }, 5000);

// ✅ Correct pattern — SW sleeps between alarm firings:
chrome.alarms.create('periodicWork', { periodInMinutes: 1 });
chrome.alarms.onAlarm.addListener((alarm) => {
  if (alarm.name === 'periodicWork') doPeriodicWork();
});
Storage as Performance Data

NeuralTab records message latency P50 in chrome.storage.local. Keep this data compact — store only a rolling window (last 100 measurements), not every measurement ever. Storage reads and writes are themselves async operations with ~1ms overhead; measuring them too often creates measurement-induced distortion.

Exercises

Exercise 20-A — Benchmark Message Latency

Open perf_monitor.html. Click "Run Message Benchmark" — it sends 20 messages and records the P50 latency. Open a tab that's doing heavy work (streaming video, a complex SPA). Click the benchmark again. How much does background tab CPU pressure affect extension message latency? Record the results for both scenarios.

Exercise 20-B — SW Restart Counter

Open the Performance Monitor, note the SW start count. Then navigate to chrome://serviceworker-internals, find the NeuralTab worker, and click "Stop." Return to perf_monitor.html, send any message (which will wake the SW), and reload. Verify the restart count incremented. Repeat 5 times — understand how often Chrome terminates extension SWs in normal use.

Exercise 20-C — Add chrome.alarms Scheduling

Add a chrome.alarms.create('cleanup', { periodInMinutes: 60 }) to background.js that runs StorageManager.pruneOldData() every hour. Add a "Last Cleanup" timestamp to the perf_monitor.html dashboard. Verify via the alarms API that the alarm is registered: chrome.alarms.getAll(console.log) in the background console.
