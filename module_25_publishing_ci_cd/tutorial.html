The Chrome Web Store Pipeline

Publishing to the Chrome Web Store is not a git push. It's a multi-step process involving OAuth2 credentials, a ZIP upload, a publish API call, and a human review period that can range from hours to weeks. Automating this process eliminates the class of errors that occur when you zip the wrong directory, forget to bump the version number, or publish to production when you meant to test in the developer dashboard.

CWS Publish API Authentication

The CWS Publish API uses OAuth2 client credentials flow — not the user-facing launchWebAuthFlow from Module 12. You register a Google Cloud project, create an OAuth2 client, and exchange client credentials for a short-lived access token in your CI pipeline.

# Step 1: Get access token using client credentials
ACCESS_TOKEN=$(curl -s -X POST \
  "https://oauth2.googleapis.com/token" \
  -d "client_id=$CWS_CLIENT_ID" \
  -d "client_secret=$CWS_CLIENT_SECRET" \
  -d "refresh_token=$CWS_REFRESH_TOKEN" \
  -d "grant_type=refresh_token" \
  | jq -r '.access_token')

# Step 2: Upload the ZIP
curl -s -X PUT \
  "https://www.googleapis.com/upload/chromewebstore/v1.1/items/$CWS_EXTENSION_ID" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "x-goog-api-version: 2" \
  --data-binary @dist.zip

# Step 3: Publish
curl -s -X POST \
  "https://www.googleapis.com/chromewebstore/v1.1/items/$CWS_EXTENSION_ID/publish" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "x-goog-api-version: 2" \
  -H "Content-Length: 0"

The Three-Job GitHub Actions Pipeline

Job 1: lint-and-validate

Runs on every push and pull request. Validates manifest.json (required fields, permission list), runs npm test with coverage thresholds, and fails fast if anything breaks. This is the gate that blocks bad code from advancing.

Job 2: build

Runs if Job 1 passes. Executes npm run build, creates a ZIP with the right exclusions (--exclude "*.map" --exclude ".git" --exclude "node_modules"), and uploads the ZIP as a workflow artifact so it can be downloaded for manual inspection or used by Job 3.

Job 3: publish-to-cws

Runs only on pushes to the main branch (not PRs, not other branches). Downloads the ZIP artifact from Job 2 and runs the three CWS API calls. This job has access to three secrets: CWS_EXTENSION_ID, CWS_ACCESS_TOKEN (refresh token), and CWS_CLIENT_SECRET.

# .github/workflows/ci.yml (publish job condition)
publish-to-cws:
  needs: build
  runs-on: ubuntu-latest
  if: github.ref == 'refs/heads/main' && github.event_name == 'push'
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: extension-zip
    - name: Publish to Chrome Web Store
      env:
        CWS_EXTENSION_ID: ${{ secrets.CWS_EXTENSION_ID }}
        CWS_ACCESS_TOKEN: ${{ secrets.CWS_ACCESS_TOKEN }}
      run: |
        # upload + publish commands here

Review Times and Staged Rollout

First-time submissions are reviewed by a human and can take 1-3 weeks. Subsequent updates for extensions without sensitive permissions typically clear in 1-3 business days. Extensions with the debugger, cookies, or nativeMessaging permissions always get manual review, regardless of update history.

CWS supports staged rollout: you can publish to 5%, 20%, or 50% of users before full rollout. This is configured in the Developer Dashboard, not the API. Use staged rollout for major changes — if your update breaks something, 95% of users never see the broken version.

Exercise 25-B — Set Up CI Secrets

Fork the NeuralTab repo on GitHub. Go to Settings → Secrets and Variables → Actions. Add the three required secrets as placeholders: CWS_EXTENSION_ID (use any string), CWS_ACCESS_TOKEN, CWS_CLIENT_SECRET. Push a commit to a feature branch and watch the CI pipeline run. Job 1 and Job 2 should run; Job 3 should be skipped (not on main). Then merge to main and verify Job 3 runs (it will fail without real credentials, but the run confirms the condition works).
